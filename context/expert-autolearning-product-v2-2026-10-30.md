# Linx Expert 自动学习与进化方案｜V2

日期：2026-10-30。状态：产品与架构收敛稿，不代表功能已实现或已通过运行验收。

:chatgpt-content-reference{index="10"}[下载完整 Markdown 方案](sandbox:/mnt/data/linx-expert-autolearning-evolution-v2-2026-10-30.md)，包含实施阶段、详细验收场景和技术基线。

**核心结论：以 Hermes 为机制参考，以 Synara 为学习与资产底座，由 Expert 绑定的单一 Harness 完成任务执行与学习。用户只需要正常使用、持续反馈、审核结果，不需要管理经验如何转化为能力。**

本版替代 V1 中“完整对齐 Hermes”的目标。改为围绕 Expert 的培养价值，选择必要能力。附件中的技术限制和未验证事项继续保留，不将调研可行性视为实现完成。:chatgpt-content-reference{index="0"} :chatgpt-content-reference{index="1"}

## 一、产品定位：用户培养出来的专长 Agent

Expert 是用户在真实工作中培养出来的 Agent。它围绕一件事或一类事，逐步掌握用户的做事方法、判断标准和交付要求。

培养的价值不是“新增了多少经验和 Skill”，而是：

**同类任务越做越符合要求，重复纠正越来越少，执行过程中需要用户参与的判断越来越少。**

用户不需要进入专门的培养流程。提出任务、指出问题、修改结果、表达偏好，就是培养过程。经验识别、分类、合并、Skill 修订和后续应用，由系统自动完成。

完整生命周期为：

**真实任务与反馈 → 自动学习与改进 → 逐渐能够独立完成 → 用户关闭自学习 → 发起任务与审核验收。**

产品上只保留两个主要状态：**培养中、自学习已关闭**。用户随时可以关闭或重新开启，不设置必须通过的毕业考试、逐项经验验收或能力发布审批。

关闭表示停止自动修改长期能力，不自动等同于“所有任务都已验证成功”。

## 二、核心原则与架构

### 2.1 学习默认自动，汇报不阻断

开启自学习后，默认自动完成提取、整理、修订和生效。普通学习不需要用户逐项确认，也不再增加一个必须单独开启的“自动采用”步骤。

经验、候选、差异和版本可以保留在内部，但不转化为默认的用户待办。

进化星图负责展示变化，版本机制负责撤回变化，用户反馈负责纠正方向。三者都不应阻断正常学习。

既有用户明确设置的资产保护或审批策略仍然保留，但不新增一套必经审批流程。

### 2.2 学习机制归 Synara，执行归 Harness

**“学习机制独立于 Harness”与“谁执行谁提取”并不矛盾。** 前者规定业务逻辑归属，后者规定学习任务由谁运行。

```text
用户使用 Expert，并在工作中反馈
                  ↓
Expert 绑定的 Harness 执行任务
                  ↓
Synara 收集当前任务证据、识别学习时机
                  ↓
同一 Harness 执行学习
简单修订可在前台提出，完整复盘使用独立后台会话
                  ↓
Synara 自动校验、提交并更新绑定
        ┌─────────┴─────────┐
   Skill Library       Space Memory
   方法、步骤、资源     偏好、事实、环境
        └─────────┬─────────┘
                  ↓
后续独立 Run 自动装配，进化星图记录变化
```

Synara 负责学习策略、触发、证据、资产归属、版本、生效和用户控制。Harness 负责推理与工具执行，不拥有正式知识库的管理规则。

一个 Expert 长期使用一种 Harness。后台学习可以建立独立会话，但不切换到另一种 Harness，不隐式更换模型、实例或账户。

继续扩展现有 `experts/evolution`、`ProviderAdapter`、Gateway 和正式资产服务。不另建 Agent Loop、事件总线、并行 HarnessAdapter 框架或第二套 Skill 库。这延续附件推荐的宿主接入路线。:chatgpt-content-reference{index="2"}

### 2.3 不依赖 OMP 原生 AutoLearn

OMP 原生 AutoLearn 不作为主链路的必要依赖。学习触发、写入和生效规则由 Synara 统一掌握。

在 Linx 托管的 Expert 会话范围内，关闭或隔离原生自动持久写入，避免两套学习系统分别修改资产。不修改用户全局 OMP 配置。

原生 capture、事件 Hook 等能力可以按需复用，但只有在确有收益、边界经过验证时才接入，不能重新成为平台依赖。

附件已指出：原生 capture 的工具名单、Memory backend 和正式资产写入都存在接入限制。仅接入 Gateway 再打开 AutoLearn，不能形成完整闭环。:chatgpt-content-reference{index="3"}

## 三、能力范围：借鉴 Hermes，但不完整复刻

以下编号沿用原技术调研。表中的取舍是本版方案决策。

| 能力                                 | V2 取舍          | 使用方式                                       |
| ------------------------------------ | ---------------- | ---------------------------------------------- |
| C01 Skill 发现与使用                 | 保留并复用       | 使用正式技能库和固定 Run 装配                  |
| C02—C04 主动修订、用户纠正、资料学习 | **核心能力**     | 在正常工作中自动学习，不要求用户加工经验       |
| C05—C06 自动与聚焦复盘               | **核心能力**     | 以任务事件和反馈触发，支持自然语言要求重点学习 |
| C07 长期记忆                         | 保留，归属 Space | 正式条目化存储，不新增 Expert 私有 Memory      |
| C08 写入管理                         | **自动为默认**   | 普通学习自动提交；审批只兼容用户明确配置的策略 |
| C09、C10、C13 生效、记录与恢复       | 保留并整合       | 支撑自动装配、进化星图、撤回和版本恢复         |
| C11 陈旧判断与自动归档               | 后置             | 不因低频使用自动归档用户培养的技能             |
| C12 合并与去重                       | 部分保留         | 日常修订中的简单去重保留，跨技能整包合并后置   |
| C14 评测型自进化                     | 后续增强         | 不要求每次学习先做基础版与候选版对比           |
| C15 历史会话搜索                     | 排除             | 不扫描跨会话历史                               |
| C16 工具实现、系统提示自动优化       | 本版不纳入       | 不自动改 Harness 实现、平台工具或系统级策略    |

Hermes 最值得迁移的是：

**识别学习信号 → 查看已有方法 → 修订准确版本 → 持久化 → 在后续任务中使用。**

同时保留 Skill 的模板、参考资料、配套脚本等组织能力，而不把所有经验都塞进一段不断变长的提示词。附件也明确区分了这种机制迁移与直接移植 Hermes Runtime。:chatgpt-content-reference{index="4"}

自动学习可以改进方法、判断条件和验收标准，但不自动扩大用户授权，也不自行改变 Expert 的职责范围。

## 四、自动学习闭环

### 4.1 从正常工作中学习

学习信号包括用户纠正、对成果的修改、明确的长期要求、执行中的方法缺口，以及失败后找到的有效修正。用户指定的资料也可以成为学习来源。

用户不需要标记“这是经验”。系统自行判断它属于本次要求、长期偏好还是通用方法。

例如，“这次汇报正式一点”优先作为当次要求；“以后这类汇报都先给结论”更新长期方法。判断偏差通过后续自然反馈修正，不把每次不确定性都交还用户。

明确纠正可以直接修订，不必等待重复出现，也不必先做额外评测。任务结束可以触发复盘，但结束本身不被当作成功证据。

### 4.2 简单修订直接处理，完整归纳后台完成

前台 Agent 可以通过学习工具提交明确的小幅修订，例如补充遗漏步骤、修正模板或记录稳定偏好。Synara 自动处理，不要求再启动一次后台复盘才能生效。

多步任务、连续反馈或需要综合执行过程的学习，由 Synara 创建独立后台会话，仍使用该 Expert 绑定的 Harness。后台不占用原前台会话，不阻断用户继续工作。

触发以任务阶段完成、明确反馈、失败修复和用户主动要求为主。计数或周期仅作为补充。

相邻信号可以合并，同一证据不重复提炼。前台修订与后台复盘共用提交记录，避免重复创建经验。没有新增价值就不修改，不为了展示成长而制造更新。

### 4.3 自动决定写入位置

**方法、判断标准和验收规则优先进入 Skill；偏好、事实和环境信息进入 Space Memory；单次任务状态继续留在 Task/Run。**

优先修改已有 Skill，只有独立方法确实值得复用时才新增。修改可以覆盖入口、模板、参考资料和配套资源，而不只是新增一条总结。

默认只改变当前 Expert 的技能行为。共享或只读来源按既有策略自动派生适合该 Expert 的版本，不静默改变其他 Expert；用户已明确允许的共享更新按其设置执行。

Space Memory 仍是一套正式存储。条目可以标注 Expert、Project 等适用范围，避免把某个 Expert 的局部偏好推广成整个 Space 的通用要求。

用户不承担上述分类、派生和搬运工作。

### 4.4 自动生效，不需要用户发布

普通学习路径为：

**识别经验 → 定位现有资产 → 生成修订 → 自动检查与提交 → 更新绑定 → 后续任务自动使用。**

候选、Diff 和写回执保留在内部。不为普通修订增加必经的审查 Agent，也不要求用户点击“采用”。

当前 Run 的装配版本保持固定，恢复和自动续接沿用原版本；后续独立 Run 自动加载最新已提交且绑定完成的内容。这一运行语义沿用原方案。:chatgpt-content-reference{index="5"}

这不妨碍当前任务立即响应用户反馈。纠正已经进入当前对话，Expert 可以立刻调整本次交付；只是后台不改写活跃 Run 的固定资产快照。

写入、绑定和实际装配分别记录回执，不能仅凭模型说“已经学会”就报告能力已应用。

## 五、产品交互：进化可见，学习不打断

### 正常任务是主入口

用户主要做三件事：使用 Expert、给出反馈、决定是否继续自学习。

不要求用户清理经验 Inbox，不要求逐条选择保留、合并或转成 Skill。版本冲突和可恢复的学习失败默认在后台处理，不阻断正常交付。

只有持续无法学习、且确实需要用户处理时，才做合并提示。遇到不能修改的来源，优先自动派生；无法自动处理时跳过该项并记录原因，不把整个任务卡在学习上。

### 进化星图展示具体变化

沿用进化星图，不新增一套经验审批中心。节点优先表达“以后哪些事情不需要再提醒”，而不是内部处理步骤。

例如：

> 已调整周报筛选：优先收录实质能力变化，过滤营销稿。

> 已补充代码审核检查：区分真实缺陷与没有依据的重构建议。

展开节点后，可以查看来源任务、相关反馈、修改内容、受影响资产，以及撤回入口。原始经验、Skill Diff 和版本属于详情，不是日常必填表单。

以已提交的变化为主要内容。正在学习等状态可以轻量展示，但不设计成用户必须处理的待办。尚未实际应用或验证效果的修改，不标成“已提升成功率”。

汇报按任务或学习周期聚合。没有变化不通知，不逐条播报每次记忆写入。

### 用户可以自然纠偏和撤回

用户可以直接说“不是这个意思”“撤回刚才学到的规则”，系统负责关联变化并修正。也可以从星图节点撤回。

撤回针对相关内容，保留其他有效改进和来源记录。恢复后的版本在后续独立 Run 生效，不自动撤销已经交付的结果或已经发生的业务动作。

## 六、关闭自学习：从培养转向稳定使用

用户随时可以关闭，不需要先评测、逐项验收经验或完成发布操作。

关闭后，停止该 Expert 的新学习触发和自动能力写入，取消尚未完成的学习任务。关闭之后才到达的旧写入不能提交。此前已经完整提交的能力保留，不因关闭而撤销。

稳定使用期间，Expert 继续读取任务资料、必要的 Space 事实和既有能力。临时指令仍然有效，但只影响当次任务，不自动成为长期规则。任务进度和交付记录照常保存。

为避免其他更新绕过关闭开关，技能绑定及影响做事方式的长期规则保持版本固定。Space 中的业务事实仍可按任务读取；必要的规则版本引用随 Expert 保存，不另建私有 Memory。外部 Skill 更新不静默替换定型绑定。

用户手动修改配置或明确升级版本仍然允许。重新开启后，基于当前能力继续培养，不复活关闭前的旧写入，也不扫描历史会话补学。

**关闭冻结的是自动学习带来的长期行为变化，不是理解新任务和执行工作的能力。**

## 七、技术落地：可靠性由系统承担

### 7.1 沿用现有运行路径

首批适配 OMP 与 Pi。OMP 优先复用现有 ACP，Pi 复用现有 SDK Adapter。只有 ACP 的具体缺口无法补齐时，才评估受控 OMP SDK Worker，不预先增加第二条运行路径。

在既有 Adapter 能力说明中记录证据覆盖、学习工具、受限执行、取消恢复和固定装配的实际支持情况。某端缺少能力时，只限制对应学习功能，不自动换 Harness 代做，也不一并禁用正常任务执行。

附件已经指出，两端的接入方式与权限语义不同，不能因为 OMP 基于 Pi 就默认兼容。:chatgpt-content-reference{index="6"}

### 7.2 使用当前任务的有界证据

复用现有持久事件链路，在裁剪前形成有界证据快照。保留用户要求和反馈、工具输入输出、错误与修正、成果引用、已有验证，以及所用 Expert/Skill 版本。

长内容保留相关片段和受控引用，同时标注截断。调试日志不作为唯一业务证据，不要求获取 Harness 私有推理，也不另开消费者争抢运行事件。这与附件对证据采集的要求一致。:chatgpt-content-reference{index="7"}

### 7.3 统一资产入口，不重复建设

正式写入通过 Skill Library 与 Space Memory 服务完成。复用稳定 ID、版本、不可变包、派生、绑定和回执，不直接修改 Harness 投影目录。

Space Memory 需要正式数据服务，不能把已有 Space 目标、共享指令字段或 Hub 项目记忆直接当作它。这是原调研已经识别的缺口。:chatgpt-content-reference{index="8"}

学习请求、证据引用和变化记录优先扩展现有模型。进化星图直接展示真实学习事件，不再维护独立的“星图知识库”。

服务端处理归属、版本冲突、重复请求和部分提交。提交前复核学习开关及授权代次，避免关闭后迟到提交，或重开后旧请求复活。这些都是内部机制，不变成用户审批。

### 7.4 后台受控，前台优先

后台只开放本轮需要的读取和学习写入能力，不继承任意业务执行工具。权限限制通过实际测试证明，不只依赖提示词。

学习任务不再次触发学习。设置并发、上下文和调用预算；前台优先，后台可以延后或取消。只重试可恢复错误，不无限循环自我润色。

**后台隔离、版本一致性和取消是工程验收项，不是用户操作项。** 普通小幅修订不统一要求跑完整对比实验。

## 八、评测型自进化：增强能力，不是学习门槛

首版先实现从真实工作中自动学习。评测型自进化用于后续更有价值的优化，例如复杂流程的多种候选方法比较，而不是每次修改都运行基础版和候选版。

评测由同一 Harness 执行，固定基础版与候选包、模型选择、输入和工具条件。使用明确提供的样例、当前任务证据或受控生成样例，不挖掘历史会话，也不对真实业务重复产生外部副作用。

实际装配被评测的候选包，采用时保存相同内容。优先依据任务完成和产物检查，模型评分作为补充。没有可靠收益或实验失败，就保留原版本，不要求用户处理每个失败候选。

该能力同样受自学习总开关控制。用户不必手动发起实验才能获得日常改进，也不必完成评测才能关闭学习。

附件对 Hermes 独立 self-evolution 的定位仍然适用：可以参考优化思路，但存在源码衔接问题，不能当作已经可直接移植并证明收益的模块。:chatgpt-content-reference{index="9"}

## 九、实施顺序与验收目标

| 阶段              | 交付重点                                                     | 完成标准                                           |
| ----------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| A：运行与资产基础 | 当前 Run 证据、学习工具、Space Memory、OMP/Pi 路径和版本装配 | 两端分别证明能受控读取、提交、取消和再次加载       |
| B：自动学习闭环   | 反馈学习、资料学习、前台修订、后台复盘、自动提交与绑定       | 不依赖人工采用，后续独立任务能使用更新后的能力     |
| C：成长与稳定使用 | 进化星图、聚合汇报、撤回、关闭与重开、前台优先和失败恢复     | 用户无需管理经验；关闭后没有迟到写入或静默规则升级 |
| D：可选评测优化   | 候选比较、真实 Harness 评测、选择与回归                      | 实际收益有依据，采用内容与被评测包一致             |

**A—C 构成首个完整版本。** 完整 Curator、自动陈旧归档、跨包合并和大规模优化搜索，不属于首版必做范围。

产品验收重点是：用户纠正后无需额外确认；下一次同类任务能够复用；学习过程不阻断工作；成长记录与真实变化一致；关闭与撤回确实有效。

效果主要看同类任务中的重复纠正是否减少、过程介入是否减少、交付验收是否稳定。区分任务类型和能力版本，不用经验数、Skill 数或调用次数代替能力提升，也不把用户未继续回复计为验收通过。

这些观察用于产品改进，不形成用户结束培养前必须达到的门槛。

**最终方案：Synara 自动组织学习并管理能力资产，单一 Harness 完成执行与提炼；用户只管使用、反馈和验收，进化星图解释变化，关闭开关结束培养。**
