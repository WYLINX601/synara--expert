## 一、工作量判断：分两期完成核心能力

| 阶段                          | 交付范围                                                                               |         工作量估算 |
| ----------------------------- | -------------------------------------------------------------------------------------- | -----------------: |
| **第一阶段：自动 Skill 学习** | 当前任务证据、自动提炼与采用、下一 Run 生效、进化星图、关闭学习与版本固定，覆盖 OMP/Pi | **12–18 工程人日** |
| **第二阶段：完整学习能力**    | Space Memory、前台学习工具、更灵活的资料读取、细粒度撤回                               |  **8–14 工程人日** |
| 第三阶段：可选自进化          | 实际任务评测、基础版与候选版比较、择优采用和回归                                       |      6–10 工程人日 |

核心能力合计约 **20–32 工程人日**。这是熟悉仓库的工程师的工作量预算，包含实现、受影响测试和真实 OMP/Pi 联调，不是排期承诺。新的 Harness、全平台安装包验证、OMP 大版本升级不计入其中。

分期的原因不是经验提取本身复杂，而是自动化涉及**事件采集、服务生命周期、正式资产提交、运行装配和关闭后的版本稳定**。这些不能只靠增加一个自动调用按钮完成。

**第一阶段保留你要求的自动体验，只延后 Memory 和前台学习工具。** 正式记忆仍归 Space，不用 Skill 临时冒充记忆，也不引入跨会话历史检索。这些边界延续原方案。:chatgpt-content-reference{index="1"}

## 二、代码已经有较好的基础，不需要重造学习引擎

当前仓库已经实现了两阶段提炼，以及正式资产采用、派生、版本恢复和星图展示。最适合的路线是：**把已有手动链路自动接通。**

| 已有基础                                                  | 第一阶段的处理                                 |
| --------------------------------------------------------- | ---------------------------------------------- |
| `SkillEvolutionService`：发现、生成、采用、取消与恢复     | 增加自动协调入口，复用现有业务                 |
| Skill Library：完整包派生、版本检查、幂等写入和绑定       | 直接复用，不建设第二套技能库                   |
| OMP/Pi 无工具提炼路径                                     | 继续使用，由 Synara 自动提交结果               |
| `RunSkillAssemblyStore`：当前 Run 固定、下一 Run 重新装配 | 增加关闭学习后的固定版本解析                   |
| 进化页、星图、差异与恢复                                  | 默认展示自动完成的变化，手动流程保留为辅助入口 |

其中有一项需要更新旧结论：**OMP 现在已经支持无工具提炼。** 仓库的后续验收记录包含 OMP 的真实发现、生成、派生采用、取消和下一独立 Run 装配。

但它目前通过 `OmpSkillEvolutionCompat.ts`，针对 **OMP 18.12.1 的固定构建**做兼容校验，并非任意版本都能直接使用。因此第一阶段应沿用当前路径，不同时引入最新 OMP SDK、SDK Worker 和工具链升级。

## 三、第一阶段架构：无工具复盘，不等于人工审批

这是本次最重要的简化。

**后台 Harness 负责分析并生成修改，Synara 负责自动保存、绑定和生效。** 后台不需要直接操作正式文件，也不需要用户批准。

```text
用户正常使用 Expert、给出反馈
                 ↓
现有 Provider 事件链路形成当前任务证据
                 ↓
ExpertLearningService
合并信号、固定来源、调度后台学习
                 ↓
现有 SkillEvolutionService
自动发现经验 → 自动生成修订
                 ↓
同一 Harness 的独立无工具会话
                 ↓
Synara 自动校验、保存、绑定
                 ↓
后续独立 Run 使用新版本
进化星图汇报实际变化
```

现有 `skill-evolution` 会话本来就不加载环境工具、MCP、原 Expert 上下文，也不直接保存内容。这个边界可以保留，改变的是宿主如何处理结果，而不是先放开后台 Agent 的权限。

这样既能实现自动学习，也避免首期被“后台工具白名单、MCP 写入口、新执行模式”拖大。

## 四、第一阶段的六项关键改造

### 1. 服务由宿主常驻管理，不再依赖进化页面

当前 `skillEvolutionRpc.ts` 在用户首次调用 RPC 时创建服务。观察逻辑异常后，也依赖下一次 owner 读取重新协调。**直接加自动触发，会遇到页面没打开、应用重启后学习无人推进的问题。**

建议新增 `ExpertLearningService`，由现有 Workbench 宿主负责启动、恢复和关闭。原 RPC 与后台共用同一个 `SkillEvolutionService`。

它只组织学习业务。原生任务、模型执行、取消和进程管理继续由宿主负责，不增加另一套 Agent 执行器。

### 2. 从“聊天正文”升级为“当前任务证据”

当前 `sourceFor()` 主要提取选定回合的用户与助手正文，无法可靠还原工具失败、修正和验证。原始事件又有保留限制，不能等任务结束后再假设日志完整。

建议在既有持久事件消费链路中，形成有界证据快照，保存：

- 用户要求与纠正，以及被纠正的必要上下文。
- 工具输入、结果、失败、修正和已有验证。
- 实际使用的 Expert、Skill 包及 Run 装配身份。

不另订阅一条 Provider 事件流，也不保存无限日志。工具证据增加独立引用类型，不能伪装成聊天消息。

来源超出预算时由系统选取关键片段，不再让用户手动选择“要提炼哪些消息”。

### 3. 自动推进两阶段，但不能直接“全部采用”

当前生成 Prompt 明确规定：**多个 proposal 是互为备选的方案，不是可以依次执行的修改。** 因此不能把现有 `proposals` 循环调用 `apply`。

自动模式应调整为：

> 发现若干独立进化点；每个进化点生成一份确定修订；依次生成、提交，再读取最新版本处理下一项。

同一目标的重复进化点先合并。没有新增价值就结束，不生成经验待办，也不发通知。

模型格式修正、版本冲突重生成都设内部预算。普通情况自动处理，不能解决的本轮跳过，不转化成用户必须清理的队列。

### 4. 复用正式提交，并解决“第一次学会后无法继续学”的问题

现有采用流程已经具备版本检查、持久操作 ID、完整包派生和“已保存但未绑定”的恢复机制，应该直接复用。

但当前新建技能的绑定只有：

```ts
{ skillId, enabled: true }
```

而 `allowEvolution` 缺省表示只读。直接复用，会让自动创建的新技能在下一轮无法继续改进。

因此，**自动创建的 Expert 专属技能，应由服务端显式绑定 `allowEvolution: true`**。权限不能由模型决定。

已有只读授权保持不变；允许改进的共享技能首次自动派生为当前 Expert 的专属版本，后续持续更新同一副本。整个过程不增加逐条审批。

### 5. “关闭自学习”同时关闭写入并固定能力版本

当前新独立 Run 的 `resolveLatest()` 会解析最新绑定和技能包。因此，只关闭触发器，还不足以保证后续使用稳定。

建议新增学习状态，包含：

```ts
{
  (enabled,
    epoch, // 学习授权代次
    revision, // 设置并发版本
    harnessKind,
    frozenSkills); // 关闭时的准确包引用
}
```

关闭时，在短提交锁内固定当前技能包，并将关闭状态、递增后的 `epoch` 和固定清单一起持久化。旧学习任务即使晚返回，也不能再提交。

新 Run 的解析规则变成：

```text
学习开启 → 最新已提交版本
学习关闭 → 关闭时固定的版本
已有 Run / 恢复 / 续接 → 原装配版本
```

用户主动改配置、恢复版本或明确升级仍然允许。普通共享源更新不能绕过关闭开关。

这些都是系统内部处理，用户仍然只操作一个开关。

### 6. 星图展示已完成变化，不展示待审批工作

复用现有 `ExpertSkillEvolution.tsx`、时间线、Diff 和恢复入口，不重新设计一个学习中心。现有组件已经具备这些展示与查询基础。

默认页面只需要自学习开关、轻量状态和成长变化。自动过程中的发现、生成、采用不成为用户操作步骤。

后台原生任务保留，必要时可从详情打开，但不自动跳转当前聊天，也不把任务列表塞满学习会话。

## 五、数据和代码改动范围

建议只新增三类持久数据，继续使用现有数据库与 Expert 扩展迁移：

| 新增数据                   | 职责                                               |
| -------------------------- | -------------------------------------------------- |
| `expert_learning_states`   | 学习开关、授权代次、绑定 Harness、关闭后的固定版本 |
| `expert_learning_evidence` | 当前任务的有界证据快照                             |
| `expert_learning_cycles`   | 学习推进记录，关联现有发现、生成和采用请求         |

原有进化请求、候选、采用事件和原生任务继续复用。**不再建立一套重复的任务状态库。**

## 六、实施批次与验收

建议拆成五个可审查批次：

| 批次 | 内容                                       |
| ---- | ------------------------------------------ |
| PR1  | 学习状态、宿主共享服务、自动提交与关闭边界 |
| PR2  | 当前任务证据、来源身份、事件去重与触发     |
| PR3  | 自动发现—生成—采用，完成固定版本解析       |
| PR4  | 开关、星图、后台任务呈现与草稿保护         |
| PR5  | OMP/Pi 真实验收、故障恢复、修正及文档回写  |

第一阶段的验收重点不是“能生成 Skill”，而是：

**用户正常反馈后，不进入进化页面、不选择经验、不点击采用；下一次独立任务确实使用更新后的方法。关闭学习后，旧后台结果不能写入，后续任务继续使用固定版本。**

同时验证第二次纠正能够继续改进同一技能、应用重启不重复创建或采用、当前业务任务不被后台学习阻断。装配回执与实际输出分开检查，不把“文件已经存在”当成“Expert 已经学会”。

**最终建议：先自动化现有的 Skill 进化链路，再扩展 Memory 和带工具学习。** 这比先迁移一套完整 Hermes 学习系统更贴合当前代码，也能更早实现你要求的“越用越好用”。

本轮完成的是源码核对与技术设计；未修改仓库、未调用用户模型，也未执行新增方案的测试。
