# Synara 专家技能索引与共享版本包研发方案

## 2026-10-29 优化候选：内容、索引与原生执行分层

本轮基于 `f879925a4`，实现和实际检查统一见[优化验收](./skill-management-optimization-acceptance-2026-10-29.md)。下列规则描述本轮候选，不自动成为 main、安装版或跨平台验收结论。

- **内容与索引**：既有包 ID 仍由内容清单决定。读取只验证资源路径、类型、大小、哈希、执行位和统计；入口名称、描述、解析字段和诊断从已验证字节重建。旧清单的派生字段不是完整性依据，原文件不重写。安全路径与容量仍严格检查，目标平台名称限制不扩大到所有宿主。
- **固定引用**：快照、Run 恢复和 Provider 二次校验共用包／入口／文件引用验证。已持久化 Run 保留其解析元数据和策略，continuation 不接受新的默认策略覆盖；新独立 Run 才解析当前库头版本。既有指纹保持兼容。
- **完整交付**：公共投影只提供完整资源树和选定入口身份，不删除未选的 `SKILL.md`。Claude 插件、Agent 定义、名称空间与 manifest 处理留在 Claude 适配；其它端使用各自原生允许名单或路径配置，并确认实际启用集合。不能精确筛选时明确报告，不自动扩大入口。
- **绑定与资源**：`selectionScope` 缺省为 `entry`，`package` 按锚点当前包展开。100 条配置绑定与最多 5000 个展开入口分别检查。`resourceMode` 缺省共享只读；`run-private` 生成独立文件的持久工作树，同包按启用绑定统一模式。私有根引用及原所有者随跨 Worker continuation 继承，原生实际读写同一工作树，恢复不覆盖输出；固定输入漂移单独报告，不标为源包损坏。
- **当前配置**：本功能尚未发布，直接使用当前技能库绑定。删除旧配置转换入口、接口、CLI 命令、映射摘要和采用时兼容分支，不建立自动迁移；普通绑定继续使用修订检查和持久操作回执。
- **界面收敛**：用户否决新增板块、技术选项和更多菜单。沿用原有技能选择与启停；专家直接编辑当前技能库绑定，诊断只在现有详情或检查中按需显示。整套选择继续使用原有多选，运行器和资源模式能力留在后台及高级 CLI。
- **提炼与采用**：候选采用直接针对保存的技能库绑定；新增与派生继续按同一操作收据恢复保存和绑定，不经过旧配置转换。OMP 仅在已注册用途下启用精确 bundle／私有 preload 约束，并在原生会话创建后及发送前验证空工具和固定系统提示；与普通 Gateway、MCP 及环境技能分开。Codex 提炼仍未支持。Pi／OMP 的显式技能引用只交付已核对的名称和实际资源路径，不以引用文本替代原生能力执行证据。

Run 私有工作树包含用户产生的输出，不作为可任意重建的缓存。引用仍在时保留工作树和源包；本轮没有建立自动清理历史输出的服务。

2026-10-29 界面与元数据收敛：专家、专家团、技能复用同一弹窗表层，草稿／CAS／路由保护保留各自归属。技能定义与列表契约移除 `createdBy`，写入、筛选、CLI 和界面同步删除；`createdAt` 与用于鉴权及操作身份校验的 actor 保留。不新增数据转换或历史记录批量改写。下方历史方案中的添加者能力不再适用。

2026-10-29 用户最终取消“启动时加载”：新 `ExpertSkillBinding`、`ExpertSkillSelection` 不含 `activation`，严格作者接口拒绝该退役字段，CLI 删除 `--activation`；绑定展开不再区分锚点启动、也无最多一个启动技能的限制。公共运行接入只提交名称、用途和固定入口的目录，删除正文预加载及 startup-only BMad 工作区预检；显式指定、原生工具／子代理／资源声明按原接入保留。

不可变快照／Run 的旧选择标记只作为历史数据读取，以保持旧 ID、内容指纹与未决初始化副作用保护；新原生入口与回执不产生该字段，不据此调用或加载正文。可变定义、操作日志和候选恢复的绑定读入时投影当前字段，保留范围、资源方式、启用状态及原请求身份；不新增转换操作、不批量改写历史快照或实例数据。下方旧方案中的启动加载与加载时机控制已退役。

### 3. G1/G11：原生兼容与排他装配

#### 3.1 Claude CLI 与空装配

默认固定 Expert 运行优先使用与应用 SDK 配套的应用私有 CLI。已核查本地 SDK `0.3.296` 随附 CLI `2.1.296`；SDK 在不指定 `pathToClaudeCodeExecutable` 时选择随附二进制，而现有应用始终显式指定。用户显式指定的 binaryPath 仍须尊重，启动前报告其兼容性，不静默替换；不升级全局 CLI 或改写认证配置。

启动前探测必须覆盖实际使用的初始化协议、插件交付、空/非空 Skill 过滤能力和实际版本，不能拿其他功能的最低版本门槛代替。私有 CLI 的打包、可执行分发和平台解析经过现有 process/platform 边界；版本支持范围由实际探测冻结。

空装配重新建立版本限定的证明：区分“已发现命令”“模型上下文中的 Skill”“Skill 工具可调用集合”，不再以 `reloadSkills()` 返回 16 项命令直接判断泄漏；显式空 allowlist、原生初始化/上下文和实际调用拒绝需要组合验证。`getContextUsage.skills` 本身是可选字段，不能对所有 CLI 一律将缺失当零，也不能因此永远拒绝合法空集。先用配套 CLI 验证其缺省语义和正/负对照，再将有证据的规范化规则写进特定版本适配器；若现有 API 不足，补应用私有兼容适配后再放行，不生成伪造零集合回执。

#### 3.2 保留原生 Skill，而非提示代理

- 移除字段黑名单与 `incompatibleReason` 引起的通用准入拒绝。合法文件可导入、保存、绑定；路径、包完整性和资源容量校验继续适用。
- Codex/Claude/OMP 的 wrapper 不能继续只保留 name/description 和两项布尔字段。优先使用原始入口的原生显式加载能力；需要投影的端构建可复用只读原生视图，完整保留 frontmatter/正文和包内相对资源，不依赖“请另读原文”实现 native hooks/fork。
- 名称如需原生命名空间化，由适配器保留 original/native 名称映射；除明确必要的标识变换，未知元数据原样保留。hooks 相对命令、原生 Skill 目录变量、脚本 cwd、跨目录资源必须有专门的保真用例。
- 原始内容与原生视图各有清单/hash；缓存按 provider + assemblyId + 投影版本命名，不能继续仅以线程 Expert snapshot ID 复用。共享不可变资源，不为每个 Run 全包复制，也不改上游源文件。
- 不承诺 Pi/Codex/OMP 会执行 Claude 特有字段。每端记录“原生支持 / 原生忽略 / 原生拒绝”的实际结果；Synara 不因字段名字禁止装配，不静默宣称已应用不存在的语义。
- startup 不能只拼正文就声称原生执行已发生。其激活要么通过该端真实原生调用，要么如实保持该端原有文本加载语义；回执区分已加载与原生行为已执行，不重复触发初始化 hooks。

#### 3.3 原生子运行

SDK 的主会话 Skill allowlist 不自动等于子代理排他继承；已核查 `initialize.skills` 只作用于 main session，`AgentDefinition.skills` 的 preload 声明也不证明排他。G11 的 `context:fork/agent` 需要单独验证，不能简单移除 `Agent/Task` 拒绝就交付。

研发先验证各端原生父/子会话的配置根、插件/入口集合和继承结果：能原生维持同装配的端走原生继承；需要宿主接管创建的端通过同一 Run 的已验证装配创建受管理子运行。不得静默把 fork 改成主会话文本执行。具体原生接缝在阶段 1 用真实对照固定后实施；G11 验收前必须证明实际支持行为，不能用 blanket block 通过。

父/子装配相同或为子集，父运行的 Skill 版本不能在子运行期间漂移；后台子运行继续持有相应包引用。普通未选 Expert 的子代理行为保持原范围。宿主已有授权继续适用，不因 Skill 中存在 hooks/allowed-tools/model 而移除审批、允许额外模型或读取凭据。

本轮沿用同一 native session 的共享任务门禁：旧后台子运行仍活跃时，新的换版 Run 继续排队，等待其自然结束或用户显式停止；等待期间不提前冻结库头，真正启动时解析最新版。不得为重建主会话销毁旧子运行的进程/消费者，也不增加同 session 并行换版承诺。此项和原生继承都列为阶段 1 验证前提。

### 4. 按 Run 解析最新 Skill

“下一次运行”定义见[产品生效表](./skill-management-product-discussion-v0.1.md#iteration-20261026)，不将审批、steering 或进程重启算成新 Run。

1. 排队阶段保存 Expert/调用意图；在共享 native 任务门禁放行后、任何可能执行 Skill 副作用的原生初始化/激活之前，在既有生命周期保护下读取当前已保存 Skill 绑定、enabled/activation 和各 Skill 最新头，构造独立 `RunSkillAssembly`。Persona/MCP/模型等仍按原任务契约，不混入其最新未采纳修改；绑定来源 revision 单独记录，避免将混合版本伪装成同一个完整 Expert revision。
2. 先发布不可变装配资源，再在既有执行记录中持久化该根 Run 的 assemblyId/准备状态及底层 turn 映射，之后才允许可能执行副作用的原生初始化、startup 或 Provider prompt。引用提交失败时不启动；重放幂等，不把孤立暂存资源当成功。初始化意图/尝试/完成单独留证，若初始化后、prompt 前崩溃且副作用是否完成不明，则恢复原装配并报告 uncertain，不自动重跑非幂等启动动作。普通按工具事件触发的 hooks 仍遵循原生契约，不将所有 hook 错误合并为“只执行一次”。
3. 同一 Run 发送重投、恢复、审批继续和子运行均读取已落盘装配。明确结束后用户重试属于新 Run，重新解析；无法确定是否已发送的自动重投仍沿用原 Run，不能追随库头。
4. Provider 会话复用前比较 assemblyId、元数据、加载语义和策略版本。变化时重建原生会话；保留用户/助手/工具历史，但不重放旧的宿主 Skill 目录/启动注入或有副作用的 hooks，不重置用户任务。
5. 解析中请求的 Skill/Expert 缺失、归档或并发失联时，不默默退回旧头、普通模式或默认 Skill；按真实对象状态返回可操作错误。正常解绑后得到空集合是有效零装配，不作为缺失错误。正在运行和恢复中的既有装配仍受引用保护，不被删除/GC 破坏。
6. 历史快照和历史验收不重写。对具有可验证 Expert 身份与当前定义的新 Run 按新策略准备；无法建立身份或旧策略不兼容的记录报告缺失项，不在后台批量转换或清理旧任务。

需要同步 `ProviderExpertSession`、装配 identity、native proof 和 receipt 的 assemblyId 归属，避免新内容错误命中旧线程的投影/证明缓存。持久化新增字段走现有扩展存储与恢复机制；具体迁移若有，按架构标准使用相应 ledger 并运行 migrations 检查。

根 Run 映射必须由执行意图/工作项标识落盘：同一请求的 goal 自动续跑即使产生新 turn，也继承原装配；同一 Hub 工作项的续跑/投递重试相同。独立 Hub 工作项或已结束后的新请求/显式重试创建新根 Run，原生子代理则继承父装配。内容/启停/加载语义/策略决定装配有效指纹；标签、时间和仅用于归因的 revision 不应单独导致 native 会话重建，仍在每 Run 审计记录中保存。

### 5. 来源刷新和内容迭代

桌面、CLI、后续 Agent 共用一条更新通道：保存/下载 → 完整资源校验 → 新不可变包 → revision CAS 切换头 → 读回结果。保留稳定 Skill ID、创建信息、标签、Expert 绑定及其启停/加载方式；保留不属于来源内容的用户配置。名称、说明、正文、完整支持文件和来源解析版本一起替换。

交互对齐 Multica：详情/列表菜单的一次“更新”和批量工具栏可执行来源更新；普通无本地编辑的条目不强迫先进入独立预览弹窗。底层仍可复用 prepare/preview 暂存和校验；本地修改覆盖时只针对明确目标确认，资源差异作为可选详情。CLI dry-run 输出同一变更计划，写入必须带 revision；旧计划失效拒绝，不覆盖新编辑。

只有可验证的 GitHub/Skills.sh/ClawHub 托管来源参加 refresh；manual/local/archive/runtime 走编辑或重新导入并替换稳定 ID。原有本地来源信息保留作来源记录，不转换成后台监听。分支跟踪与显式 commit/tag 固定严格按原来源；不能为找“最新”擅自换分支或仓库。无需定时器，不隐式调用外部脚本。

批量每项独立提交：`updated/unchanged/skipped/conflict/failed`，无托管源为 skipped，源内容相同为 unchanged；下载、内容校验、名称冲突及 CAS 失败不改变旧头或绑定。发布失败复用既有新包回滚和引用保护，不删除其他任务依赖的资源。更新在下一 Run 使用，当前运行没有热替换。

2026-10-27 审核修复：单项和批量的预览确认携带 `expectedPackageId`，服务端重新下载后严格比较，来源变化返回 conflict 并要求重新预览；未展示预览的一键更新继续读取执行时来源。远程下载、解包与独立校验在管理提交队列外完成，列表和文件读取直接读取已提交状态；提交时重新检查 revision、操作回执和授权。保存、替换导入及来源更新在包生命周期锁内、切换库头前，用候选头重新验证受影响 Expert 的启用装配，不要求全库名称唯一。

### 6. G4/G6：统一查询与批量绑定服务

查询将 Skill 库与当前 Expert 保存态聚合，统一输出被绑定的 distinct Expert 数及 enabled 数；“已使用”不等于启用。来源细类在服务端规范化；过滤维度间 AND/维度内 OR。时间未知项始终排后，排序最后追加名称/稳定 ID，避免 UI/CLI 不一致。维持已有文字搜索范围，本轮不顺带建设分页/搜索服务。

新增批量追加命令，不仅前端循环保存：输入确定 Skill ID 集合、目标 Expert revision 和 requestId；dry-run 与 apply 均由同一服务端规则生成计划。已有绑定跳过，不重启 disabled；新绑定 enabled + on-demand；保留单 Expert startup 约束与所有无关字段。

每个 Expert 的新增集合在现有 ExpertStore 的 CAS/队列内一次提交，多 Expert 逐项执行而非宣称跨对象事务。全部先做结构校验；每个提交点重验目标、Skill 存在与 revision；冲突不覆盖其他会话更改。重试相同 requestId 幂等，部分成功重试只处理未完成项。当前配置直接使用技能库绑定，不提供旧配置转换状态。

结果至少含 `expertId/status/oldRevision/newRevision/addedSkillIds/skippedSkillIds/error`；状态区分 applied/unchanged/conflict/failed。桌面确认页、批量结果和 CLI 使用相同结果对象，刷新双方缓存及使用统计。筛选变化不改变已确认的批量目标集合。

### 7. G7：CLI 与未来管理 Agent 接口

复用 `synara` 现有命令树，不把 `apps/server/scripts/cli.ts` 的构建发布脚本误当产品 CLI。增加独立管理 transport client，通过所选本机实例的现有 owner 授权能力调用服务端；不直接写 JSON/SQLite/内容包，不为了 CLI 开启 publicUrl 或新增跨机发现。

管理命令范围（实际实现与验证以本轮实施记录为准）：

```text
synara skill list|get|create|update|delete
synara skill import --url ... | --path ... | --file ...
synara skill refresh <id> | --skill-ids ...
synara skill files list|read|write|delete
synara skill tags set <id> ...
synara expert skills list|add|set|remove|enable|disable
synara expert skills add --expert-ids ... --skill-ids ...
```

list 支持与桌面相同过滤/排序；content 支持互斥的参数/stdin/本地文件输入；文件内容支持二进制传输。`--json` 输出版本化 envelope 与逐项结果，诊断只进 stderr；write 支持 expected revision、dry-run、requestId，删除/覆盖本地编辑需要明确的本次操作确认参数。成功、部分成功、参数错误、冲突、未授权和运行失败有稳定可测试错误码；读回返回持久化新 revision。

CLI 鉴权增加明确的本机 management 配对用途，不能只复用现有默认 client 的外部 MCP 配对：owner 在已登录桌面发起并确认一次性、短时、绑定 instanceId/flavor 的授权；CLI 交换得到可过期/撤销的管理凭据，单独私存。授予 `skill.manage` 与 `expert.skillBindings.manage` 对应的窄命令能力，不把普通 client 升成通用 owner，不允许借绑定接口改 Persona/MCP/模型等字段；服务端每次调用核验能力。原外部 MCP 凭据不隐式获得这些能力，本轮不新增 MCP tools。

实例用显式 profile/home/endpoint 及可信实例描述选择，保存/交换时校验 instanceId，CLI 使用 stdin 或私有凭据引用，不把 token 放进参数/日志。默认不启动新 server、不读写其他 app flavor 的 home；过期/撤销/错实例返回确定错误，回到 owner 明确授权的配对流程，不自动提权或重试登录。无认证的受信 loopback owner 路径按既有策略保留；未来 Agent 的实际委托与启用仍是后续任务，不因本轮有了管理凭据而自动获得授权。

服务端结构化命令能力为将来的管理 Agent 留出直接复用点；它可通过 CLI（后续若授权再接专用 tool）完成查询、预演、写入、读回。外部导入 Skill 不得把内容变成控制面指令或更换 CLI 目标实例。

## 2. 架构与数据所有权

### 2.1 四个核心对象

**技能包 `SkillPackage`**

保存一个明确目录边界内的完整资源，包括多个技能、脚本、模板和模块记录。以实际内容的 SHA-256 标识版本；Git commit、版本标签仅作为来源信息。

**技能入口 `SkillEntry`**

指向包内一个 `SKILL.md`，保存名称、描述、相对路径和兼容性信息。包中存在其他技能，不意味着它们自动加入专家的技能目录。

**专家选择 `ExpertSkillSelection`**

记录专家选择了哪些入口，以及加载时机：

```ts
type ExpertSkillSelection = {
  packageId: string;
  entryPath: string; // 包内相对路径
  activation: "startup" | "on-demand";
};
```

首期每位专家允许 **零或一个启动入口**，以及多个按需入口。同一专家不允许选择名称相同的两个技能，避免工作流按名称调用时产生歧义。

**任务快照 `ExpertSnapshotV2`**

继续固定 Persona、输出要求、MCP 和参考资料，技能部分改为固定包版本与入口选择。任务不再拥有技能资源副本。

现有 `references` 的保存机制保持原职责，本次只调整技能资源。

## 3. 包导入、更新与清理

### 3.1 导入流程

1. 选择本机 `SKILL.md` 或资源包目录。
2. 服务端生成只读预览：真实根目录、文件数、大小、入口列表、来源、冲突和兼容性问题。
3. 确认导入后重新校验来源；来源变化则返回“预览已失效”，不发布不同内容。
4. 在临时目录收集资源、计算哈希、设置文件权限并同步磁盘。
5. 原子发布到内容地址；相同内容已存在时校验并复用。

导入不执行包内脚本、不安装依赖、不修改项目配置。

### 3.2 完整性规则

- 内容哈希覆盖根目录名称、相对路径、文件类型、文件内容和可执行标记；不包含本机来源绝对路径和导入时间。
- 保留现有单文件 16 MiB、整包 100 MiB、5,000 个条目的上限，错误中明确超限项。
- 入口必须是包内普通文件；禁止路径穿越、大小写碰撞和特殊设备文件。
- 允许选择一个指向目录的外层软链接，预览展示其真实目标；包内部软链接首期明确拒绝。
- 不通过静默排除文件来缩小包。边界过大时要求重新选择目录。
- 发布前设置只读权限和可执行位；启动、恢复时校验资源清单。损坏版本不得自动替换为新版本。

只读存储和哈希校验用于维护版本完整性，不宣称它们构成对同一操作系统用户的安全隔离。

### 3.3 更新与删除

- “从来源导入更新”生成新包版本，展示新增、删除和变更入口。
- 更新 Expert 引用产生新 revision；新任务使用新版本，已有任务继续引用原版本。
- 删除包前检查专家定义、保留的 revision、任务快照和已接受的 Hub 工作引用；存在引用则拒绝并列出引用者。
- 首期提供手动删除无引用包，不建设后台自动 GC、远程包市场、自动升级或跨包版本求解器。
- 备份与恢复必须包含包、来源记录和任务清单，不能只备份快照 JSON。

## 4. 统一索引的运行行为

### 4.1 启动与按需加载

任务启动按固定顺序执行：

1. 固定 Expert revision、包版本和入口选择。
2. 校验包完整性、入口和当前工作目录的必要条件。
3. 生成仅包含所选入口的目录：名称、描述、固定绝对路径、加载时机。
4. 将目录及启动入口正文加入现有专家指令组合。
5. 使用当前 Provider 的指令注入机制启动会话并记录提交回执。

工作流正文不全部预载。模型根据目录，用现有文件读取能力读取原始 `SKILL.md`；相对引用始终以该文件所在目录解析。这符合 Agent Skills 的目录发现与渐进加载方式。[官方实现指南](https://agentskills.io/client-implementation/adding-skills-support)

目录过滤只是能力展示与调用路由，不是文件访问沙箱；包内资源和环境自带技能的可访问性仍由宿主权限决定。

### 4.2 显式调用

输入框选择专家技能时，提交 **入口标识＋任务快照标识**，不再接受客户端提供的任意文件路径作为执行依据。

服务端完成：

- 校验入口属于当前固定快照。
- 从固定包解析正文和技能根目录。
- 将完整正文加入本轮请求，不转发为 Provider 原生技能命令。
- 多技能调用按用户选择顺序处理并去重。
- 缺失、损坏或超出预算时明确失败，不静默跳过或截断。

默认单个 `SKILL.md` 上限 64 KiB，单次技能目录与正文组合上限 128 KiB，按 UTF-8 字节检查。普通非专家任务继续沿用现有技能发现与调用路径。

### 4.3 元数据兼容范围

- `recommended_skills` 仅作为推荐信息，不自动添加、激活或递归安装。

保留原目录名符合规范约定；遇到源技能名称不一致时展示诊断，不改写上游文件。[格式规范](https://agentskills.io/specification)

启动、停止后恢复、服务端重启、fork、handoff、Hub 接受与派发均从固定清单解析。恢复时不得读取最新 Expert 配置；新原生会话需要重新提交同一份固定目录。

角色正文持续属于基础指令。恢复、压缩或重试不自动重新执行角色初始化脚本；正文已提交不等于初始化动作已完成。

### 4.5 回执与失败语义

  packageIds: string[];

四端均检查预期指令与实际启动配置一致。回执写入失败沿用现有失败清理机制。

界面分别显示“资源校验通过”“目录已提交”和真实测试证据，不把目录提交写成“全部技能已执行”。版本缺失、权限不足或 Provider 不兼容时阻止启动，不切换专家、模型或资源版本。

## 7. 测试数据集中切换

提供一次性、可重入的切换工具，执行前生成具体清单：

1. 导入并验证所有新包，转换专家技能引用，保留专家 ID 和非技能配置。
2. 列出依赖旧快照的任务、运行记录、Hub 排队工作和资源目录。
3. 只处理明确列入清单的测试任务；发现普通任务引用则阻止清理。
4. 停止目标测试会话，通过宿主删除与取消能力清理关联数据，保留事件与引用一致性。
5. 保存切换备份和进度记录，发布新定义，再清理旧快照与投影。
6. 中断后根据记录继续；失败不得留下指向已删除包的定义。

保留普通任务、项目文件、账户凭据、MCP、Hub 参与名单及其他无关内容。切换失败通过备份恢复，不依靠运行时兼容旧快照。旧格式意外残留时明确提示需要完成切换。

## 8. 实施阶段与退出条件

实施顺序：P1 包存储与契约 → P2 四端统一加载 → P3 配置界面与 BMad → P4 真实验收与集中切换。

**P1：包存储与契约**

完成类型、导入预览、内容寻址、V2 快照和引用保护。退出条件：六位专家引用同一个包，快照不包含技能副本；源目录修改不影响固定版本。

**P2：四端统一加载**

完成目录、启动角色、显式调用、恢复与回执。退出条件：四端适配测试通过；缺失资源、错误版本和回执失败均能正确阻止启动并清理。

**P3：配置界面与 BMad**

完成最小界面、六角色预设和工作区预检。退出条件：用户可完成导入、配置、预检、调用、更新；角色入口、脚本和模板从完整包路径读取。

**P4：真实验收与集中切换**

在独立 worktree、home 和端口完成验证，再执行限定范围的数据切换。安装、推送、发布不包含在本方案的开发交付中。

## 9. 测试与验收标准

### 必须覆盖的场景

- **存储**：重复导入、并发发布、来源变化、失败中断、可执行位、损坏检测、路径越界、内部软链接、大小写冲突及容量限制。
- **版本**：新旧任务分别使用对应包；删除源目录后仍可运行；有引用包不可删除。
- **配置**：零启动入口、一个启动入口、多启动入口拒绝、重复名称、草稿冲突、断线晚返回、预检失败与更新差异。
- **调用**：只展示所选目录；伪造入口和快照引用被拒绝；显式调用读到固定正文；正文不被静默截断；环境存在同名技能时不误用。
- **生命周期**：首次启动、停止恢复、服务端重启、取消、fork、handoff、Hub 排队与派发；快照和目标不漂移，不重复派发。
- **BMad**：六角色入口不同而包相同；定制文件命中正确名称；跨目录模板及脚本可读；项目输出不写入包。
- **切换**：中断重试可恢复；保留字段和普通数据一致；清理后不存在悬空绑定。
- **平台**：macOS、Linux、Windows 的路径、权限和可执行行为。静态检查不能代替 Windows 实机结果。

### 真实运行证据

四端分别执行一个隔离小任务，用随机标记验证固定技能正文与配套资源确实被读取，再覆盖停止恢复和取消。BMad 六角色逐一验证身份入口，并完成一个包含工作流、模板和项目输出的小样例。

保持现有 Provider、模型和认证选择。认证失败记为阻塞，不自动更换模型或修改账户；未完成某端真实回合时，不报告“四端验收完成”。

### 最终检查

集中执行：

- `bun run fmt:check`
- `bun run lint`
- `bun run typecheck`
- 受影响 Vitest 与设置页/输入框 browser 测试
- `bun run test`
- `bun run workbench:check-boundaries`
- `bun run migrations:check`
- `bun run windows-runtime:check`

记录受检源码、Provider 版本、检查结果及未验证范围。性能验收以“同包只保存一份、任务启动不复制包、上下文不预载全部工作流”为确定条件；另记录导入、校验和启动耗时，不预设未经测量的提升比例。

专项方案作为架构权威记录，实施结果另记验收文档；`context/PROJECT_CONTEXT.md` 只更新入口、确认决定和当前状态。
