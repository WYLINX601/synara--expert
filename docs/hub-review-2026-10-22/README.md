## 2. 产品基线：需要合并理解，而非同时执行两版定义

| 对象或原则       | 本轮复核后的阅读基线                                                  | 状态                                                   |
| ---------------- | --------------------------------------------------------------------- | ------------------------------------------------------ |
| Hub              | 持续工作空间，可开展讨论和多项工作                                    | 沿用 V0.4                                              |
| Expert           | 角色、技能、资料、工具的可复用专业配置                                | 沿用                                                   |
| 专家团           | 可复用的成员、用途、协调方式与协作偏好配置；不是运行实例              | V0.4 修订 V0.3「不设独立 Team」                        |
| 当前 Hub 成员    | 创建时采用配置副本；来源版本用于追溯；全局更新不自动覆盖              | 沿用 V0.4                                              |
| 普通／专家团模式 | 能力选择规则不同；正式工作都遵循计划与人工出口规则                    | V0.4 新增设计，尚未实现                                |
| Graph／计划      | 本次工作范围、分工、依赖和放行条件；模板只供参考与复用                | 沿用                                                   |
| Task／Thread     | Task 表达工作及完成条件；Thread 承载连续交流，可跨阶段复用            | 沿用；不能把一轮结束当成业务完成                       |

| 人的参与         | Agent 主导／人机共创，与自动／用户放行分别定义                        | 沿用 V0.3；不退回早期三种工作方式版本                  |

创建配置不是执行授权；讨论不是计划批准；看成果不是验收；专业审核通过不是用户阶段放行。这四个边界应在产品文字与真实命令中一致。

## 5. 当前协作原型基线与未决议题

用户先选择优化协作过程，经过 V0.5、V0.6 两轮草案，在 V0.7 明确将状态与操作分离，并确认合并到本评审稿。本轮 V0.8 再补充协调者配置、横向阶段与放行计数；以下三层为整合后的目标，已有模拟交互保留用于继续评审。

| 层次               | 内容                                                         | 边界                                                                               |
| ------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Graph 状态看板     | 输入框上方展示工作名称、整体状态、已放行阶段数和横向阶段路径 | 无业务执行按钮；允许收起和选择阶段，详情在侧栏按需查看；不塞入专家内部 Plan 步骤   |
| 按时间排列的消息流 | 范围确认、专家提问、审核进展、版本成果、修改意见与执行回执   | 在对应消息卡中操作；已处理卡保留原内容与回执，移除旧执行按钮，历史成果仍按版本查看 |
| 专业线程           | 保留原讨论、修改记录与线程入口                               | Hub 负责协调，详细协作继续在原线程；不另造专家内部 Plan                            |

看板独立于消息滚动区，业务状态更新不自动展开。用户可主动收起或查看阶段详情，阶段始终横向排列，窄屏在图内滚动。正式产品需适配用户字号和宿主布局，不固定沿用 V0.7 的 96px。读者停在底部时跟随新增内容，向上阅读后保持位置；「查看最新消息」属于消息区导航。

以下保留原复核议题，并标明当前处理情况。全部尚未进入正式产品。

| 议题类别   | 问题                                                      | 当前处理与待确认事项                                                                                                                |
| ---------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| A 先定规则 | 计划批准、审核通过、用户放行、任务完成容易混用            | 保留现有 Task 状态源；明确何种出口需用户、批准哪版、允许做什么。待用户放行时不以完成勾号代表整个组合阶段完成                        |
| A 先定规则 | 专家团模式的无匹配回退及固定背景来源尚未对齐              | 专家缺失时提示能力缺口与调整入口；项目来源首版只读，关联资料另行管理。明确旧 Hub 不自动切换行为                                     |
| A 先定场景 | 一个 Hub 可承载多份计划，但原型只有单一全局工作状态       | 补「两项工作并行，其中一项待回复」场景。建议只增加紧凑的当前工作选择与待处理数量，不新增管理驾驶舱；具体形态待确认                  |
| B 协作过程 | 等待输入会自动改变 Hub 输入框收件人，用户不易继续问协调员 | 当前稿保留 V0.5 的默认发给 Hub；点击回复后显式显示对象和工作，可取消定向；各自草稿保留                                              |
| B 协作过程 | 返工复用「目标用户待回答」；暂停隐藏已完成成果和线程      | 分别呈现「正在修订」「等待必要补充」「审核中」；暂停是当前进度上的标记，保留各阶段状态、成果和已有线程                              |
| B 协作过程 | 卡片过高，当前行动被压到首屏之外                          | V0.7 将只读阶段路径移至输入框上方；操作随消息出现，历史消息保留。取消 V0.6 在状态卡内展开节点并操作的设计；读者离开底部后不强制吸附 |
| B 协作过程 | 新候选 v3 与审核 v1 未明确绑定                            | 审核摘要直接说明「审核对象：需求方案 v3」；用户决定固定同一版本，历史批准可查                                                       |
| C 创建配置 | 名称、用途、任务目标之间容易混淆                          | Hub 名称使用长期空间示例；用途是可选服务方向，具体任务在进入后表达；普通／专家团给一句能力差异说明                                  |
| C 创建配置 | 原型全局设置与当前导航、列表和字体不同                    | 继承当前壳、字号和保存保护；只增加团队标签与必要控件，不照搬演示外壳、固定字号或演示按钮                                            |
| C 失败状态 | 原型以成功路径为主                                        | 补创建失败保留草稿、专家不可用、旧版确认、成果缺失、并发修改、断线重连；这些须有后端事实，不使用按钮伪造成功                        |

B 类协作布局已合入当前原型；后续继续细化 A 类规则与 C 类创建、异常场景。Graph 看板应从已有任务与协作事实派生，不新增一套独立业务状态机。

分阶段验收场景：普通讨论不启动整套计划；单节点委托可确认；人机共创能定向回复与切回 Hub；审核后停在用户出口；退回后继续修订而非无故等用户；暂停不抹掉历史；只批准方案阶段时不能进入开发。两份计划的回复与批准不串线留待下一轮，不声称当前 V0.8 已覆盖多计划。
