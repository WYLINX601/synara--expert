# Hub 交互设计与开发对接 V0.4

日期：2026-10-22  
状态：可点击交互原型 + 产品增量设计；未修改仓库、未连接真实 Agent。  
仓库基线：`WYLINX601/synara--expert`，`main@93c751172091495c3b26991b92624cd6571a92fb`。

## 1. 本轮结论

保留一个「新建 Hub」入口，在同一弹窗内选择「普通」或「专家团」。设置里的现有「专家」页面增加「单个专家 / 专家团」两个标签，不增加一级专家团中心。

「专家团」标签管理可复用配置。「Hub 设置 → 参与专家」管理当前工作空间的成员副本。创建 Hub 可以使用预设，也可以临时选择专家，不必先保存预设。

这修订 V0.3 中「所有 Hub 都等同于专家团」和「MVP 不提供独立团队配置」的结论。其余计划确认、专业线程、人机共创、版本交接和阶段放行原则继续沿用。

**Hub 是工作空间；专家团是可复用配置；专家团模式的 Hub 是配置的一次使用；Graph 是本次工作的执行计划。**

增加专家团配置页的理由是复用成员与协作方法，不是因为双模式必然要求另一套管理系统。

## 2. 原型怎么使用

打开 `Hub_交互原型_V0.4.html`。文件不依赖外部脚本、图片、字体或网络。可下载到电脑后用浏览器打开。

顶部「01 创建 Hub」「02 专家团设置」「03 协作过程」是演示导航。底部用于切换模拟的运行事件，不属于正式产品。正式执行者不会通过这些按钮伪造状态。

建议按以下路线体验：

```text
设置 → 专家 → 专家团
    ├─ 新建 / 编辑 / 复制 / 归档专家团
    └─ 使用配置创建 Hub
             ↓
新建 Hub：普通 / 专家团
    ├─ 普通：名称，可选工作方向与项目背景
    └─ 专家团：选择预设或临时选人，可调整当前成员
             ↓
创建成功：空白工作空间，不启动工作线程
             ↓
发送明确工作需求 → 计划卡 → 用户确认
             ↓
需求共创 → 技术审核 → 等待用户放行 → 本地开发 → 成果
```

示例专家、工作内容和成果均为演示数据。输入框支持普通输入与 Ctrl/Cmd + Enter。编辑专家团支持 Ctrl/Cmd + S。弹窗支持 Esc 关闭。

原型中的专家团配置尝试保存到当前浏览器的 localStorage；不可用时仅保留在内存。示例 Hub 与运行状态不持久化。浏览器对于本地文件存储的处理可能不同。

## 3. 两种模式的边界

| 项目 | 普通模式 | 专家团模式 |
|---|---|---|
| 专业角色来源 | Hub 默认配置；需要委托时使用普通工作线程 | 从当前 Hub 已选 Expert 中选择，并按既有机制绑定配置 |
| 进入门槛 | 不要求选专家 | 至少一位专家；不强制凑齐多人 |
| Hub 的主要行为 | 通用讨论、规划和协调 | 协调、专业路由、规划和汇总 |
| 找不到合适专家 | 不涉及固定专家名单的匹配 | 暴露能力缺口；不静默降级为普通线程 |
| 模板与 Graph | 按工作复杂度使用，不由模式关闭 | 按工作复杂度使用，专家团可提供模板偏好 |
| 正式工作授权 | 遵守相同确认、权限和人工出口规则 | 遵守相同确认、权限和人工出口规则 |

普通模式不是关闭多线程或关闭审批。专家团模式也不是每次必须让所有专家参与。两者的主要差异是能力选择规则，不是两套运行时。

Coordinator 保持固定协调职责。团队用途帮助其理解服务方向，成员能力摘要用于路由；不把各 Expert 的完整 Persona、Skill、MCP 配置合并成一个万能角色。Coordinator 不作为必选成员，不另外配置「队长」。

当前核对的 `GroupSettingsDialog` 中，`mode` 表示 `onboarding / edit`，不是这两种协作模式。`GroupExpertsSection` 支持选人，并明确存在普通线程回退。本轮双模式及团队预设是新增设计，不能据已有字段宣称已实现。[R1][R2]

## 4. 页面与交互规格

### S01 新建 Hub

入口：现有 Hubs 侧栏的「新建 Hub」。从专家团配置点击「创建 Hub」复用同一弹窗，不新增第二套创建流程。

形态：居中的单页弹窗，约 540 px 宽。超出视口时内部滚动，操作区保持可见。不做多步向导，不展示完整设置导航。

| 控件 | 默认与参数 | 行为 |
|---|---|---|
| 模式分段选择 | `collaborationMode`，普通为默认 | 明确点击专家团配置进入时，预选专家团模式；切换时保留草稿 |
| 名称 | 必填，建议上限 80 字符，最终对齐已有校验常量 | 空值不提交；不要求唯一名称 |
| 专家团选择 | 仅专家团模式显示；已保存配置列表 + 临时选择专家 | 选择只填充当前草稿，不启动任务、不获取额外权限 |
| 成员摘要 | 展示成员名，不展开 Persona / Skill / MCP | 「调整成员」在同一弹窗展开成员选择器 |
| 用途 / 工作方向 | 可选；预设可预填，用户可改 | 是长期服务方向，不是本次任务目标 |
| 项目背景 | 可选，引用既有可访问项目 | 全局新建默认不关联；只有显式从项目创建时预选该项目 |
| 创建 Hub | 唯一主操作 | 校验、保存、进入空状态；不创建或启动正式任务 |

不把来源项目、目录、记忆或凭证写入专家团配置。临时选人不要求「另存为专家团」才能创建。不存在或无权限的 Expert 引用需报错；工具离线可保留配置，但执行前必须检查。

界面可见参数和系统必需参数分开。技术 ID、requestId、revision、运行环境默认值由现有系统补齐。创建请求去重；失败保留草稿；关闭弹窗不启动后台工作。

### S02 设置 → 专家 → 专家团

形态：现有专家设置内增加标签页。沿用列表 → 编辑器模式，不新增一级导航。设置搜索应能定位「专家团」，深链接可采用 `section=experts&tab=teams`，以现有路由实际形式为准。

默认列表显示名称、用途、成员摘要。名称点击进入编辑。每行提供「创建 Hub」；复制和归档为次要操作。规模增大后沿用搜索，不增加复杂筛选器或统计看板。

新建/空状态只要求名称和成员。没有预设时仍可以在新建 Hub 中临时选人。列表展示的样例不等于用户已经安装这些专家。

归档只影响后续选择，不终止使用过该配置的 Hub。MVP 先提供归档，不做删除正在运行的团队实例。原型的「恢复示例」是演示工具，不是正式产品归档恢复设计。

### S03 专家团编辑器

| 字段 | 是否必填 | 保存内容 |
|---|---|---|
| 名称 | 是 | 配置的显示名 |
| 用途 | 否 | 一句话服务方向 |
| 成员 | 是，至少 1 位 | Expert ID 引用，不复制专家定义 |
| 协作模板偏好 | 否，位于可折叠区域 | 可优先参考的模板引用；不固化本次任务 Graph |

不加入项目绑定、共享记忆、文件路径、成员独立模型、工具凭证或 Coordinator 的完整人设。

专家自己的角色、技能、资料和工具仍由已有 `ExpertEditor` 管理。团队编辑器只管理组合关系。[R3]

保存采用显式操作。返回或切换页面前，对未保存编辑提供保留/放弃选项。保存成功增加配置 revision。并发修改需显示冲突，不静默覆盖。

### S04 Hub 主界面

保留既有应用 Rail、Hubs 侧栏、Coordinator 主对话、专业线程及成果入口。普通和专家团使用同一外壳，不新增工作流主页面。[R4]

顶部只显示当前 Hub、模式、已关联项目与常用入口。未设置项目不展示占位项。模式标签表达能力组织方式，不暗示任务已经启动。

创建后的空状态只显示名称、必要成员摘要和输入框。最多两个示例请求；点击只填入输入框，由用户发送。没有任务时不显示空 Graph、空进度条或虚构 Worker。

专业讨论可以先发生，并路由到相关 Expert，不要求先批准完整执行流程。默认留在 Hub，不自动切换到 Expert Thread。只有用户主动点击才进入专业线程。

### S05 工作卡：从计划确认到完成

仓库已有 `HubWorkItemCard`，可复用其标题、展开、Expert 身份、进度和线程入口的呈现方式。但它是工作项级卡片，不是已实现的计划 Graph 卡；不能把它的 completed 直接当成业务计划验收完成。[R5]

本轮新增计划级卡片，引用既有工作项和任务状态。一个计划只有一个逻辑卡片对象，其展示随状态更新，不为每次工具调用新增一条大卡片。

| 状态 | 首屏信息 | 主操作 | 次要操作 |
|---|---|---|---|
| 待确认 | 目标/范围、顶层阶段、负责人、人工出口 | 确认执行 | 调整计划、查看详情 |
| 执行中 | 当前阶段与负责人 | 可无 | 进入对应线程、暂停 |
| 缺少必要输入 | 谁在等待、需要什么 | 去回答 | 继续浏览其他工作 |
| 等待人工放行 | 固定成果版本、审核结论、放行后的动作 | 确认并进入开发 / 确认完成 | 退回修改 |
| 阻塞 | 原因、受影响范围 | 针对原因处理 | 调整计划 |
| 已完成 | 正式成果、约定内执行结果 | 查看成果 | 查看历史 |

简单顺序用阶段列表；并行任务在同一阶段分组；作者—审核者作为组合阶段，默认收起。展开仅查看内部工作，不暴露拖拽连线工具。

用户批准方案之前，组合阶段对下游仍未放行。显示「审核通过」只表示专业审核结论；不能显示为整个阶段已完成并自行开发。

待确认按钮必须绑定计划版本、目标节点/阶段、候选成果版本、实际用户身份和 requestId。重复点击不得重复执行；旧卡片不得批准新成果。卡片只是命令入口，不维护第二份可写业务状态。

### S06 专业线程

点击明确的「进入线程」「去回答」进入原 Thread。首次未派发的线程不伪装成已经存在；下游尚未满足依赖时不提前创建可执行 Worker。

顶部增加紧凑的工作关联栏：来自哪个计划、当前阶段、返回 Hub。继续复用该线程历史，不复制一份 Hub 专业对话。输入框可以标出当前回复对象，以免用户把补充发给错误对象。

提供信息、进行取舍与阶段放行是不同动作。Graph 只接收必要输入/阻塞/结果提交/正式变更事件，不为每轮讨论建立审批节点。

### S07 阶段成果与人工放行

查看成果复用 Hub 成果库或已有文件预览。原型以右侧单个检查面板表示，不自动打开，不并列堆叠多个抽屉。

审核通过后，主卡展示成果版本和下一步。查看文件不等于批准；进入线程不等于批准；未回复不等于批准。

「退回修改」在卡内展开意见输入，提交后续用作者原线程。新成果重新审核并重新确认。已批准的旧版本保持记录，不覆盖为新版本也已批准。

只授权方案阶段时，主操作是「确认并完成」，不是「进入开发」。需要新增开发范围时形成新版计划。

### S08 当前 Hub 设置

沿用 `GroupSettingsDialog` 的常规 / 参与专家 / 记忆 / 环境 / 插件分区，不额外增加与全局专家团配置完全重复的页面。[R1]

「参与专家」展示本 Hub 的成员副本和来源配置版本，并允许另存为专家团。当前 Hub 的修改不回写全局预设。普通模式里此分区提供「启用专家团」，不展示一份未被使用的固定成员列表。

整体切换协作模式：MVP 仅在没有未结束的正式执行计划时允许。存在运行或等待中的计划，应先完成/取消，避免隐式改派。普通对话不应因此被禁止。

成员变更主要影响后续规划与派发。移出名单不等于终止已批准的工作，原线程与成果保留。撤销实际权限则按权限机制立即限制，不能借快照继续越权。

修改来源项目或长期工作方向不能默默更换运行中任务的输入。影响当前计划时，走既有的变更分析与重确认流程。

## 5. 配置复用：副本，不是持续绑定

```text
ExpertDefinition ──引用──> 专家团配置 v1
                                  │ 使用
                                  ▼
                  Hub：成员 / 用途 / 模板偏好副本
                    │               │
                    │               └─ sourceTeamRef = 配置ID + v1（仅追溯）
                    ▼
                本次计划 vN ──用户确认──> 执行
```

专家团配置更新到 v2，不更新已有 Hub 的成员、用途、Context、任务或批准记录。MVP 不做「自动跟随最新版」，也不做一键强制更新所有 Hub。

明确复制字段：名称草稿、用途、Expert ID 引用、模板偏好。明确不复制：项目背景、文件/目录、共享记忆、历史对话、成果、凭证、执行授权和运行中计划。

Hub 实例不需要保存第二份重复 Team JSON。使用预设时，将成员与用途写入已有 `expertIds`、`goal` 等有效配置；新增 `sourceTeamRef` 仅记录来源。团队成员引用和实际 Thread 的 Expert 快照是不同层次。

## 6. 最小数据与产品契约

以下是新增信息的语义，不是现有接口签名。正式实现优先复用当前服务、持久化与版本控制方式。

```ts
// 建议新增：可复用配置，不承载运行状态。
type ExpertTeamDefinition = {
  id: string;
  revision: number;
  name: string;
  purpose?: string;
  expertIds: string[];
  workflowTemplateRefs?: Array<{ id: string; revision?: number }>;
  archived: boolean;
};

// 对已有 Hub 配置做小幅扩展，避免和创建/编辑界面的 mode 混用。
type HubCollaborationExtension = {
  collaborationMode: 'standard' | 'expert_team';
  sourceTeamRef?: { id: string; revision: number };
  workflowTemplateRefs?: Array<{ id: string; revision?: number }>;
};
```

已有 Hub 的名称、用途、成员、来源项目继续保存在既有字段。旧 Hub 未显式设置新模式时，优先保留原行为，不根据成员是否为空自动改变已授权任务。迁移与首次显式启用需在技术方案中定义。

| 产品动作 | 必要语义 | 关键限制 |
|---|---|---|
| 列出专家团 | 查询、归档过滤 | 不额外加载所有专家完整 Persona |
| 保存专家团 | 定义字段、预期 revision | 冲突不能静默覆盖；引用存在性校验 |
| 使用专家团新建 Hub | 模式、当前草稿、来源 id/revision、requestId | 形成当前配置副本，不授予执行权限 |
| 更新 Hub 成员 | Hub ID、原 revision、成员变更 | 不自动回写预设，不隐式改派运行中工作 |
| 提交计划确认 | 计划 ID/revision、范围、身份、requestId | UI 隐藏状态不是授权检查 |
| 提交阶段决定 | 阶段、版本、通过/退回、意见、身份 | 与工具调用审批分开，重放安全 |

新增专家团标签只扩展 `experts` 模块，避免另起平行管理客户端和权限体系。原型没有实现这些后端契约。

## 7. 与当前仓库的对应关系

| 已核对组件 | 可复用内容 | 本轮工作 |
|---|---|---|
| `SidebarGroupsSurface.tsx` | 新建 Hub、Coordinator 与子线程导航、设置入口 | 创建前先收集双模式草稿；保持现有入口 |
| `GroupSettingsDialog.tsx` | 创建/编辑模式、分区设置、专家加载、保存与退出处理 | 创建首屏做轻量封装；运行实例继续使用原分区 |
| `GroupExpertsSection.tsx` | 专家搜索、成员勾选、归档/不可用提示 | 抽出可复用成员选择部件，供创建和预设编辑使用 |
| `GroupGeneralSection.tsx` | Hub 名称、Goal、Space、并发和模型配置 | 创建时只展示必要字段；高级项留在现有设置 |
| `ExpertsSettingsPanel.tsx`、`ExpertList.tsx`、`ExpertEditor.tsx` | 列表/编辑器、显式保存、归档、版本冲突与离开保护 | 同级加入专家团列表/编辑视图，不改造个人 Expert 的能力字段 |
| `workbench/registry.ts`、`settingsNavigation.ts` | 现有专家模块注册、导航与搜索 | 保留一级 Experts 入口，增加团队子标签搜索及路由 |
| `HubWorkItemCard.tsx` | 工作项、Expert 名称、展开进度和线程入口 | 新增计划级容器；复用内部呈现，但不混淆状态语义 |
| `HubPendingApprovals.tsx` | 已有待处理入口，可进一步评估复用 | 需区分工具权限审批和 Graph 阶段放行，不据文件名认定已有后者 |
| `ProjectAgentConfig` | `goal`、`expertIds`、`sourceProjectId` 等配置基础 | 复用已有字段，只补新模式/预设来源/偏好引用 |

代码核对不等于端到端验证。尤其是创建事务、配置 revision、普通线程回退、实际授权入口和兼容迁移，仍需实现前沿调用链核查。

## 8. 本轮不做

不新增一级团队中心，不做团队市场，不强制创建预设，不让用户配置队长，不复制 Skill/MCP，不新增共享记忆副本，不做拖拽 Graph 编辑器，不自动切换页面，不实时热更新所有 Hub，不把 Agent 消息当用户审批。
