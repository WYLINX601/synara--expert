1. 本版范围与来源

本稿整合 V0.3 的运行约束、V0.4 的可复用专家团配置、本地 V0.7 已确认的状态与消息分离，以及「Hub产品定位讨论」新增的协调者配置、横向 Graph 与简洁呈现要求。当前整合版本统一为 V0.8；引用对话中的 V0.5 与本地 V0.5 是两条不同的迭代记录，不互相覆盖。

来源：Hub产品定位讨论，本轮读取了最新讨论文本。该对话生成的 PRD、HTML、ZIP 附件尚未取得，不把回复摘要当作附件全文，也不沿用其“48 项检查通过”的声明。本轮验证另记。

议题 本版采用 替代／保留
专家团 可复用的用途、成员、协调方式和协作偏好配置 替代 V0.3 的“不设独立 Team 配置”；不增加独立运行中心
协调者 固定基础职责＋一个可选“角色与协调方式”字段 修正“固定职责意味着无需配置”；不新增队长 Expert
Graph 输入框上方横向阶段，可收起、检查详情 保留 V0.7 的状态与操作分离；不采用把执行按钮放回进度面板的建议
进度 已放行的顶层阶段数／当前版本内顶层阶段总数 替代把作者、审核者、人工确认分别计数；不展示推算工作量百分比
消息流 按时间保留关键提交、用户待办、决定与回执 不因每次运行进度变化追加一张完整计划卡
信息密度 状态由图标、节点、短标签表达，详情按需查看 不再用段落重复同一状态；必要范围和批准后果不可省略

本稿是产品目标与可点击模拟的说明。源码事实沿用主评审稿记录的固定 HEAD，不声称新增能力已存在于运行产品；本轮不改正式应用、不提交或发布。

2. 产品对象与职责

对象 负责什么 边界
Hub 持续工作空间、讨论、当前配置与多份工作 创建不等于执行授权；不是一次性任务
专家团预设 复用成员、用途、协调方式和协作模板偏好 不包含对话、记忆、项目资料、凭证或批准
Expert 专业角色、技能、资料、工具与产出要求 继续复用现有专家配置，不在团队表单重复填写
Coordinator 规划、路由、上下文交接、跟进、汇总与异常协调 专业判断交给对应专家；协调方式不能覆盖权限和人工出口
Graph／协作计划 本次范围、分工、依赖、输入引用、放行条件和版本 原子节点关联原有 Task；不是单线程 Plan 步骤列表
Task／Thread Task 记录业务工作；Thread 承载连续讨论和执行 回合结束不等于业务完成，同一线程可有多个历史任务关联
Context 共享信息与约束、必要输入及来源 不能替代 Graph 的可校验依赖和权限

Graph 与 Plan 使用相近的紧凑视觉语言，但不共享完成语义。Agent 内部 Plan 步骤的完成或清空，不能放行 Graph 阶段。

3. 创建、专家团与当前 Hub 设置

保留一个“新建 Hub”入口。普通模式不要求专家成员；专家团模式选择已有预设或临时选择专家。名称必填，用途和背景按需补充；创建时不要求配置完整 Graph、协调者 Prompt、模型或并发。

“设置 → 专家”保留“单个专家／专家团”标签。专家团编辑器顺序为名称、用途、协调者、成员、协作偏好；用途表示“做什么”，协调方式表示“怎样组织专家”。未填协调方式不阻止保存和使用。

当前 Hub 设置继续使用已有分区，允许修改自己的成员及协调方式。采用预设后形成配置副本并保留来源 ID 与版本；修改预设不影响既有 Hub，修改 Hub 不回写预设。“另存为专家团”创建新配置，不能顺带复制授权或对话。

项目背景遵循当前仓库的固定来源契约。原 V0.4 中更换来源的展示不作为已成立的产品能力；新增关联资料与更换 Context 来源须分开设计。

创建失败应保留草稿；保存时校验成员引用与版本冲突。专家不可用可以保留配置，但执行前必须提示缺口；专家团模式不静默退回普通线程。普通模式采用当前可用的普通线程机制，不伪造专家审核。

4. 协调者：一个可选字段

字段建议名为 coordinatorInstructions?: string。这是目标契约命名，未写入正式仓库 Schema。

层次 配置与执行规则
基础职责 内置规划、路由、交接、跟进和异常处理；编辑器只显示一句简要提示
角色与协调方式 可选文本；默认折叠，摘要为“默认协调方式”或“已自定义”；空白按默认处理
恢复默认 清空草稿中的自定义内容，保存后生效；取消编辑不改变已保存配置
作用域 仅指导 Coordinator，不覆盖专家 persona，不整段灌入所有专家 Context
共享约定 所有成员必须理解的共同背景进入共享 Context，通过引用供任务读取
硬性约束 必须先审核、必须用户确认等约束进入 Graph／权限校验，不能只写在协调方式里

示例：产品交付负责人。问题未清楚时先组织澄清，形成候选后组织评审；遇到分歧汇总依据和影响，不代替用户改变目标。

不增加独立头像、性格、知识库、技能、MCP、角色名和风格等多组字段；模型与执行设置继续留在现有高级设置。

配置依次经历“预设版本 → Hub 副本 → 运行快照”。新计划确认时固定本次协调方式与配置版本。运行中保存 Hub 配置只影响后续计划；不得静默替换当前快照或重排当前计划。若确需改变当前协作，提出显式计划修订，说明影响并确认受影响范围。旧预设缺字段时使用内置默认，无需批量重写历史数据。

5. 三层界面与消息连续性

层次 默认信息 可进行的交互
Graph 看板 输入框上方显示名称、当前状态、已放行数及横向阶段 展开／收起、选择阶段查看详情；这些均为查看行为
阶段详情 谁在做、依赖谁、当前输入／成果版本、审核分支、返工关系、等待原因 查看证据和进入线程；确认、退回、暂停等执行命令仍在消息卡
主对话消息流 计划提议、关键成果提交、必要问题、用户决定及回执 确认范围、定向回复、看成果、放行、退回、暂停／恢复

看板只读是指不改变业务执行状态，并非禁止折叠或查看详情。没有正式计划时隐藏；草案可预览，明确标“待确认”；确认后持续保留。进入专业线程仍保留当前工作关联，返回恢复先前阅读位置。

普通输入默认发给 Hub。点击“在此回复”才显示明确对象和工作；取消定向保留各自草稿。讨论、回答和浏览成果均不算授权。

仅在计划提议、需要用户处理、关键阶段交接、显著异常、暂停恢复及最终交付时形成消息卡；周期性进度和同一审核分支的普通更新只更新状态。旧卡保留原内容、版本与处理回执，关闭过时执行按钮，历史成果仍能按固定版本查看。

停在底部时跟随新增消息；用户向上阅读后保持位置，状态更新不重新吸附。折叠、详情和窗口变化不应抢焦点；“查看最新消息”属于消息区导航。消息区仍有足够空间露出当前操作；不把原型的固定像素高度当成正式布局规范。

6. 横向 Graph 与放行计数

阶段从左向右排列，窄窗口在 Graph 内部横向滚动，不转为蛇形、不挤出页面。收起时保留一行摘要。阶段默认展示名称、状态与必要的人工出口标记，不重复姓名和长说明。

标准示例为“需求澄清 → 方案与审核 → 开发与验证”。只批准方案范围时共两个阶段，没有未授权的开发节点。人工确认是“方案与审核”的出口，不独立算一个专家任务或阶段。

场景 已放行 当前阶段呈现
计划草案／等待目标用户补充 0/3 待确认计划／需求澄清待回复
澄清结束，正在产出或审核方案 1/3 方案与审核进行中
专业审核通过，用户尚未决定 1/3 方案与审核待你确认
用户退回候选成果 1/3 方案与审核修订中；新版本需重新审核
用户批准指定方案版本，开发开始 2/3 开发与验证进行中
开发满足该计划的出口条件 3/3 全部阶段已放行
只批准方案范围，用户确认成果 2/2 本次工作完成，无开发

“已放行”包括满足自动出口条件的系统放行与有效用户批准，并不表示每个阶段都需要人工点击。分母仅计当前已接受计划的顶层阶段，不计内部作者、审核者、执行尝试或审批按钮。草案数量需标明尚未执行；待确认修订不能混入正在执行版本的分母。

阶段是否已放行，由当前有效版本下的任务结果、审核结论与出口决定派生。计数不是单调增加的百分比：若显式修订使已放行结果失效，应说明范围与原因，保留旧记录并重算受影响阶段。

关系 默认呈现 详情／推进要求
顺序 左到右阶段与方向 前置有效放行且输入可用后启动
并行汇合 同一阶段标明并行审核 详情列出各分支状态；所有必要分支通过后才等待用户放行
产出—审核 一个“方案与审核”阶段 作者、审核者、候选版本、轮次；反馈回到作者，不建双向前置依赖
人工出口 阶段内“待你确认” 消息卡展示具体版本和后果，确认才释放出口
受阻／暂停 短状态标签与图标 详情说明原因、影响；保留已放行阶段，不退回到未开始

不提供拖拽编排、自由节点类型、任意循环或每条边的审批编辑器。并行分支必须来自真实计划，不能为了视觉丰富临时画出未配置的专家。

7. 计划确认、版本与调整

提出需求后先讨论；需要正式交付时形成草案。确认卡只呈现目标、范围、分工关系、人工出口和本次额外约束；已有 Expert 配置与背景不重复抄写。用户可以自然语言调整，不要求手动连线。

确认绑定计划 ID／revision、允许执行的范围和真实用户身份。服务端成功返回后才显示已授权；“保存／导出计划”、普通回复、协调员转述均不能替代授权。

重大变化包括目标、范围、专家、关键依赖、必要出口、权限或预算变化。运行中分别显示“执行中 v1”和“待确认修订 v2”及差异；受影响部分暂缓，未受影响且仍被授权的分支可继续。新修订确认前不得用新图替换运行事实。

本地原型重点演示执行前调整与候选成果退回；运行中计划修订、多份并行计划切换尚未完整模拟，不能据此承诺已支持。

8. 成果、审核与人工出口

作者提交固定成果引用；审核必须指向该候选 revision／摘要。审核返回通过、需修改或明确阻塞；审核者完成工作但结论为需修改时，组合阶段不能放行。

用户卡片呈现候选版本、审核结论、关键风险及批准后具体动作，采用“确认并进入开发”或“确认并完成”，不用含糊的“继续”。退回需提供修改意见，回到原作者线程；新版本必须重新审核和确认，旧批准不能复用。

放行记录至少关联 scopeId、planRevision、候选成果引用集合／outputDigest、decision、requestId；服务端补充真实用户及时间。退回附 comment。放行前与实际派发前均重新验证版本、范围、权限和必要输入，过期卡片不得放行新版。

每个出口确认前解析为 auto 或 user。示例原型中需求澄清与开发验证采用自动出口（结果模拟），方案出口采用用户确认；正式工作可要求最终成果也由用户确认，此时必须停在最终人工出口，不能因运行回合结束而显示全部放行。

9. 状态来源与运行约束

复用原有 Task 业务事实、工作运行记录、版本成果与 Thread。Graph 原子节点关联 Task ID，依赖只有一份可写来源；组合阶段状态可缓存，但必须能从当前轮次、子任务和放行记录重算。

派生展示 需要的事实
未开始／待前置 未授权，或必要前置尚未有效放行
排队中 已满足执行条件且真实入队，不等于正在运行
进行中／审核中 对应任务确实执行；审核角色运行不等于待用户审批
等你回复 存在本轮必要输入请求，关联对象明确
待你确认 候选与必要审核均有效，人工出口尚未放行
受阻／失败 原因与影响范围明确；不统一显示加载动画
已暂停 暂停事实覆盖当前进度；停止未完成时显示正在停止
已放行／已完成 当前有效版本满足出口规则；不是 Provider completed

派发须同时满足有效授权、未暂停取消、所有必要前置放行、固定输入可访问、无待处理失效／修订、专家和线程权限满足、无冲突执行及资源条件。

并行汇合默认 all。产出—审核反馈通过受限轮次和新尝试执行，不构造循环前置依赖；自动返工需有上限，超限请求用户处理，不由 Agent 重置额度。线程优先续用；审核与作者线程分开，单线程同时只接受一个受编排活动工作。

Coordinator 配置、Graph、任务、消息卡和摘要均读取同一运行事实；不让模型文字计划、Agent Todo 与前端各维护一套进度。

10. Context、暂停与恢复

执行时由系统装配本次 brief、Expert 快照、Coordinator 专用配置、共享 Context、原始用户要求、固定前序成果与反馈。按角色隔离所需信息，专业任务不自动接收 Coordinator 私有组织指令。必要输入必须实际加载或可读取；索引存在不代表已读，缺失和冲突须显示。

输入版本在启动时固定，恢复不重新查询“最新”。任务只提交新成果和新增结论／阻塞，系统负责关联 ID、版本、身份与授权。工具权限不能被角色文本或 Context 覆盖。

暂停停止新派发并请求中断可中断工作，保留已完成事实、草稿、线程和成果；无法立即停止的外部动作如实反馈。恢复前核验真实执行状态、输入和有效授权。取消不等于暂停，不提供沿用旧授权的无条件续跑。

持久化计划版本、配置快照、尝试、输入、结果、放行和暂停记录。重复结果、审批与迟到回报必须去重并关联原尝试；旧尝试仅进历史，不能覆盖新版。不能把单个 requestId 当作所有外部副作用 exactly-once 的保证。

11. 目标数据契约与能力衔接

以下是开发前必须落实的产品契约，不是本次新增 API。

所有者 最小信息／职责
专家团配置 ID、revision、名称、用途、expertIds、可选 coordinatorInstructions、协作偏好、归档状态
当前 Hub 配置 成员及协调方式副本、Hub 配置版本、来源预设 ID／revision；不回写预设
计划／运行 objective、planRevision、授权范围、顶层阶段、Task 依赖、releasePolicy、配置快照、输入与成果引用
Task／Attempt 复用业务状态、当前尝试和对应 Thread；新增需求通过现有契约扩展
阶段出口与决定 当前候选、必要审核、放行记录、失效原因、幂等请求；由服务端校验
UI 投影 同一事实源派生摘要、Graph、详情和消息卡；前端不得单独批准或推算真实成功

原子计划建议至少有 objective、brief、expertId、dependsOnTaskIds、workMode（agent/co_create）及明确的出口策略；输入选择有歧义时才增加 inputBindings。配置快照格式、事件 Schema、并发控制和迁移方案待技术设计，不在独立原型中假装完成。

复用方向：现有任务、依赖、成果版本、专家编辑器保护、聊天与 Thread 入口。ProposedPlanCard、ComposerActiveTaskListCard 等组件在新增讨论中被提出作为候选；当前适配性仍需实际开发前核验，不直接把它们的复制／保存动作当作批准命令。完整源码差异与固定版本证据见主评审第 3、6 节。

正式实现仍在当前聊天父布局内，继承订阅、快捷键、滚动与生命周期；使用公共能力、已有组件和用户字号，不凭薄路由宣称隔离。
