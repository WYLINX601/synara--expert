# 工作台日常开发流程

## 目的与适用范围

本流程用于 Synara 工作台的日常功能、修复和维护，目标是让每次改动只经过与风险相称的检查，并保留足够的交付依据。

按实际受影响的代码和运行路径选择检查。目录、包名或文件名本身不决定测试范围；跨包、生命周期、持久化和平台边界的影响才决定是否升级检查。

流程分为开发、集成、交付三个阶段。开发中做短反馈；集成时集中跑代码检查和相关测试；冻结候选后再做昂贵的真实运行、打包和安装验收。

首次接入和官方上游升级，仍使用对应的完整验收要求。准备安装包时复用有效的代码检查结果，增加产物验收；普通页面或业务逻辑改动不重复执行首次改造矩阵。

本文件补充日常开发的检查选择，不改现有 `workbench:sync` 工具、候选 SHA / runtime 绑定规则或 CI 正式门禁；也不增加 `--fast` 等绕过开关。执行工具命令前，先确认当前 checkout 的 `package.json` 确实提供该入口。

## 任务执行 SOP（v1.1，2026-10-16 起执行）

来源：用户确认执行二开 v1.1 并要求优化项目 context、落地仓库规范。本节和下方检查矩阵共同构成日常执行入口；架构规则仅在[架构标准](./workbench-adaptation-plan.md#current-standard-v11)维护，上游升级转入[升级 SOP](./workbench-implementation-plan.md#sync-sop)。

| 步骤              | 执行动作                                                                                                                                    | 退出条件                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1. 选入口         | 从 [context](../context/PROJECT_CONTEXT.md#execution-entry) 选择当前任务的设计和验收材料，核对 Git 分支、HEAD、未提交差异、工具链及已有失败 | 目标、现有用户改动与本次范围可区分；有恢复依据   |
| 2. 定需求与接口   | 明确场景、完成条件、数据所有者、复用能力、模块依赖及宿主接入点；新模块填写架构标准中的轻量说明                                              | 产品行为、父布局、权限和失败行为已明确           |
| 3. 确认必要设计   | 核心流程、信息架构或重要视觉方向变化先确认方案/原型；明确需求的小改、局部 UI 修复可直接实现并预览                                           | 达到本次已有的设计确认要求，不重复索取已获授权   |
| 4. 实现与聚焦验证 | 按下方开发阶段工作，使用隔离 home/端口；优先模块内修改，同步契约、接入清单和受影响测试                                                      | 核心场景及必要失败路径通过，形成可审查 diff      |
| 5. 集成           | 主会话审查完整 diff，按矩阵取检查并集，集中执行最终检查                                                                                     | 结果对应实际源码；失败、未运行及原因明确         |
| 6. 交付与回写     | 冻结输入，完成适用运行/产物验收，使用本文摘要模板；按下方文档回写规则更新                                                                   | 开发完成、合入、真实运行、安装与发布状态分别记录 |

功能开发通常使用 `codex/feature-*`；已有任务分支可以复用。桌面应用承载日用工作，开发与复现在独立预览 worktree 进行，按下方两角色流程验收后更新应用。dirty 工作区先保存并区分现有改动，不为满足分支形式或环境分工搬走、覆盖用户工作。上游同步统一在隔离候选执行。

## 桌面应用日用与独立预览流程

来源与状态：2026-10-24，用户确认改为“桌面应用日用＋独立预览”，并要求更新规范与配置。桌面应用是唯一日用数据主源；预览按问题复制必要现场，承担复现、开发与验收，测试数据不回写日用。此处是已确认的流程要求，现场复制与批注自动关联等能力须另有实现及验收证据，不能由本节推定已实现。两种角色不改变 Synara Stable/Beta 的身份、数据隔离或发布规则。

历史决定：2026-10-23 的浏览器日用双环境方式，以及 2026-10-24 此前的“浏览器日用、预览、应用版”三角色及“日用→应用”首次迁移／增量导入方向，均已被本次用户确认取代。原浏览器日用仅保留为历史回退入口；原目录、备份与演练记录仍保留，见[环境历史记录](./browser-environments-2026-10-24.md)。后续不要求维护三套真实工作数据，也不把浏览器日用向应用增量导入作为默认开发前提。

### 环境分工与首次配置

| 项目 | 桌面应用（日用）                                     | 独立预览（复现与开发）                                          |
| ---- | ---------------------------------------------------- | --------------------------------------------------------------- |
| 代码 | 运行已验收固定提交构建的应用，记录实际安装产物       | 从应用实际提交和依赖基线开始，使用独立 worktree，记录后续 diff  |
| 数据 | 真实聊天、专家、配置与日常工作的唯一主源             | 独立数据 home，按当前问题复制一致性现场；不自动同步、不回写日用 |
| 运行 | 使用日用应用身份、数据目录和进程                     | 使用隔离进程、数据目录及未占用端口；桌面预览还需独立应用身份    |
| 职责 | 完成真实工作、提出问题、在应用内浏览器查看和批注预览 | 复现问题、修改源码、聚焦测试与效果验证，向应用交付代码          |

预览基线对应应用正在运行的实际版本，而非仅凭当前 `main`、分支名或版本号推断。记录完整源码 SHA、锁文件、工具链与依赖输入，以及应用产物与源码的对应证据；不能确定时标为待核对。保留既有开发成果，区分它们与应用基线、当前任务的差异，不为对齐基线重置用户工作。

worktree 只隔离代码；预览的数据目录、进程、端口和验证写入的工作区还需分别隔离。独立浏览器预览可通过 `SYNARA_MANAGED_WORKSPACE_ROOT` 指定新建 Chat 的管理目录，Studio 与 Groups 位于其下；该配置不改变 OS home 或 Provider 凭据目录。将新建管理文件放入预览私有 home 可纳入该环境的备份。已有线程和手选 Project 的绝对目录不会自动改写；复制后先盘点外部引用，写入验证使用隔离副本，这不是文件系统沙箱。

首次配置先盘点应用版本、worktree、运行实例、分支和未提交改动，复用合适环境，不丢弃已有成果。按实际启动方式核对参数；开发模式先检查 dev runner 的 dry-run，并检查 IPv4/IPv6 监听及认证配置。记录应用与预览各自的代码／产物、数据目录、工作区路径、访问入口和启动／停止方式，禁止两个后端同时打开同一数据库。

### 按问题复制一致性现场

1. **固定问题来源**：在应用日用中记录问题及发生版本，保存相关 Project、Hub、线程、消息等稳定标识与来源对应关系。快照需保持数据库一致性，并包含复现所需的配置、附件、成果文件及其固定 `ownerThreadId/path/revision`；不能仅复制文本、名称或“最新”成果引用。
2. **补足文件与界面证据**：按问题复制必要工作区文件，注明源路径与副本路径；记录相关界面、状态和复现步骤。home 外的文件和符号链接目标不由数据库备份自动覆盖，缺失内容、脱敏或与原现场不一致的部分要明确标记。共同 web 问题保留浏览器界面证据；桌面专属问题保留独立桌面预览的证据。
3. **显式单向刷新**：现场只从应用复制到预览，按问题和来源快照显式刷新，不持续自动同步。刷新前保存预览未提交代码与需要保留的测试数据，列明覆盖范围和差异；不得覆盖应用主源，也不把预览的任务、消息、配置或测试成果回写为日用数据。
4. **重新建立执行边界**：导入任务、未完成工作和自动化默认暂停，进程、运行租约及权限审批不继承为预览的执行授权。测试需要继续执行时，仍经过预览当前的权限校验与审批；Provider 凭据与全局目录的共享不等于获得调用授权。复制、暂停与恢复须记录实际结果，不能用本流程文字替代实现和验证。

### 从实际使用到应用更新

1. **发现与记录**：在桌面应用中完成真实任务、记录问题并发起改进任务，保留问题对应的版本、数据现场与必要运行信息。重要流程或视觉变化仍按既有设计确认规则执行。
2. **复现与开发**：以应用准确源码及依赖基线准备独立预览，按上述规则复制必要现场，让 Agent 在预览 worktree 修改代码。记录基线与修改差异；缺少原现场时说明限制，不把当前副本当作完整复现。
3. **批注与验收**：通过应用内浏览器查看预览并批注，将问题、预览版本及验收结果对应记录。共同 web 问题在浏览器预览中验收；桌面窗口、原生集成、身份或生命周期等桌面专属问题使用独立桌面预览，不共享日用进程或数据库。按本文检查矩阵完成适用检查，审查完整 diff 并固定受检提交；预览可用或有批注不等于验收通过。现场复制与批注自动关联尚须单独实现和验收，未具备时显式记录对应关系。
4. **集成与构建**：通过 main 合入条件后，按任务授权合入 `main`，从固定提交及依赖输入构建应用产物；若合并结果、依赖或打包输入变化，补齐受影响检查。交付应用前核对身份、数据目录和本次变更关键路径，不让日用应用跟随预览热更新。
5. **备份与切换**：保存日用工作，等待相关任务结束或明确停止，取得一致性备份并保留旧产物和恢复位置。由外部终端或独立维护入口切换并重启应用；依赖待重启应用后端的 Agent 先完成交接，不能承担自身的最终切换。保留外部 Codex 或终端维护入口。
6. **核验与恢复**：确认运行的是目标提交的应用产物并继续使用原日用数据，核对项目、线程、附件、固定成果版本与本次变更经过的关键路径，记录实际结果和失败。涉及数据结构或持久化变化时，更新前在一致性备份副本上验证迁移和恢复；回退使用兼容的代码／数据组合，不能仅退代码读取不兼容的新库。测试副本不覆盖日用数据库。

“最新日用应用”指最近验证通过并实际完成切换的产物。合入、构建、安装、切换、推送与发布按对应任务授权和实际结果分别记录；确认本流程不自动执行这些操作。官方上游升级继续执行升级 SOP，不因采用两角色流程缩减验收要求。

## 三阶段流程

### 阶段一：开发

1. 明确目标、受影响路径和完成条件；检查当前分支、工作区改动与基线，避免把无关改动带入任务。
2. 对 UI、server 或 desktop 开发，按仓库说明使用隔离的数据目录与未占用端口。先看 dev runner 的 dry-run；不得为了让测试通过而重置日用数据库或复用生产数据。
3. 实现一个可审查的变更。开发过程中只运行受影响的测试或快速检查；修复缺陷时优先复用能稳定重现问题的现有测试。
4. 对纯文案、格式调整或没有可验证行为变化的小修，不机械新增测试。改动会影响流式文本、自动跟随或滚动测量时，使用聚焦的 browser 测试覆盖对应行为。
5. 失败时先看首个失败项与日志，区分代码问题、测试运行器错误、环境问题和既有失败。运行器返回 error、退出码非零或结果不完整均记为失败。

### 阶段二：集成

1. 功能完成后，按下方矩阵选定最终检查集合；一次性跑格式、lint、类型检查和受影响的 Vitest，避免每个小改动都重复全仓库检查。
2. 若改动实际跨越多个包、公共生命周期或恢复流程，增加完整 `bun run test`。跨包只按真实调用与数据影响判断，不能仅凭改动位于 `contracts` 等目录决定。
3. 若需要多个工作区或子 agent，先划清文件归属、验收范围和依赖。任务边界确定后再并行执行；最终格式、lint、类型和集成检查由主会话集中完成。
4. 检查失败先修复代码或 CI 配置，再重跑失败项与受影响项。只有输入完全相同且证据仍有效时，才复用已通过结果。
5. 集成结果记录到一份简短验收摘要；只有失败、环境阻塞或需要复核时，才附详细日志或专项证据链接。

### main 合入条件与保护

- 必需检查通过、变更可审查、证据对应待合入源码后，才报告可合入。日常开发可保留已知失败的记录，但不能把该记录当成完整验收通过；必需门禁失败时继续修复，正式上游升级不得静默跳过。
- 仓库能力和对应操作授权允许时，main 使用 PR、必需 CI 状态检查及限制强推/删除的保护。检查名按实际 CI 核对；个人维护可记录人工审核结果，不要求自己审批自己的 PR，也不默认额外审查人数。
- 自动保护未启用时，人工核对同一套门禁和待合入 SHA，保存审核记录；这只是手动执行，不声称已有远端强制保护。最新只读状态见 [WB-05 核对](../workbench/WB-05-automation.md#2026-10-16-remote-read-only-audit)。配置仓库规则、触发 workflow、推送、安装与发布不由文档修改自动执行。

### 阶段三：交付

1. 冻结候选源码和依赖输入，记录完整 Git SHA、锁文件与工具链基线；最终代码检查必须对应准备交付的 tree。存在未提交改动时另记 diff，不能用 HEAD 冒充实际受检内容。
2. 按矩阵执行候选验收。只对本次改动覆盖的 Provider、MCP、桌面身份、数据库迁移或上游路径做真实运行验证。
3. 只有桌面启动/身份行为变化或本次要交付安装产物时才构建对应包。产物交付还要启动产物并核对应用身份与数据目录；构建成功本身不代表启动验收通过。
4. 确认所有必需检查均通过，失败和未运行项均有说明。发布、签名、生产操作以及 Provider/model 选择沿用已有授权与发布流程。
5. 交付报告只保留结论、版本与 tree、变更范围、检查结果、未验证范围和下一步。需要追查时再链接原始日志，不复制大段重复证据。

## 按实际影响选择检查

记号：

- **C**：代码最终检查：`bun run fmt:check`、`bun run lint`、`bun run typecheck` 和受影响的 Vitest。
- **B**：完整 workspace 测试 `bun run test`。
- **P**：与流式、滚动或交互时序直接相关的聚焦 browser 测试。
- **M**：迁移 lineage 检查及受影响的迁移、恢复测试。
- **W**：平台/进程边界专项检查 `windows-runtime:check`。
- **R**：改动所经运行路径的隔离真实运行，如 Provider、取消/恢复或 MCP。
- **D**：桌面目标的启动/身份检查；仅在身份/启动改变或交付安装包时执行。
- **Q**：文档链接、命令有效性和规范一致性检查。

纯文档变更做 Q，不触发无关应用构建或测试。任何代码改动在交付前做 C；下表额外列出受影响范围要求。

| 改动类型                               | 最低检查                         | 专项验证与范围                                                                   |
| -------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------- |
| 文档                                   | Q                                | 检查新改链接、命令与规则；不构建应用                                             |
| 单包 UI / 业务                         | C                                | 验证改动页面；流式、滚动或交互时序变化加 P，不默认运行真实模型和全仓库测试       |
| contracts 或跨包                       | C；实际跨包或生命周期改动加 B    | 覆盖调用方与契约消费者；按实际影响增加专项                                       |
| Provider / session / 取消 / 恢复 / MCP | C；生命周期改动加 B              | 真实运行链路改动加 R，覆盖受影响的 Provider 和路径                               |
| 迁移 / 持久化                          | C + 受影响数据测试；迁移改动加 M | 数据转换验证备份、失败重试和恢复；跨包或生命周期改动加 B                         |
| Desktop 启动 / 身份 / 平台             | C；平台/进程边界加 W             | 启动或身份变化加 D；只改界面时不默认打包                                         |
| 上游集成                               | C + B，执行现有正式候选门禁      | 固定 base/target SHA；按差异加 M / W，保留原生与专家真实运行、恢复及产物验收要求 |
| 准备安装包                             | 最终候选适用的代码检查 + D       | 复用输入一致的代码检查；构建并启动对应目标包；运行或数据变更按以上类型叠加检查   |

混合改动取各类要求的并集；同一项检查只跑一次。C 的命令从根目录执行。Web 聚焦测试使用根命令 `bun run test:web:focused`，测试路径相对 `apps/web`；其他包的测试命令以当前包 `package.json` 为准，不假定通用参数形式。

平台/进程边界变化运行 `bun run windows-runtime:check`；迁移改动运行 `bun run migrations:check` 并覆盖相应恢复路径。跨包或生命周期改动运行 `bun run test`，不可用 `bun test` 替代仓库 runner。

真实模型、真实 MCP 或 Provider 只用于验证本次修改经过的运行路径；mock/夹具通过不等同于真实运行通过。未改动的 Provider 不因交付动作而重复实测。

新增或改变功能模块的宿主接入、导入依赖或保留例外时，增加 `bun run workbench:check-boundaries`，核对[接入点清单](../workbench/integration-points.json)与扫描范围；新目录不在现有扫描范围时需同步纳入或明确其宿主装配职责。边界规则变更增加其相关 Vitest 与非法导入反例。该静态检查不代替权限或生命周期实测。

2026-10-16 起，清单声明的功能文件必须参与扫描，接入与回归路径必须存在；保留依赖按精确文件和 import 说明职责、原因与测试，不使用目录整体豁免。Context 功能复用宿主 `contextClient`，Space 辅助函数接收实际所需的命令能力。迁移归属由 `migrations:check` 审计：旧 111 的身份和内容被冻结；v1.0.5 候选经精确 schema 核验及统一备份后审计接管到 Context 独立 ledger，活动原生 catalog 归官方，新增原生迁移须可追溯到固定上游，新 Linx 扩展进入独立 ledger；缺少来源依据时先补证，不新增豁免。正式升级增加第七项边界门禁，历史六项结果保留原范围。实现与实际检查见[架构对齐验收](./workbench-adaptation-acceptance.md#alignment-implementation-20261016)，基线核对按[升级 SOP](./workbench-implementation-plan.md#sync-sop)执行。

上游集成需要锁定稳定版本与完整目标 SHA，在隔离候选中处理并验证差异。继续执行现有候选门禁、SHA/runtime 绑定、原生与专家实际运行要求；不以本流程缩减上游验收。

## 失败后重跑与证据复用

- 失败后先定位原因，不为隐藏失败而降低阈值或增加 skip，也不把超时、运行器错误或不完整输出记成通过。测试本身错误时可有依据地修正，并重跑相关用例。
- 通过证据仅在源码 tree、锁文件、工具链、依赖和执行配置均相同的情况下直接复用；日志保留它对应的源 SHA。
- 源码变化会使受影响证据失效。未受影响的证据可用于说明差异和风险，但必须注明它对应的 SHA 与变更，不能改写为新 SHA 的通过结果。
- 日常开发中的测试代码或运行器改动后，重跑被改变的测试与依赖它的门禁，不机械重跑真实模型或打包。正式同步工具要求精确 SHA 绑定时仍按其规则执行，不搬用旧记录绕过门禁。
- 先修代码与 CI，再冻结候选并执行昂贵验收。候选冻结后若产品、依赖、构建或打包输入发生变化，重建候选并重跑受影响的检查与验收。
- 失败日志按需保留链接；摘要明确失败项和错误原因，不需要为每一条通过结果复制完整日志或建立重复索引。

## 主会话与子 agent 分工

主会话负责范围判断、风险分类、检查矩阵、变更整合、最终门禁和文档同步。涉及发布、生产操作或 Provider/model 选择时，遵守对应授权边界。

只有目标、约束、文件范围和验收方式清楚后才委派执行。子 agent 负责有边界的实现、测试或证据收集，不替主会话决定产品行为、架构和验收门槛；跨文件改动应先约定文件归属，避免并发覆盖。

集成后由主会话检查 diff、核对子任务结果，并集中完成交付 tree 的最终检查。输入一致且完整的子任务检查可直接复用；主会话只补缺项和集成后受影响项，不重复执行同一检查。

## 验收摘要模板

```text
目标：
候选版本 / 完整源码 SHA / tree 或未提交 diff：
变更范围：
检查：通过 [项目]；失败 [项目与原因]；未运行 [项目与原因]
真实运行 / 产物验收： [验证路径和结果，或未运行原因]
遗留与下一步：
```

摘要只记录实际执行和实际结果。无法验证的项标为未运行或受阻，不写成推定通过。

## 文档与 context 回写 SOP

1. 架构或接口决定写入现有专项方案；检查与操作规则写入本文或升级 SOP；接入位置和依赖例外写入接入清单；实际结果写入对应验收记录。一项结论有一个权威位置。
2. 只有目标、入口、已确认决定、当前状态或下一步改变时才更新 context，保留简短摘要并链接权威材料；不复制日志、完整检查矩阵或旧候选的通过结果。
3. 每条新增的耐久决定标明来源、适用范围、确认状态和日期；历史证据保留原 SHA 与失败结果。发现日期较新但源码不匹配时标注范围，不刷新日期冒充重验。
4. 纯文档交付检查相对链接及锚点、路径、命令入口和 AGENTS/规范一致性；需要格式检查时只处理本次文档，不改用户已有文件。无需启动产品或重建应用。
