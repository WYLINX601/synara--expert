## 当前执行标准 v1.1（2026-10-16）

来源与状态：用户在完成《二次开发方案比较》的审核修订后，于 2026-10-16 明确要求执行 v1.1 并落地仓库规范与 SOP。本节是后续 Linx 二开的架构标准；下方 2026-10-08 设计与源码基线保留为历史实施记录，不作为当前源码或新功能已验收的证明。

采用 **Fork 持续维护 + 独立功能模块 + 薄路由入口 + 宿主适配层 + 每周上游升级候选**。沿用同仓库、同工具链和统一构建，按实际需求增量整理，不建设通用动态插件 SDK、微前端、第二套执行器或事件总线。

### 模块与数据所有权

Synara 宿主拥有认证、任务执行、Provider、事件投影、数据库连接和恢复生命周期；接入层负责页面/导航装配、窄客户端、依赖注入及兼容转换；功能模块实现业务规则、页面和测试。跨进程 schema 归 contracts，运行逻辑留在对应应用，共享运行工具使用 shared 的显式子路径。

新模块在现有需求或设计记录中说明以下内容，不要求另建 SDK 或每次新增文档：

```text
模块 ID / 职责与范围：
页面入口 / 真实父路由及布局 / 访问条件（无页面则注明）：
数据所有者 / 读写入口：
宿主依赖 / 对外能力 / 跨模块协作：
失败与不可用行为 / 接入点 / 验收场景：
```

跨模块使用明确的公共服务、契约或导出的业务能力，不读取另一模块内部状态。Home、Task 等复用宿主任务数据源、查询缓存及投影；模块只持有自己的业务状态，不复制任务执行状态。基础组件、纯工具和适用的查询能力直接复用；存量 Expert/MCP 只在消除真实耦合时整理，不因目录名称整体搬迁。

新增或变更宿主依赖时同步接入清单与扫描覆盖；例外精确到文件、specifier、原因和测试。现有 [边界检查](../scripts/check-workbench-boundary.ts)覆盖指定 features、server experts、命名的 Expert/MCP 与 Space/Context Web 界面，以及接入清单的 `featureFiles` / `featureRoots`；真实 CLI 要求清单存在、引用可访问、保留依赖与实现一致。新目录必须登记或纳入自动命名范围；该检查不是传递依赖分析或运行时安全隔离。

Expert 中心继续由现有 `_chat` 父路由和查询缓存承载。专家、专家团与技能共用无业务状态的 `SettingsEditorDialog`，沿用技能弹窗的响应式尺寸、关闭入口和初始焦点；列表留在背景，编辑内容内部滚动。专家与专家团复用 `SettingsSaveBar` 固定底部操作，未修改时保存禁用。草稿、保存、冲突检查、路由深链及离开保护仍由原编辑器拥有，关闭、Escape 与路由离开均经过原保护；保存期间拒绝关闭。显示版本号与持久修订分别处理，隐藏界面徽章不改变快照或并发检查。接入清单登记共享呈现组件，不新增宿主订阅或任务数据源。

Skill 绑定作者契约只管理身份、启用、范围与资源方式。Expert／Skill 编辑器不提供加载时机；宿主只交付目录和完整资源，正文由原生运行器按需读取或明确调用。只读固定记录保留必要的原历史字段以校验指纹，作者接口和新写入不使用它们；未决初始化保护仍覆盖原生 hooks／插件。

Context 页面、自动保存与旧指令迁移通过 `workbench/host/contextClient` 读取现有 `ContextApi` 和 capability，不再直接读取完整 native API 或旧指令 store。宿主保留“不支持”与“支持但连接不可用”的区别，返回原 API 对象，保持自动保存队列身份。Space 命令辅助函数只接收所需的 orchestration 方法；批量归属在传输结果不确定时仍保留 `getShellSnapshot` 校准能力。Space controller/路由同步、Context RPC/生命周期/投影/持久化继续作为明确登记的宿主接入。

连接状态与共享连接代次由现有宿主 transport 提供。重连开始即暂停依赖 Context 的写入，当前代次的实际读取成功后再恢复；多个观察者复用同一查询结果，旧代次的晚返回不能授权新连接。自动保存队列仍按原 API、数据实例和项目区分。相同项目或 Space 切换数据所有者时，未保存、已发送待回执及结果不确定的操作都属于受保护状态；保留旧草稿及离开保护，明确丢弃后才采纳新所有者。首次发送与迁移交互在异步步骤返回后再次核对当前连接及数据归属，不以开始时的闭包快照放行。

### Hub 协作模块接入（2026-10-22）

`hub.collaboration` 负责专家团预设、Hub 配置副本、计划修订、固定候选、审核与人工出口；宿主继续拥有 Goal、Task、Attempt、HubWork、Provider 会话、线程和成果版本。首期一个 Hub 同时一份活跃计划，确认后绑定一个原生 Goal；不新增执行器或绕过原生队列。

- 服务端业务位于 `apps/server/src/hubCollaboration`，通过 `workbench/host/hubPlanService`、`hubPlanExecution` 和窄 RPC 适配接入宿主。扩展仓储复用同一 SqlClient 事务，原子保存计划版本、原生任务绑定、事件、回执和 outbox；Expert ledger 追加 7、8、9 号迁移，已运行迁移不变；9 号持久化定向问题与答复授权。
- 前端位于 `apps/web/src/features/hubCollaboration`。专家团挂载既有 Experts 设置，当前副本挂载 GroupSettingsDialog；Graph 与消息卡嵌入原 ChatView / MessagesTimeline，继承原聊天布局、滚动、快捷键与订阅。Graph 只读，业务操作留在消息卡。它不是隔离聊天行为的新路由。
- `contracts/hubCollaboration.ts`、`hubPlan.ts` 持有跨进程契约；新增能力通过可选 capability 协商，旧服务缺失能力时不开放对应写操作。前端用宿主窄客户端读取快照和事件，以现有项目事件触发刷新并在可见时轮询兜底；不引入第二事件总线。
- 执行授权只来自 owner 计划命令。Agent 只能提案或提交自己当前尝试的专业证据；队列准入、实际启动、续跑和恢复共同检查计划绑定。确认时固定成员、协调方式及每个节点的显式 Provider/instance/model，运行中的配置编辑不改写该快照。
- Provider 回合结束与业务成果验收分开：已结束但没有有效成果的节点显示受阻，只有 owner 的显式重试可创建新 attempt；重试保留原 Work 的终态、固定模型及阶段代次，不重复已有有效成果的节点。固定成果引用使用 `workerThreadId`；`ownerThreadId` 只用于读取时定位来源。
- Worker 通过显式 `synara_hub_request_input` 提问，问题固定计划版本、阶段代次、节点、尝试与线程。owner 的 `respondInput` 原子记录答案及 outbox；续跑复用同一 Worker 的原生 follow-up 准入、容量预约、命令回执与实际 Provider 启动门禁，绑定完整输入及原运行设置。回答不批准权限、计划或成果；仍有原生审批／输入或活跃回合时等待，暂停保留、失效拒绝。已接受回执只修复历史送达记录，不新增执行授权。
- 续跑回合收尾优先使用原生消息与回合的准确关联。排队消息尚无 turnId 时，只能以现有 ProjectionTurns 的同线程、同回合、同 pendingMessageId 记录补足只读关联；未知或不匹配时保持预约，不凭时间接近推断。回合结束只释放对应占用；没有业务成果仍是未提交，不转成成功。固定成果校验解析真实作者 Worker 身份，不伪造 owner 或放宽成果接口授权。
- 受管理 Worker 的原生恢复继续使用 health ladder；step1 只允许同一持久 episode 的固定 nudge 引导原活动回合，step2 先完成旧回合停止，再通过与定向回复共享的原子容量预约派发固定任务。宿主实际启动门禁依据精确验证返回的恢复种类检查原生待办和活动回合，不以前缀授予权限；目标项目沿用冻结 Work 及当前 Hub 关联权限。不能确认首轮已接受／排队事实时，不另开自动补发通道。
- 计划停止先保护已有成果及需要显式重试的正常结束／失败尝试；其他未完成且已停止的 idle Work 通过既有取消路径解除调度阻塞。缺失线程不能报告停止完成；现有停止回调依赖宿主投影，不能据此宣称已验证所有 Provider 的实际进程清理。
- 默认输入仍给 Hub；显式选择问题后复用原生问题表单，普通输入框保持挂载并保留草稿和附件，自动队列发送暂缓。问题草稿经窄适配复用 `composerDraftStore`，以完整尝试身份隔离；在 Hub 内回复与进入原线程回答使用同一问题命令，不建立另一套消息路由。Graph 按当前问题投影等待回复／送达，原生 Work 状态保持真实值。
- T3 的 `planRevisionImpact` 只计算新旧定义及配置的影响闭包，以阶段共享候选为失效边界，再沿新旧依赖取下游。未受影响结果仅为 carry-forward 候选，不能自动沿用成果或审批；运行中修订、hold 与确认／撤销在接入完成并验收前仍不开放。
- Graph 默认使用原生输入区胶囊收起，展开后横向展示节点，详情按需复用 StageInspector。节点快照的原生任务、Work 与报告只读投影须核对当前修订、阶段代次和分配尝试；审核结果还绑定当前候选 ID 与摘要。Graph 不推断权限恢复、不直接重试；确认与计划操作定位既有消息卡，继续经过原命令校验，不另建执行状态或详情系统。
- 接入清单见 `workbench/integration-points.json` 的 `hub.collaboration`。边界检查覆盖声明目录的静态导入、深层接入与约定例外，不证明运行时权限隔离或真实 Provider 成功。实施状态与未验收范围见[Hub 评审记录](./hub-review-2026-10-22/README.md#implementation-status)。

### Expert Skill 主动进化接入（2026-10-29）

`expert.skill-evolution` 持有来源快照、提炼请求、候选与采用事件；正式 Skill、不可变包和绑定继续由技能库拥有。来源限定为同一专家已正常结束的明确回合，专家不新增 Memory。手动流程由用户点击提炼及认可摘要授权；自动流程遵循下节明确开启的学习授权，不要求逐项采用。

- 跨进程契约位于 `packages/contracts/src/skillEvolution.ts`。服务端业务在 `experts/evolution`；`workbench/host/skillEvolutionRpc` 保留 owner、原生命令和投影接入，`skillEvolutionPersistence` 使用宿主 SqlClient，Expert ledger 加法迁移为 10。请求先持久化再派发已有 Thread/turn 命令，不新增执行器或队列。
- 原生 Reactor 和 ProviderService 在构造时捕获持久登记能力，启动与发送共同核对 purpose、Provider 实例和模型。Pi/Claude/OMP 适配器提供无工具、无环境 Skill/Context/Hub Memory 的会话；Reactor 的受限派发允许名单和 ProviderService 保持相同三端范围；普通上下文校验继续有效。隔离任务不借普通恢复或原生 fork 放宽约束；取消沿用原生准确回合。未支持的 Provider 明确拒绝，不自动切换。
- 改进权限属于 ExpertSkillBinding.allowEvolution，缺省关闭；与启用、资源方式和原生工具权限独立。共享来源首次采用时派生完整专属副本并保留绑定全部字段，后续更新同一身份；原版重新绑定时复用已有副本。公开全局策略及范围配置已移除，归属仅由创建／派生记录并只读展示。派发、采用、恢复和持久化前重新校验权限，撤销阻止旧意图继续修改。采用沿用版本 CAS 和持久操作回执，保存与绑定分阶段恢复；事件在实际保存及绑定完成后记时。旧包保留进入既有生命周期锁和引用检查，恢复内容产生新修订，恢复原绑定保留副本。
- 两阶段共用原生受限执行链路：start 只发现经验机会，generate 通过准确父机会摘要和反馈生成文件草稿。子记录固定独立任务、模型、来源和生成轮次；不依赖跨记录事务，新轮次使旧草稿不可采用，忽略及权限撤销阻止后续写入。服务端仍只在正式采用时写技能库与绑定。
- 前端挂载原 `/experts/$expertId?tab=evolution`，继承 `_chat` 布局；通过 Expert 编辑器窄槽位复用来源任务、模型选择、Skill 详情和草稿保护。时间环每个 Skill 一个节点，候选不生成能力，未知基线不编造日期、调用量或分数。

接入清单见 `workbench/integration-points.json`。该检查只覆盖静态边界；实现、真实模型和未验收平台分别见[本轮验收](./expert-skill-evolution-acceptance-2026-10-29.md)。

### Expert 自动学习接入（2026-10-31）

自动学习扩展既有 `experts/evolution` 与同一正式资产服务。`ExpertLearningService` 仅协调当前任务证据、发现、逐点单结果生成与采用；宿主继续拥有原生 Thread/turn、账户、模型、事件消费、取消和恢复。第一阶段支持明确选择的 OMP/Pi，缺省关闭；不扫描历史会话、不增加 Memory 或评测执行器。

- `expertLearning` 契约与公开 RPC 仅提供读取／设置。可信自动调用身份由服务端登记，客户端不能声明 epoch 或自动采用权限。Expert ledger 的 11 `ExpertAutomaticLearning` 保存状态、证据和周期；12 `ExpertLearningEvidenceDelivery` 保存有界的当前回合证据交接记录，沿用宿主 SQL 连接，未重写旧迁移。
- RPC 与后台复用按真实 owner 隔离的 `SkillEvolutionService`。HTTP 宿主构造时启动并恢复，不依赖进化页。一个宿主同时推进一个自动周期；当前 Expert 的前台工作优先。派发前登记稳定身份，保存未绑定时重试同一意图，不生成新副本掩盖中断。
- 唯一持久 Provider 事件消费者在正常投影后、确认消费位置前，持久交接已脱敏且有界的当前回合片段；宿主作用域中的独立循环随后采集证据。证据存取失败保留待重试记录，不阻塞业务输出或其他线程；交接自身尚未持久接受时不确认业务位置。没有增加 Provider 事件订阅或模型执行器。
- 交接记录固定原 turn、Expert／快照、Project／Space、Provider 实例及最小已应用运行身份，成功后释放正文但保留去重和来源元数据；比较版本再清理，避免覆盖期间的新事件。重试重新核对归属与学习代次，不能把旧证据归给新位置或新 Run。实际 started／reroute 模型优先于启动模型，原始 effort 也随交接保留。消息和工具使用不同引用，缺失与截断保留覆盖说明；学习会话不再产生学习来源。生产依赖缺失不能静默禁用采集。
- 学习提交、开关和显式 Expert／Skill 修改共用短提交门，模型执行不持锁。关闭递增 epoch；原生启动、发送与正式写入重新校验；最终原生准入在同一短门内读取当前授权，接受后释放而不持锁等待模型生成，保留原 Effect 的取消与作用域。关闭回执后旧代次不能继续绑定。学习线程退出通用自动续跑，普通业务任务不受取消影响。
- 关闭时保存完整绑定与解析条目并保留包引用。新独立 Run 通过窄解析能力读取固定清单；已有 Run、审批和 continuation 优先原装配。共享源的后续修改不会推动关闭的 Expert；明确变更身份／范围或修改自身私有内容才协调对应固定项。只改启用、改进许可或资源方式保留固定来源。
- 自动采用保留 `allowEvolution` 既有约束，首次改进共享技能完整派生为 Expert 专属副本，后续复用同一身份。自动新建绑定显式允许后续学习。采用意图、包引用、修订检查和完整资源保留仍归原资产服务。
- 普通 OMP 仅在会话局部关闭原生 AutoLearn；受限提炼沿用固定 18.12.1 bundle、preload、空工具和固定提示词断言，不修改全局配置或换模型。Pi 沿用已有受限 Adapter。源会话的实际模型／账户配置传给后台，不自动降级。
- 设置和进化共用 owner/Expert 查询状态，等待回执后才表示关闭成功；失败重读仍不确定时保留不确定状态。进化页优先显示已保存并绑定的成长，手动提炼复用现有折叠区域；自动无变化／失败不产生待办。后台会话默认从普通侧栏隐藏，显式固定仍可查看；原草稿保护和编辑冲突继续有效。

实现范围和实际验收分别见[实施计划](../context/expert-autolearning-implementation-plan-2026-10-30.md)及[自动学习验收](./expert-autolearning-acceptance-2026-10-31.md)。静态边界、受控测试、真实 Provider 与平台验收分别记录，不能互相替代。

### Skill 文件交付与 OMP 提炼接缝（2026-10-29 候选）

## 4. 前端设计

### 4.1 设置页面与入口

扩展现有 `registry.ts` 作为自定义入口元数据的唯一来源，包含模块 ID、现有 page ID、标签、描述、图标、导航分组及可搜索说明。页面实现的惰性加载映射放在单独的 Web 装配文件，按 page ID 做穷尽类型校验；元数据不静态导入大页面或原生 store，避免导航与搜索加载整套专家页面及循环依赖。

原生 settings 路由只负责确定页面、提供窄上下文并挂载工作台页面宿主。专家 / MCP 页面内的布局、表单、校验、草稿与保存反馈由原组件负责。保留当前 `experts`、`mcp` 与旧连接/应用接入地址的归一化结果、tab、expertId、connectionId 和浏览器前进/后退行为；具体 URL 字段复用已有解析，不凭模块声明接受任意路由或代码。

所有入口消费同一元数据，不能分别在 registry、导航、搜索中手写三份模块信息。原生设置条目继续使用其现有来源。页面加载失败保留返回与重试入口，不丢弃未保存草稿；切换页面继续使用 `useExpertDraftGuard` 的保存、放弃、取消与关闭提示语义。

### 4.2 页面数据与导航接口

按实际调用从 `wsNativeApi` 和现有 settings 代码收拢所需能力，例如读取/保存专家、管理连接、发现/导入配置、打开指定专家或连接。方法直接复用现有 contracts 的输入与输出，不建立第二套同义 DTO。

页面通过窄客户端能力调用业务请求。`wsNativeApi` 已有集中映射，若使用已有类型的能力子集即可限制页面依赖，就不再增加转发文件。现有查询 key、revision 冲突、失效刷新与后台 refetch 行为继续使用已有查询体系；不能让宿主订阅另维护一份任务状态或覆盖 dirty draft。实时状态采用现有快照/订阅机制，保留断线重连、重放和最终状态校准。

本地接口随同一源码 tree 编译，首期通过类型检查和行为测试保证一致，不维护多套历史适配器。独立部署的前后端仍遵循现有协议兼容机制，不另设一个能掩盖线协议差异的模块版本号。

### 4.3 原生界面的扩展位置

只针对现有 `ExpertComposerPicker` 和 `ExpertTaskControl` 明确宿主传入的上下文：当前线程/草稿身份、已有专家绑定、允许的选择/控制操作及禁用原因。组件保留其现有实现，不复制 ChatView、输入框或任务状态 store。

如果实际检查显示提取挂载组件可以消除多个原生接入点的重复条件，则增加一个明确的、类型化的挂载入口；若现有组件已足够集中，仅登记接入点与测试，不再增加空包装。首期不提供任意位置插入节点、运行脚本或修改任意原生 props 的插件机制。

挂载入口不改变消息到达、自动跟随、流式文本或虚拟化测量行为。未绑定专家的原生任务沿用现有路径；已经绑定专家的任务，必需能力缺失必须呈现可诊断错误，不能因组件异常静默清除绑定或退化为通用助手。

### 4.4 视觉与可访问性

复用现有 Button、Dialog、输入控件、主题和披露动画，沿用 `text-ui*` / `text-chat*` 字体设置、键盘和 reduced-motion 行为。共享原生组件 API 如有真实变化，只为受影响的少数复合组件增加适配，不为每个按钮建立别名层。前端适配不承担新的视觉改版。

## 5. 服务端设计与深层接入

专家与 MCP 的业务处理从现有请求分支按职责收拢，依赖由 `createWorkbenchExpertRuntime` 及既有服务装配注入。原生 RPC 入口继续拥有 schema 校验、`requireOwner` 授权、请求准入、取消信号与错误映射；一次请求只有一个明确的执行路径。现有 `rpcEffect` 与 `expertRpcEffect` 各自负责的错误处理语义保持原样，不能在提取时无依据地统一。

保留已有 RPC 名、payload、响应和 revision / CAS 语义。现有 handler map 已按 `WS_METHODS` 静态登记，优先从中提取业务处理并沿用既有 dispatch；无需再加一套动态注册。不得新增接收任意字符串和任意参数的“调用插件”接口，不得仅靠 UI 隐藏实现授权。实现前核对 Effect 等现有服务依赖，不因提取文件引入第二套错误或运行容器。

连接检查继续显式触发并释放连接；工具调用继续由既有 Gateway 会话拥有，保留工具白名单、实时停用、凭据引用、取消与关闭。配置发现继续只读来源，导入继续使用已有冲突预览、引用保护和版本检查。适配层不改变 Provider/model 选择，也不把所有 Provider 的能力压成相同布尔值。

以下深层接入继续原位维护，列入升级检查：

| 接入               | 必须保持的行为                                | 首期策略                     |

| 任务创建与启动     | 提交前固定专家快照；必需资源/连接失败阻止启动 | 保留原有调用与顺序           |
| 恢复、fork/handoff | 按现有语义使用固定绑定及 runtime payload      | 保留既有 Provider 差异与测试 |
| 事件与投影         | 专家绑定随任务持久化、重放、查询和 hydration  | 不新增旁路状态或异步补写     |
| 迁移与恢复         | 统一 SQLite 所有权、事务、备份和恢复点        | 不搬表、列或迁移历史         |
| 凭据与进程         | 现有 secret store、共享平台与进程边界         | 不复制凭据/启动/清理实现     |

## 7. 实施顺序与每阶段退出条件

首期已执行 A0–A4，实际结果见验收记录。后续继续执行同一原则：先保存候选基线并核对既有失败，再修改接入。各阶段保持可审查的独立变更；每阶段完成后收掉被替代的旧路径，避免长期双重注册或双写。仅改目录而没有消除依赖/重复的工作不纳入首期。

| 阶段        | 工作                                                             | 退出条件                                                   |
| ----------- | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| A0 基线核对 | 保存候选实际 tree、源码/测试差异；核对现有复用项、失败与接入清单 | 能恢复实施前版本；清单覆盖本次模块与原生接入               |
| A1 设置入口 | 统一元数据与页面装配、导航、搜索、旧地址转换                     | 自定义页面实现不再静态嵌入原生设置文件；深链与草稿行为通过 |
| A2 请求接入 | 收拢窄客户端和服务端处理，保持 contracts 与认证入口              | 方法名/响应不变；授权、CAS、错误、取消与缓存语义通过       |
| A3 边界治理 | 扩大扫描范围、登记深层接入；整理有收益的原生 UI 挂载点           | 能阻止模块新增旁路依赖；暂留依赖有明确职责和测试           |
| A4 验证收益 | 受控宿主接口变化演练；最终检查；记录实际投入                     | 变化主要集中于对应宿主接入，模块行为与原生链路通过         |

A4 的演练在临时分支或工作区进行：模拟设置宿主渲染参数变化，或客户端/请求装配接口形状变化，通过宿主接入恢复兼容，验证专家和 MCP 页面/业务规则无需同步改写；模拟变化在交付前移除。演练只证明所选接口类型的隔离，不能当作真实官方升级成功。

暂不为任务内核提取通用生命周期接口。当后续官方升级出现重复适配，或新的独立模块需要同一能力时，另按行为与事务边界评估；不能为了统一命名把启动、恢复、授权、存储同时重写。

## 8. 验证、交付与回退

设计阶段已完成链接、命令、图示与格式核对。代码实施检查按下表执行，实际通过、失败与未运行项见实施验收记录。

| 代码实施范围            | 所需检查                                                                |
| ----------------------- | ----------------------------------------------------------------------- |
| 所有代码变更            | `bun run fmt:check`、`bun run lint`、`bun run typecheck`、受影响 Vitest |
| 设置与 UI 入口          | 聚焦 browser 验证；字体、深浅色、键盘、草稿离开、旧地址与前进/后退      |
| RPC / 跨包 / 生命周期   | 实际跨包或生命周期改动加 `bun run test`；覆盖所有消费者                 |
| 依赖边界                | 边界检查与反例测试；命令入口以实施 checkout 的 package scripts 为准     |
| 流式与布局时序          | 若经过相关路径，增加 transcript、自动跟随与测量相关 browser 测试        |
| Gateway / Provider 运行 | 路径变化时验证原生与专家的真实首轮、取消、恢复、MCP 调用和释放          |
| 平台或迁移的实际变化    | 分别增加 `windows-runtime:check` 或 `migrations:check` 与恢复验证       |
| 官方集成或安装包        | 继续正式候选门禁、固定 SHA/runtime 绑定、隔离运行和产物验收             |

Web 聚焦测试使用 `bun run test:web:focused`，browser 的实际命令按 Web package scripts 核对。使用 `bun run test`，不使用 `bun test`。集中执行最终检查，不以目录搬迁为理由机械重复真实模型或打包。

代码验收至少覆盖：原生无专家任务、保存与冲突、dirty 草稿、全局停用、工具白名单、来源导入冲突、旧任务快照、未授权请求、断线后的缓存/状态校准。先复用现有用例，只为新增边界和行为变化补有意义的测试。

隔离实例使用独立 home 和未占用端口，启动前检查 dev runner dry-run 及双栈监听；升级数据实验用一致性副本。首期不改变存储格式，代码回退仍需核对同期依赖和数据兼容；任何意外数据格式变化都应拆成独立迁移任务，不能用 Git 回退替代数据恢复。发布与生产安装沿用已有授权范围。

## 9. 风险、投入控制与收益评估

| 风险                            | 控制                                                   |
| ------------------------------- | ------------------------------------------------------ |
| 接口过大，把官方内部整体透传    | 仅暴露现有模块所需操作；新能力随真实需求加入           |
| 统一接口丢失 Provider 能力差异  | 保留支持条件、失败和不可用状态，不能静默降级           |
| 装配成为共同故障点              | 按页面/业务能力分开；保留错误来源和原生任务路径        |
| 新层改变时序或拖慢应用          | 不增加跨进程服务、全局队列或完整状态复制；按需加载页面 |
| UI 抽离丢失草稿、缓存和导航语义 | 复用现有 guard / queries，browser 回归覆盖真实路由     |
| 原生组件或深层数据模型仍变化    | 明确保留的接入与验收成本，不宣称任意版本兼容           |
| 抽象投入持续扩大                | 一项提取必须消除具体依赖或重复；无收益包装停止扩张     |

记录首期实际实现与验证投入，再在后续两到三次真实上游集成中记录：官方变更规模/类型、文本冲突文件、实际需语义适配的原生与业务模块文件、修复时间、验证时间和失败原因。同一变更产生的测试/文档文件单列，避免用改动文件总数冒充耦合程度。

判断收益时比较相似变化，并计入适配层维护和回归成本；测试数量、mock 演练或一次无冲突合并均不能证明成本下降。收益来自集中修改与减少重复，深层运行与数据验证仍需投入。尚无真实升级序列，本文不承诺固定工期、节省百分比或升级次数即可回本。

首期完成后，保留本方案、实际接入清单和一份简短验收摘要即可。是否进一步建设插件框架，由实际独立模块需求和升级记录决定。
