# Synara 代码与 Hub V0.8 技术方案审计报告

源码固定基线：`93c751172091495c3b26991b92624cd6571a92fb`。方案对象：用户提供的《Hub 专家团与协作 Graph 技术方案 V0.8》，日期 2026-10-22，文档自述为“技术评审提案，尚未实施”。本文的源码行号均指原始基线，修复后的行号会变化。

## 1. 审计结论

当前代码存在可以复现的数据一致性、异步状态和安全问题，建议在继续实现 managed 协作计划之前优先修复。最重要的发现是：任务行与依赖边可能部分提交；SQLite CAS 会误报冲突；暂停或归档可能在外部动作失败后返回成功；成果发布存在检查后读取的竞态；MCP 自动重定向会转发自定义凭据；两种 TOML 解析依赖可分别造成原型污染与同步死循环。

本次已形成完整源码修复候选、补丁和回归证据。修复范围包括持久化、Hub 生命周期、成果读取、MCP 客户端、技能包读取并发、前端请求隔离及 TOML 依赖。没有把 V0.8 新业务模块冒充成已实现功能。现有停止操作的持久补偿、其他依赖安全公告及真实 Provider 的停止与恢复仍是发布前需要处理的事项。

### 范围与证据强度

- 对仓库结构、契约、入口、依赖和规范进行扫描，重点深审 Hub / Goal / Task / HubWork、成果库、Expert / Skill / MCP、前端 Hook 与 V0.8 的相关接缝。仓库约 9,526 个跟踪文件，其中约 4,351 个 TS / TSX 文件；这不是对每个文件逐行审计的声明。
- 结论区分“应用路径已复现”“代码可直接确定”“版本命中但尚未验证可利用”和“未来方案需要澄清”。依赖公告数量不等于项目中可利用漏洞数量。
- 回归使用真实 SQLite、受控异步交错、临时目录、两个本地 HTTP 服务和真实 Chromium。Provider、远端 MCP 生产服务及真实用户数据库未用于测试。
- P1 表示应优先阻断发布的数据、凭据或核心运行风险；P2 表示重要的正确性、可用性或规模问题。这是本项目修复优先级，不替代公告的 CVSS 等级。

### F01–F03：持久化与并发

**CAS 误报不是普通版本冲突。** SQLite 的 `changes()` 表示同连接上最近已完成的 INSERT / UPDATE / DELETE 的变化数。在当前 UPDATE 的 RETURNING 表达式中，它不能作为当前行是否更新的可靠判据。本次用“上一条 DELETE 命中 0 行，随后以正确 revision 更新”的真实 SQLite 场景复现了误报。[SQLite 官方语义][sqlite-changes]

修复保留 `WHERE id = ? AND revision = ?`，每个实际修改行固定返回 1，由是否得到返回行判断 CAS。对同仓库其他 `RETURNING changes()` 的使用进行了区分：AutomationRepository 判断的是返回行数，不消费 `changed` 数字，不能仅按文本相同就判为同一 Bug。

**任务保存需要以一组事实为单位提交。** 原实现先 insert / update Task，再删除旧依赖、逐条插入新依赖。输入两个相同依赖 ID 时，第二条边触发唯一约束，但任务行、revision 或前一条边已经落库。新代码用 `sql.withTransaction` 包住完整保存，同时在服务入口拒绝重复 ID。事务不是依靠“调用方通常会包一层”的假设。

**行级 CAS 不保护整个 DAG。** A 和 B 分别读取旧图，同时提交 A→B 与 B→A；它们更新不同的行，因此两个 revision 条件都可成功。本次用受控异步交错和真实数据库复现。修复只对 `updateTask` 的图校验与提交使用已有项目锁，不对所有入口随意加锁，以避免内部事务再申请项目锁造成锁顺序反转。当前保证范围是同一服务实例；若未来多个进程共享写入数据库，需要把该并发协议升级为数据库层可强制的事务规则。

### F04–F07：生命周期、完整集合与状态机

暂停是两个动作：先阻止新的工作准入，再请求在途线程停止。原实现写入 pausedAt 后吞掉 interrupt 错误，并记录成功回执。同 requestId 再来时只能读到成功，无法补做停止。

本次让暂停、归档及取消归档的线程命令失败显式返回；未完成时不写成功回执；即便 Hub 控制字段已经改过，也会重查线程状态，补做尚未完成的动作。归档命令本身不是幂等操作，因此重试前还需跳过已到目标状态的 Coordinator、成员或被父线程级联改变的子线程。

该修复不把 `pausedAt` 解释为“Provider 已确认停止”。没有新增持久 outbox、pausing 状态或跨重启补偿。**`stopGoal` 内部的 interrupt 错误仍有吞掉路径，这是明确的剩余问题，详见第 4 节。**

停止和依赖解锁中的 `limit: 100` 属于业务完整性问题。停止分支应完整遍历当前 Goal 中未归档、已分配线程且非 done / cancelled 的任务；依赖解锁应检查所有未归档且为 planned / blocked 的直接后继。新增同时间戳分页场景，避免只用 createdAt 游标时跳过同一时刻创建的记录。

Goal 终态修复针对服务状态转换本身。旧代码只拒绝 stopped→active，先 pause 再 resume 可以绕过。此次拒绝 stopped 的所有非终态迁移。服务层测试包括 user 和 Coordinator principal；当前 Agent Gateway 并未暴露任意 Goal pause / resume 工具，因此不将它描述为已证实的远程 Agent 越权攻击。

### F08：成果读取竞态

原流程先 `realpath` 检查源路径位于工作区内，再 `stat`，最后按路径 `readFile`。能修改源文件或父目录的 Worker 或同权限进程若在检查后把文件或父目录换成符号链接，读取会跟随新目标。只比较读取前后的字节数无法拦住同尺寸替换。本次通过真实成果发布入口复现了文件替换和父目录替换两条路径。

新读取过程固定文件描述符，并比较 dev / ino / size / mtime / ctime；POSIX 使用 O_NOFOLLOW / O_NONBLOCK，读取最多为已验证大小加一个哨兵字节，读取后再次核对路径和文件身份，finally 关闭句柄。合法且稳定的工作区内符号链接仍可使用。读取字节上限和 finally 关闭句柄已做代码核验；本轮未单独编写文件持续增长和句柄关闭的故障注入测试。

这些测试证明修复阻断了已复现路径，不是对所有文件系统竞态的形式证明。Windows reparse point 和跨平台文件系统行为仍需专项测试。若安全边界要求抵御能够持续修改整个目录树的同 UID 恶意进程，应使用操作系统提供的目录句柄约束打开能力或更强的进程权限隔离，不能仅把多次路径检查当作沙箱。目标成果库写入路径还有检查后写入的结构，本次没有复现可利用链，因此列为后续核验项，不与已复现源读取漏洞混记。

### F09：MCP 重定向泄露

锁定的 `@modelcontextprotocol/sdk@1.29.0` 默认跟随重定向。测试中本地 MCP 服务返回 307 / 308 后，另一 origin 收到 `X-API-Key`；POST 还携带 initialize JSON-RPC 请求体。SSE GET 同样泄露自定义凭据。该行为与维护者的 [GHSA-6prh-2h8m-c8cw][mcp-advisory] 一致；不能据此泛称所有运行时都会跨站转发 Authorization，现代 fetch 对它有另外的处理。

修复放在 transport 的 fetch 注入点，覆盖 POST、GET 与其他请求。只写 `requestInit.redirect` 不够，因为该 SDK 的 SSE GET 没有使用该设置。回归包含 POST / SSE GET × 307 / 308 四种情况，修复后第二个服务收到 0 个请求。

兼容变化：该客户端拒绝所有自动跳转，包含同 origin 跳转；配置应填写最终 MCP endpoint。这里只针对实际使用路径加防护，没有声称消除了 SDK 的全部公告。后续仍应评估升级 SDK 至覆盖全部相关公告的版本。

### F10–F11：TOML 解析依赖

两项均通过真实应用入口核验，而非只比较包版本。

- `readMcpSourceEntries` 读取特制本地 / 导入 Codex 配置后，后续普通对象继承了注入的属性。导入结果过滤发生在 parse 之后，1 MiB 文件上限无法阻止短文本原型污染。[维护者公告][toml-pollution]
- `buildCodexTextGenerationConfig` 处理畸形数组注释文本后不返回，外部子进程超时才能终止。同步解析的死循环不能由普通 try/catch 或包裹 Promise 的超时恢复。[维护者公告][smol-dos]

入口要求受影响的本地文件或被用户导入的配置；本次没有证实未认证远程攻击或 RCE。针对这两种直接解析入口，修复选择 `toml@5.0.1` 与 `smol-toml@1.9.0`，也覆盖同一轮审计命中的递归、长整数、表数组和键解析复杂度公告，不只升到最早修复上述两个样例的版本。Effect 保留的旧传递依赖见第 4.2 节。[smol-toml 复杂度修复][smol-quadratic]

两包均无新增运行时子依赖。保留现有 parse / stringify 接口。toml 新版本默认拒绝超安全整数，避免旧行为中的静默舍入；应用没有启用 bigint 选项，因此不会主动引入 BigInt 到 JSON 摘要中。新增子进程回归避免漏洞复发时挂死测试运行器。

### F12：技能列表的资源消耗

包读取会读取并校验文件内容。单包上限可到 100 MiB，而原列表通过 Promise.all 同时读取所有历史包。单包上限不能限制整个列表调用的在途内存。回归用两个实际导入包观测并发：旧实现峰值 2，修复后峰值 1；篡改内容仍会返回 package_corrupt。

本次采用串行验证，降低峰值资源占用，代价是大列表的总耗时可能增加。没有做 RSS / OOM 压测，因此不报告虚构的内存降幅。后续可以设计有界并发或带完整性证明的清单索引；不建议为了速度长期缓存“曾经校验通过”的内容而忽略磁盘后续变化。

### F13–F16：前端异步一致性

旧 Hook 对列表加载、事件更新、项目切换和 mutation 分别使用不同守卫，造成多种竞态。修复以请求 scope 隔离生命周期；列表读取期间记录事件，在列表落地后重放，并对可用实体 revision 做保护。重连 snapshot 重新补读列表；任务读完所有页；切换与关闭会失效旧请求；busy 由当前 scope 内在途操作数决定。

任务分页不是显示偏好。ProjectPanel 使用 `agent.tasks` 构造 `taskByThreadId` 和成员线程集合，遗漏历史页会影响关联功能。[ProjectPanel.ts:175–183、266–270][panel]

新增 8 个回归在临时 React Hook 适配环境中验证了修复前全部失败、修复后全部通过；随后使用真实 Chromium 153.0.0 执行包含原有 3 个 DOM 场景的完整 Hook browser 文件，11 个测试通过。RPC 是测试替身，这不是实际 Provider / WebSocket 端到端验证。没有修改产品布局、可见文案或新增 UI 交互。

### F17：既有回归测试的同步条件

完整回归发现一个隔离测试在 `session.lastError` 为 null 时断言失败。生产路径先提交失败 activity，再经过线程与 Provider 查询，提交 session 错误；前一个 activity 可见并不保证后一个命令已经完成。[ProviderCommandReactor.ts:8065–8078、1630–1673][reactor]

独立原始 HEAD 配合原始 toml 3.0.0 / smol-toml 1.7.0，对同一用例出现一次通过、一次相同断言失败，确认原有测试的调度敏感同步缺口。此次仅在测试中用既有 waitFor 等待同一摘要条件，再执行原 expect；没有改变生产逻辑、默认 2 秒超时、后续重启或 replay 流程。修正后 live / restart 两个分支通过。同批另一个独立线程调度用例仍有超时，见第 4.4 节。

## 4. 尚未关闭的风险

### 4.1 stopGoal 的中断补偿仍需持久机制

虽然已修复超过 100 条任务的漏处理，`updateGoalStatus` 的停止分支仍会捕获并忽略线程中断命令的 dispatch 错误。Goal 写成 stopped 不能证明在途外部副作用已停止。[原始停止分支][service]

不能简单让每次 stopped 重试都中断当前 Coordinator：同一 Hub 可能已经启动新的 Goal，共享线程已承载新工作，旧停止请求会误伤它。可靠修复需要持久 operation / admission generation、目标 turn / attempt 绑定、稳定命令 ID 和重启后的对账。V0.8 已提出中断 outbox 与 pausing / cancelling，应把它当 T2 必须交付的能力。此次候选不新增 schema 以假装完成这套协议。

### 4.2 依赖公告仍未清零

### 6.3 T2 的最低验收门槛

- 同时批准 / 退回只能形成一个有效决定；同 requestId 同内容重放、不同内容冲突。
- 同一业务命令涉及的任务提交、依赖、授权版本、决定、事件和 outbox 在一个共享事务内提交；中途失败全部回滚，事务不跨网络调用。
- 批准与暂停并发时，最终 admission 以同一控制边界排序；已经发出的 Provider 命令按在途处理。
- 创建线程后落库失败，先按原 workItem / attempt / dispatchKey 对账，不换 ID 重新启动。
- 旧 candidate / generation 的结果只写历史；旧 UI 卡片不能批准新候选。
- 服务重启先恢复原生执行事实，再处理 outbox 与 hold，最后开放新派发。
- 真实 Provider 完整跑通一次作者→审核→人工放行→下游，并验证停止失败和重启；只用单元测试不能替代。

这些是对用户方案的评审建议，本次交付没有实现 Graph、新计划表、人工批准命令或 outbox。

同时提供 `synara-audit-fix.patch`。在基线提交的干净分支上先执行：

```bash
git apply --check /path/to/synara-audit-fix.patch
git apply /path/to/synara-audit-fix.patch
bun install --frozen-lockfile
bun run fmt:check
bun run lint
bun run typecheck
bun run test
```

浏览器回归使用仓库的 browser 测试配置，正常开发环境先安装匹配的 Chromium，再执行：

```bash
bun run --cwd apps/web test:browser:install
bun run --cwd apps/web test:browser src/components/chat/project/useProjectAgent.browser.tsx
```

上述重现建议采用仓库固定的 Bun 1.4.2 与 Node 24.13.1。本次验证使用 Bun 1.4.2；最终完整工作区测试和前端编译器补验固定使用 Node 24.13.1，较早的聚焦回归、Chromium 回归及部分静态检查使用 Node 24.19.0。各次运行结果见第 7 节，不能将它们合称为同一环境下的一次全绿运行。完整包内 `_audit/` 目录包含报告、补丁、修改清单、摘要和验证日志；具体采用与发布仍需处理第 4 节剩余项。此次没有向远程仓库推送、创建发布或修改用户生产实例。
