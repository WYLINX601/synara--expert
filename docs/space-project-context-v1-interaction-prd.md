# Synara Space / Project Context V1.1｜最小增量前端交互 PRD

版本：V1.1 · 当前交互基准  
日期：2026-10-13  
范围：沿用现有 Sidebar、Space、Project、Environment 与 Chat 控件，为 Space 和 Project 增加少量 Context 编辑与按需查看。

本文取代 [PRD v0.1](./prototypes/space-context-v1/history/prd-v0.1-2026-10-13.md) 作为当前交互基准。目标行为已经批准；[独立 React 原型](./prototypes/space-context-v1/README.md)用于呈现前端交互边界，不代表服务端持久化、Provider 注入或生产链路已经实现。当前验收结果与最新截图分别以[验收记录](./prototypes/space-context-v1/acceptance.md)和[视觉与交互 QA](./prototypes/space-context-v1/design-qa.md)为准；旧版材料与截图只作历史追溯，见[history](./prototypes/space-context-v1/history/README.md)。

## 1. 产品结构

Context 使用现有信息层级：Sidebar 中切换 Space；每个 Space 下展示普通 Project 列表；每个 Project 下展示现有 Threads。不得增加 Space 分区、树状 Space 节点或另一套项目导航。

| 对象    | 入口与行为                                                                                            |
| ------- | ----------------------------------------------------------------------------------------------------- |
| Space   | 复用现有 Space 编辑弹窗，在编辑现有 Space 时一并编辑名称、图标和 Space Context。                      |
| Project | 扩展聊天 Environment 面板中的原 Project instructions 区域；不新建 Project 配置页或独立 Context 中心。 |
| Thread  | 从现有 Chat 的「＋」菜单按需打开只读 Context 详情；不增加常驻入口条或状态栏。                         |

## 2. 字段与输入

| 归属    | 字段                 |                            上限 |
| ------- | -------------------- | ------------------------------: |
| Space   | 方向目标、共享指令   | 目标 4096 字符；指令 16384 字符 |
| Project | 项目目标、原项目指令 | 目标 4096 字符；指令 16384 字符 |

四字段保留用户原始文本，不自动生成、改写、归类、合并或截断。允许清空。输入框不能用 `maxLength` 静默截掉粘贴内容；超限时显示相关错误并暂停保存，直到内容有效。常态不显示字符计数。

前后端采用同一字符计数口径；正式契约确定前，原型以 JavaScript 字符串长度作为联调参考，不将演示实现直接升级为生产契约。

## 3. Space 编辑

在现有 Space 编辑弹窗中直接编辑名称、图标、目标和指令。四项属于同一个草稿与保存事务：一次提交包含当前四项；成功后关闭弹窗，失败时弹窗保持打开并保留全部草稿。保存期间锁定四个字段，避免提交内容与可见编辑不一致。

新建 Space 仍只填写名称和图标，Context 两字段为空；Void 仅保留原名称与图标设置，不出现 Context 字段。可选的 Context 编辑插槽只在编辑真实 Space 时显示。未使用新增控件的旧调用继续保持原有行为。

## 4. Project 编辑与自动保存

原 Environment 面板的 Project instructions 区按此顺序显示：

1. 所属 Space 的只读继承内容，默认折叠，标题为「继承自 {Space 名称}」。展开后仅显示 Space 目标与指令；不复制到 Project 字段，也不提供覆盖入口。没有所属 Space 时不构造虚假的继承层。
2. Project 目标。
3. 原 Project instructions 指令。

仅在用户请求操作时提供「复制到 notepad」一类手动复制入口；可在父层有未保存草稿时禁用复制。继承内容直接展示为只读字段。

Project 的目标和指令共享一个自动保存队列。每次编辑后等待 500ms 再提交；连续输入重新计时，队列只保留最新待提交草稿。同一 Project 的请求串行执行，以明确捕获的 `projectId` 和 revision 做条件保存；成功响应只能推进后续请求的 revision，不能用较旧响应覆盖较新的本地草稿。切换 Project 时，未完成请求仍绑定原 Project，不得写到新选中的对象。

保存失败或版本冲突时暂停自动队列并保留草稿。冲突需要展示最新已保存值与本地草稿，等待用户选择；不得静默覆盖或自动合并。保存结果不明确时先回读权威配置，再判断成功、失败或冲突；不得盲目重复写入。常态不显示计数或固定「已保存」提示，只在保存进行中、失败或冲突时显示必要状态。

离开 Project 编辑区时，先 flush 尚未提交的草稿并等待结果。成功后才继续离开；失败、冲突或结果仍不明确时保留草稿并沿用现有离开保护。选择放弃只能取消尚未提交的 debounce/队列和本地草稿；已经发送到服务端的写入不能伪装成已撤回，须按其真实结果回读和反馈。用户从 Project 打开所属 Space 编辑，不算离开 Project；两处草稿相互独立。

## 5. Chat 查看与发送

「＋」菜单按需提供「查看上下文」行；选中后关闭菜单并打开详情，焦点返回由父层入口管理。未提供入口回调时，加号菜单维持原有内容和顺序。

Chat 常态不显示 Context chip、层数、计数器、固定保存状态、配置更新横幅或 legacy Notes 横幅；不设置 Context 空页引导。配置更新、旧对话和历史模式说明只在用户打开的详情中展示。迁移异常只显示在相关 Project 编辑区或该 Project 新对话的首次发送位置，不扩散到无关 Project。

普通发送不弹配置草稿保护，也不强制 flush 自动保存队列。首次有效发送时由服务端使用当时实际已提交的配置绑定 Context；前端不把未提交草稿当执行上下文。首次绑定返回的服务端 snapshot 是权威结果。若编辑仍在 debounce、队列中或保存未确认，发送使用服务端实际已提交值。前置校验拒绝时不建立绑定。绑定完成后，源配置变化不替换该 Thread 的 snapshot。

Thread 详情展示其真实绑定快照；尚未绑定时，若展示配置预览，必须明确标为已保存配置的预览。旧对话继续沿用历史内容，不补入新 Context，也不清理原有 Thread Notes。Space 删除或 Project 更换所属 Space 后，既有 snapshot 仍可查看；未来新对话按新的归属处理，详情可说明绑定来源与当前归属不同。

快照读取失败时显示读取失败与重试入口，不用当前配置替代历史快照。会话未运行时可标为「上次已加载」并附记录时间；恢复后等待当前会话的加载确认。来源编号、配置版本、哈希、Provider、会话代次与绑定时间放入默认折叠的技术详情。原生 Provider 文件指令可能另行加载，四字段详情不能代表模型接收的全部上下文。

## 6. 快照、Provider 与派生对话

加载状态与配置快照分开处理。「已加载」只能在服务端确认 Provider 应用结果后出现。加载失败重试使用原用户消息和原 snapshot，不重新选择最新配置，不重复插入用户消息或生成重复回复；结果不明确时先等待或回读状态。

「消息尚未执行」必须有执行侧明确确认；执行结果不明确时展示等待确认状态，不能直接提供会导致重复执行的重发操作。历史模式由服务端识别，不能靠消息数量或页面是否为空猜测。

非空 Context 只允许在当前支持它的运行方式下启动或恢复；V1 首期支持范围为 Codex 与 Pi。已有绑定按其固定 snapshot 判断能力，不能以最新配置替代。四字段全空时完全沿用现有 Provider / Expert 能力，不因 Context 限制原有流程。

同一 Project 的 fork/handoff 在来源已绑定时继承固定 snapshot；来源为历史模式时继承历史模式；来源未绑定且现有规则允许派生时，由派生 Thread 在自己的首次有效发送中绑定。跨 Project 派生继续遵守现有禁止规则，不提供携带旧 Context 绕过限制的入口。

Context 不编辑 Expert Persona、Skills、模型或专家选择入口。执行侧统一合成 Context 与 Expert 指令，保留双方内容后交给对应 Provider，不能用 Context 参数覆盖现有 Expert 指令。前端只依据加载确认展示结果，不将快照存在或请求已发送等同于加载成功。

## 7. 旧项目指令迁移

发现旧指令时，只对相关 Project 提示迁移。写入前由用户确认数据归属确实属于当前工作区与 Project；不得仅凭旧 ID 推断归属。迁移以当前 Project revision 做条件保存，逐项回读核对后才标记完成。冲突需用户选择；保存失败或结果不明确时保留旧数据和未完成状态。批次允许部分完成，已核对项不因其他项失败而回滚。

完成状态必须持久保存且重启后可恢复。迁移只处理约定的旧项目指令字段，不清理或改写 legacy Thread Notes。只有该 Project 确有待认领、待处理或冲突的迁移数据时，才限制它自己的普通新对话首次发送；已有 Thread、其他 Project 与无迁移数据的用户不受影响。

## 8. 原型与接入边界

原型是独立 React / Vite 演示壳，直接导入现有 UI 控件，不是完整 Sidebar、ChatView 或生产路由接入。审核工具（主题、字号、故障条件）默认收起；提供方使用原输入区选择控件，仅为演示。业务 `nativeApi` 与网络边界 fail-closed；系统窗口 Hook 使用专用的 unavailable mock。原型不调用真实 Synara API、数据库、Provider，不读写 Synara 的 localStorage 或 Provider 配置。

UI 扩展以可选 props 提供，旧调用默认兼容；没有新增正式 API、contracts、Provider 执行链路或服务端行为。原型里的保存、绑定、迁移与加载状态不能作为真实服务端能力或验收通过的证据。正式实现必须另行完成条件保存、回读、事务、snapshot 与 Provider 应用验证。

正式前后端联调需提供以下能力，API 字段名、错误码和事务边界另在技术方案中确定：

| 前端依赖                 | 服务端或执行侧需提供                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------- |
| 配置读取与编辑基线       | 四字段、归属、配置 revision、条件保存、确认结果与事件更新；重启可恢复                                 |
| 保存失败、冲突及结果不明 | 最新权威配置、可辨别的冲突/失败/未确认状态、回读与请求去重                                            |
| 首次发送与详情           | 独立不可变的 Thread snapshot、四字段副本、来源 ID/名称/版本及绑定信息；绑定、应用和消息执行的明确边界 |
| 加载与恢复               | 与 snapshot 分开的加载记录，包含 Provider、会话代次、确认状态；原消息/快照重试与执行结果核对          |
| Expert 与 Provider 共存  | 能力判断、统一指令合成、不覆盖 Expert；原生恢复与空 Context 兼容                                      |
| 历史、派生及归属变化     | 服务端历史标记、来源快照、同项目继承/跨项目限制，删除来源后的快照仍可读                               |
| 旧指令迁移               | 工作区/Project 归属确认、逐项 CAS、回读核对及持久迁移状态，保留旧数据与 Notes                         |

普通发送不携带前端草稿作为执行上下文。切换工作区或对象后，不复用另一对象的草稿、来源预览或迁移归属。正式持久化、原生 Provider 与 fork/handoff 验收另行进行。

## 9. 验收场景

当前原型演示与生产接入验收分开记录。下表定义产品场景；只有本轮[验收记录](./prototypes/space-context-v1/acceptance.md)中有证据的项目才可标为通过。

| ID     | 场景                                   | 预期结果                                                                          |
| ------ | -------------------------------------- | --------------------------------------------------------------------------------- |
| CTX-01 | Sidebar 切换 Space 与浏览项目、Threads | 保留现有层级和列表；不出现新分区或树状 Space 节点。                               |
| CTX-02 | 新建 Space、编辑 Void                  | 新建仅要求名称和图标；Void 不显示 Context。                                       |
| CTX-03 | 编辑 Space 四字段并保存                | 名称、图标、目标、指令一次提交；成功关闭，失败保留全部草稿。                      |
| CTX-04 | Project 打开 Context 区                | 按继承、项目目标、原项目指令排序；继承默认折叠且只读。                            |
| CTX-05 | 粘贴超限内容                           | 原文不截断；展示错误并暂停该次保存。                                              |
| CTX-06 | Project 连续输入                       | 500ms 防抖，串行提交，最终保存最新目标与指令。                                    |
| CTX-07 | 一次写入在途时继续编辑                 | 后续值进入队列；旧 ACK 不覆盖新草稿，下一写入按确认 revision 执行。               |
| CTX-08 | 保存期间切换对象                       | 每个请求绑定捕获的 Project ID；草稿或响应不得串到另一 Project。                   |
| CTX-09 | 保存失败或版本冲突                     | 自动队列暂停，草稿保留；比较最新值后由用户决定，不静默覆盖。                      |
| CTX-10 | 写入 ACK 丢失或结果不明确              | 先 readback；确认后再反馈，不盲目重复写入或虚报成功。                             |
| CTX-11 | 离开有草稿的 Project 编辑区            | 先 flush 并等待成功；失败、冲突或未知结果时由原 guard 保留编辑区。                |
| CTX-12 | 离开时选择放弃                         | 只丢弃未提交队列与草稿；已提交写入按服务端实际结果处理。                          |
| CTX-13 | 普通发送时仍有编辑草稿                 | 不弹保存 guard、不强制 flush；首次绑定只使用服务端实际已提交配置。                |
| CTX-14 | 首次绑定成功后源配置变化               | 服务端返回的 snapshot 保持不变；更新信息只在 Context 详情内出现。                 |
| CTX-15 | 首次加载失败后重试                     | 使用原消息与原 snapshot，不重复发送或回复；未知状态先回读。                       |
| CTX-16 | Provider 启动与恢复                    | 非空 Context 在不支持时明确拒绝；全空 Context 保留原有能力。                      |
| CTX-17 | 同 Project 派生与跨 Project 派生       | 同项目按固定 snapshot / 历史模式继承；跨项目继续禁止。                            |
| CTX-18 | 首次发现旧指令                         | 确认工作区和 Project 归属后 CAS 写入并 readback；完成状态可跨重启恢复。           |
| CTX-19 | 迁移冲突、失败或 ACK 不明              | 旧数据保留；冲突需选择；结果不明先回读；仅阻断相关 Project 的新 Thread。          |
| CTX-20 | legacy Thread Notes                    | 迁移与 Context 保存不清除、不改写历史 Notes。                                     |
| CTX-21 | 常态 Chat 界面                         | 不显示常驻 chip、计数、固定状态、更新/legacy 横幅或空页引导；可从「＋」打开详情。 |
| CTX-22 | 新增 UI props 缺省                     | 旧调用保持现有 Space、Environment 与「＋」菜单行为。                              |
| CTX-23 | 键盘、焦点、主题与字号                 | 可访问标签、键盘操作、焦点返回和 Settings 字号均符合现有控件规范。                |
| CTX-24 | 同时使用 Expert 与 Context             | 专家指令与四字段均保留，加载结果以当前会话确认记录为准。                          |
| CTX-25 | 快照读取失败、恢复或执行结果不明       | 不用最新配置伪装原快照，不把旧加载记录当作当前成功，不盲目重发。                  |
