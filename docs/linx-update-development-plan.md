## 1. 结论与范围

**Linx 是独立产品，仅建设 Linx 自有的发布与应用升级链路；不把 Synara 上游同步作为产品能力或发布前置。** 复用现有 Electron 更新器、构建器和恢复能力，不重新建设更新服务器、安装器或第二套任务系统。

唯一交付路径：

```text
Linx 源码固定提交
  → 质量检查、构建、签名与产物验证
  → 发布 Linx GitHub Release
  → 用户点击检查更新
  → 用户点击升级
  → 下载、验证、安装前安全门禁
  → 退出、替换、重启、迁移与健康确认
```

源码 push 只触发 CI；正式版本标签经发布门禁后才对应用可见。应用不拉源码、不现场编译、不合并任何上游分支。

### 已确认的用户决定

- **D-01 [ADOPTED]**：产品名称为 **Linx**。用户输入中的前导 `[` 按文本输入残留理解，不作为品牌字符。
- **D-02 [ADOPTED]**：按独立产品演进，不保留“官方升级＋自有升级”两条产品链路。先前咨询中 AD-01 的双链路建议被本决定替代。
- **D-03 [ADOPTED]**：期望手动检查新版本，主动点击升级，由应用自动完成后续安装流程。
- **D-04 [ADOPTED]**：当前授权为制定开发计划和记录命名；不是立即修改应用、停用远端工作流、改 GitHub 仓库名、发布或安装的授权。

### 本计划包含

产品命名与旧安装承接、单一发布策略、应用内检查/升级、安全安装与恢复、发布流水线、引导版本及下一版本的真实升级验收、过时上游同步入口退役。

### 不包含

整仓库机械替换 `synara` 字符串、删除许可证/历史归属、重写 Provider/Expert/Hub、插件或模型 CLI 自动更新、自建 CDN/账号授权服务器、灰度发布、强制升级、自动回滚用户数据。仅保留隔离开发/验收环境不构成第二条产品发布链路。

## 3. 必须保持的架构约束

### AD-01：一个产品、一个受控正式发布入口

绑定发布工作流、构建策略、桌面更新器。Linx Release 是唯一正式更新来源；不依赖 upstream tag、候选合并状态或官方 latest。旧官方 stable/beta/bridge 发布分支、自动 Beta 标签及 npm 官方包发布不得继续成为 Linx 发布副作用。验证通过后退役专用于上游同步的工作流及调用；历史证据、Git 历史和许可证保留。

### AD-02：品牌改名不等于重建安装与数据身份

建议正式显示名改为 Linx；Bundle ID、已有 home、Electron profile、协议 scheme、凭据命名空间先保留为 Linx 的持久兼容身份，不建立新旧双读写或临时别名层。这些内部字符串不是第二个产品。

首个引导安装必须解决 `Personal Workbench.app` → `Linx.app` 的实际承接：核对旧进程退出、安装路径、单实例锁、Dock/登录项、深链、系统权限与钥匙串访问；禁止两个 app 同时写同一 home。旧 app 仅作为不可同时启动的恢复产物保存，不作为另一在用版本。更换签名身份可能触发权限重新授权，不承诺无感保留。

如用户要求 Bundle ID/home/scheme 全改为 Linx，应先补独立迁移方案、唯一源到唯一目标的切换及恢复验收；不能在品牌替换中顺手执行。

### AD-03：构建时固定可信来源，缺省拒绝

复用现有 app-update.yml 和 updater 校验。配置固定 Linx 产品标识、发布仓库、正式频道、平台/架构与版本；不从客户端输入或普通启动环境切换 feed，不回退官方源。

版本必须是可解析且单调递增的 SemVer，拒绝同版、降级、未经支持的预发布版本和错误产品/安装身份。Linx 与遗留官方版本不得按“数字更大”混选。标准元数据、内嵌身份和原生签名共同构成检查，不为本需求另建一个并行发布数据库；哈希只能证明完整性，不能替代发布者真实性。

### AD-04：显式用户意图贯穿下载与安装

手动检查只查询、展示版本和说明；不后台轮询、不因前台激活触发、不在检测到版本后自动下载。点击“升级并重启”授权本次固定目标的下载和安装；按钮提前说明重启影响。

空闲且预检通过时可一次操作完成；若有活动任务、审批、未保存编辑或无法核对的执行状态，保留已下载包并提示阻塞，不自动取消任务、不无限后台等待并突然重启。待用户解除阻塞后再次点击安装。普通退出不安装。应用重启或目标变化后不沿用旧的自动安装意图。

### AD-05：状态只有一个权威所有者

桌面主进程拥有更新状态、下载/安装互斥和持久安装记录；renderer 仅通过既有窄 IPC 发请求/订阅。业务后端拥有原生任务、审批、自动化派发与数据兼容状态。

安装安全门禁必须是受控维护过程，不是一次查询“当前空闲”：进入维护后拒绝新派发/写入，排空已接受操作，确认 UI 未保存状态与所有相关窗口，停止后端并验证退出，随后制作/核验一致性恢复集。预检到退出之间不得允许新的任务插入。失败要释放维护状态并恢复可用界面。

### AD-06：成功必须跨过重启与数据健康

“下载完成”“调用 quitAndInstall”或“进程退出”都不是成功。复用现有安装记录，关联源版本、目标版本、产物摘要与尝试标识；下一次启动确认目标版本、正确 home、迁移完成、后端 ready 和必要投影健康后才记为成功。

迁移遵循既有追加式 ledger 和已应用脚本冻结约束，不因产品独立重写旧迁移。程序回退与数据恢复分开：不兼容迁移后不能仅启动旧程序，不自动覆盖升级后的新增数据。优先发布更高版本修复包；需要恢复时显示影响并取得明确授权。

## 4. 用户流程与可见结果

1. **检查更新**：展示当前 Linx 版本；点击后进入检查状态。离线、限流、清单异常是检查失败，不能显示“已是最新”。
2. **发现版本**：显示目标版本、发布说明和“升级并重启”；只认已完整发布且适配本机的版本。发布说明按不可信内容安全渲染。
3. **下载与验证**：展示进度；重复点击不重复下载或安装。复用现有断点/停滞处理，关闭应用后不得自动续接安装授权。
4. **安装前门禁**：校验空间、安装目录权限、产物身份、签名、数据兼容和恢复集；进入维护状态排除任务竞争。拒绝时说明具体原因和可继续动作。
5. **安装与重启**：退出、调用既有平台安装器、重启。系统要求权限确认时真实呈现，不能承诺绕过系统提示。
6. **结果确认**：新版健康才显示成功；版本未变、启动失败或迁移失败进入可诊断恢复路径，不循环重装。

复用现有菜单、Sidebar 更新订阅、按钮及通用弹窗；不创建更新中心页面或改变主布局。产品名称与更新交互属于计划范围，具体界面方案在实施前按现行 SOP 确认。独立产品不得默认继承原版 Beta 诊断上报；现有能力门禁逐项盘点，不能通过统一 flavor 顺手开放受限功能。

下列 LU 编号用于工程交接，不代表已创建 Hub 任务或 BMad Epic。开发估时在 LU-00 完成签名和平台核对后给出，避免以未知凭据/跨平台问题承诺日期。

- 交付：实现任务共用的产品/发布配置契约、平台清单、旧安装承接步骤与 UI 状态草案。正式架构决定采用后同步现有架构标准，不以本计划自动覆盖其规范。
- 门禁：Q-01 至 Q-03 已处理；无法取得签名时允许代码与构建验证继续，但真实自动升级/正式发布保持阻塞。

### LU-01：Linx 品牌、版本与单一路径切换

- 依赖：LU-00。
- 主要接入：desktopIdentity、桌面 package 与构建身份、build-config、版本策略、品牌资源及当前发布/同步文档。
- 工作：显示名/关于/安装包与 Release 标题统一 Linx；消除最终包 `1.1.0` 与 Workbench `0.1.x` 的版本权威冲突；保留选定的持久安装身份。不重命名全部内部 import 或重做 Logo。
- 清理：从 Linx 默认开发/发布路径移除上游 sync 门禁、旧 bridge 与自动 Beta/npm 发布；移除专用同步 schedule 及无调用的专用脚本/测试，保留共享质量和迁移检查。盘点宿主自动化，授权后单独停用并留回执；源码删除不等于远端停止。

### LU-02：Linx 更新策略与客户端接入

- 依赖：LU-00；与 LU-03 可按固定配置契约并行，最终集成依赖 LU-01。
- 主要接入：桌面 main/updateState/updateMachine、preload、现有跨进程契约、Sidebar 更新动作及现有按钮。

- 门禁：点击检查不下载，点击升级才下载；检查/下载/安装三类错误可区分；旧状态、重复点击及晚返回不能触发第二次安装；Preview/dev 无正式更新授权。

### LU-03：签名构建与 GitHub Release 流水线

- 依赖：LU-00；发布联调依赖 LU-01。
- 主要接入：现有 release.yml/release-platform.yml、构建器、release-update-policy、发布清单生成、产物 provenance 与 smoke 脚本。
- 工作：改为 Linx 单一正式发布入口，复用平台构建步骤；源码 push 只做 CI，正式标签固定 SHA/版本/锁文件；构建 macOS DMG、签名后 ZIP 及一致清单，配置签名/公证；其他选定平台提供对应产物。
- 发布原子性：先上传不可被正式客户端发现的候选资产，核验选定平台全部齐全、hash/size/签名/元数据后再公开 Release。失败不把不完整版本置为最新；已发布同版本资产不可覆盖，修复使用新版本。
- 门禁：从发布前候选产物完成隔离启动；远端资产下载后再次校验。正式源只发布 Linx 合格产物，不混入旧 Synara Release 的 latest。必要时使用专门的公开发布仓库，须先决定，不能依赖 GitHub 隐式 fallback 避险。

### LU-04：安装维护门禁、数据恢复与重启确认

- 依赖：LU-00；与 LU-02/LU-03 共用目标身份与版本契约。
- 主要接入：既有安装准备/marker、后端停止与任务派发边界、既有数据库迁移/备份恢复服务；新增跨进程字段归 contracts，运行编排不进入 contracts。
- 工作：实现 AD-05 的互斥维护过程；沿用现有迁移备份，补齐配置/专家/技能及受管引用的恢复覆盖清单，不每次复制整个工作区；持久化尝试结果并跨启动验证健康。
- 失败处理：下载/预检失败保持旧版；停止/交接失败恢复可用状态；替换后启动失败提供可用的外部恢复说明与已校验恢复入口；数据恢复只能由明确操作触发。
- 门禁：任务竞争、后台自动化、待审批、多窗口未保存状态、磁盘不足、备份失败、崩溃中断均不得破坏旧数据或误报成功；更新后新数据受保护。

### LU-05：引导安装与下一版本真实升级

- 依赖：LU-01～LU-04 和适用质量门禁全部通过。
- 工作：先在隔离数据副本上验证旧 Workbench → Linx 引导安装 B0；再发布 B1，通过 B0 的真实菜单检查/点击升级完成安装重启。B0/B1 为角色名，不预占具体 SemVer。
- 引导限制：旧应用没有可用 feed，必须手动安装一次 B0；不能宣称上传 GitHub 即可唤醒旧应用。B0/B1 使用选定的连续签名身份，验证重命名后旧路径、登录项与系统授权。
- 交付：绑定精确 SHA/tag/产物摘要的验收记录、最终发布说明、签名验证结果、恢复操作与有限产物轮换。日用安装/公开发布按对应授权执行，不拿隔离验证代替。
- 门禁：LU-AC 全部适用项通过，用户/Hub 验收后才关闭任务。

依赖：`LU-00 → LU-01；LU-00 → LU-02/LU-03/LU-04；LU-01～04 → LU-05`。不是要求立即派发并行人员；共享 main/契约文件由一个集成负责人管理。

## 6. 验收矩阵

- **LU-AC-01 品牌与身份**：新包和应用可见品牌为 Linx；旧数据仍可见；错误 home/双实例被阻止；改名后的深链、登录项和权限行为有真实记录。
- **LU-AC-02 单一来源**：官方高版本、错误产品、错误签名、缺失清单、未发布候选、错误架构、同版/降级均不得进入安装；没有上游同步或官方发布副作用。
- **LU-AC-03 手动语义**：启动/前台/计时器不检查；检查不下载；仅显式升级下载并尝试安装；普通退出/重启不偷装。
- **LU-AC-04 可信发布**：标签、app 版本、SHA、锁摘要、清单、实际下载字节匹配；发布失败不可见为最新；同版本不可改写。
- **LU-AC-05 并发与运行保护**：重复点击幂等；维护期间新任务/自动化写入被拒绝；运行、待审批、编辑未保存或状态不可核对时不安装；失败释放维护状态。
- **LU-AC-06 故障结果**：离线/限流、下载中断、损坏缓存、空间不足、权限不足、备份失败、安装器失败、重启后版本未变分别可诊断；不循环重装、不误报最新或成功。
- **LU-AC-07 真实升级**：每个声明支持的平台从 B0 真正升级到 B1，验证版本、重启及后端健康；mock feed、单测、安装包启动不替代真实替换。
- **LU-AC-08 数据与恢复**：旧数据副本升级前后聊天/专家/技能/配置及受管引用可核对；至少一次跨现有 ledger 迁移与恢复演练；无迁移版本另测快速路径；更新后新增数据不被静默覆盖。
- **LU-AC-09 首次承接**：ad-hoc 旧包 → 签名引导包路径实际验证；旧 app 不与 Linx 并行写数据；引导后不再依赖手工源码构建。
- **LU-AC-10 退役与交付**：旧自动同步入口不再是默认路由；远端是否停用有独立回执；恢复引用和产物轮换完成，未验平台明确不宣称可用。

检查选择：实施阶段结束执行 `bun run fmt:check`、`bun run lint`、`bun run typecheck` 与受影响 Vitest；本功能跨桌面/服务端/发布生命周期，最终执行 `bun run test`。宿主接入更新 integration-points 并运行 `bun run workbench:check-boundaries`；平台/进程边界运行 `bun run windows-runtime:check`；迁移变化运行 `bun run migrations:check`；品牌变化运行 `bun run brand:check` 并同步其 Linx 合约。

现有单测覆盖版本边界、来源、状态竞争和恢复不变量；UI 以实际菜单/按钮操作验证；签名与替换以真实打包产物验证。每个选定平台独立记结果，不将 macOS arm64 通过转移给 Intel/Windows/Linux。

## 7. 待决策与阻塞点

- **Q-01 首批支持平台**：建议先验收当前日用 macOS arm64，再独立扩展 Intel/Windows/Linux；这是建议而非用户已批准的缩减。正式 LU-00 必须确认范围。Windows 需要独立安装器身份及签名，不是简单打开现有 flavor。
- **Q-02 签名与公证**：建议 Developer ID 签名＋Apple 公证；尚未核对账户/证书/CI secrets。没有凭据时不得把关闭验证、移除 quarantine 或自写无校验替换当作完成。用户若明确不采用，需另行批准不同分发方案及其信任模型。
- **Q-03 持久身份**：建议品牌为 Linx，但延续 `com.wylinx.workbench`、旧 home/profile/scheme，以减少一次升级同时改动数据与权限的风险；若要求彻底改内部身份，先追加迁移工作包并重新评审。
- **Q-04 发布仓库**：建议保留现有公开仓库地址；LU-00 盘点既有 Release 是否混有官方版本，决定清晰隔离的发布仓库或可证明严格准入的 feed 配置。不能未经授权改仓库名、可见性或删除历史 Release。
- **Q-05 视觉品牌资产**：已确认名称 Linx，未确认新 Logo/图标。本计划不擅自设计新视觉；实施可先复用获准资产，若含原产品标识需提交替换方案再确认，不把它误报为完整品牌迁移。

这些问题阻塞相应实现/发布门禁，不阻塞开发计划交付。本计划不附未经基线实测的工期承诺。
