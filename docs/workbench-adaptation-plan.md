### 模块与数据所有权

Synara 宿主拥有认证、任务执行、Provider、事件投影、数据库连接和恢复生命周期；接入层负责页面/导航装配、窄客户端、依赖注入及兼容转换；功能模块实现业务规则、页面和测试。跨进程 schema 归 contracts，运行逻辑留在对应应用，共享运行工具使用 shared 的显式子路径。

新模块在现有需求或设计记录中说明以下内容，不要求另建 SDK 或每次新增文档：

```text
模块 ID / 职责与范围：
页面入口 / 真实父路由及布局 / 访问条件（无页面则注明）：
数据所有者 / 读写入口：
宿主依赖 / 对外能力 / 跨模块协作：
失败与不可用行为 / 接入点 / 验收场景：
```

跨模块使用明确的公共服务、契约或导出的业务能力，不读取另一模块内部状态。Home、Task 等复用宿主任务数据源、查询缓存及投影；模块只持有自己的业务状态，不复制任务执行状态。基础组件、纯工具和适用的查询能力直接复用；存量 Expert/MCP 只在消除真实耦合时整理，不因目录名称整体搬迁。

新增或变更宿主依赖时同步接入清单与扫描覆盖；例外精确到文件、specifier、原因和测试。现有 [边界检查](../scripts/check-workbench-boundary.ts)覆盖指定 features、server experts、命名的 Expert/MCP 与 Space/Context Web 界面，以及接入清单的 `featureFiles` / `featureRoots`；真实 CLI 要求清单存在、引用可访问、保留依赖与实现一致。新目录必须登记或纳入自动命名范围；该检查不是传递依赖分析或运行时安全隔离。

Context 页面、自动保存与旧指令迁移通过 `workbench/host/contextClient` 读取现有 `ContextApi` 和 capability，不再直接读取完整 native API 或旧指令 store。宿主保留“不支持”与“支持但连接不可用”的区别，返回原 API 对象，保持自动保存队列身份。Space 命令辅助函数只接收所需的 orchestration 方法；批量归属在传输结果不确定时仍保留 `getShellSnapshot` 校准能力。Space controller/路由同步、Context RPC/生命周期/投影/持久化继续作为明确登记的宿主接入。

### 路由与布局契约

先核对真实父布局，再选择 URL 与挂载层级：

| 布局职责      | 适用页面                         | 必须核对的继承行为                       |
| ------------- | -------------------------------- | ---------------------------------------- |
| 全局布局      | Home、Space 等跨项目页面         | 认证、导航、全局订阅、启动协调与快捷键   |
| Chat 布局     | 项目工作区或依赖聊天侧边栏的页面 | 任务选择、侧边栏、终端、快捷键及聊天状态 |
| Settings 布局 | Expert、MCP 等配置页             | 设置导航、查询参数、草稿保护及返回行为   |

以上是职责分类，不代表已存在三个独立、解耦的布局组件。当前 root 也包含全局任务协调，`_chat` 还拥有侧边栏与任务交互；不能只换父路由就宣称与任务状态隔离。只有出现实际需求才提取共享布局。

路由入口只负责参数校验、访问条件、惰性加载与宿主装配，业务规则留在模块。沿用现有文件路由及生成工具，不手改生成路由树；首版不引入 Virtual File Routes 或动态路由加载器。registry 元数据不会自动创建路由。

导航目标必须对应真实路由；新增页面在现有测试中覆盖直接访问、刷新、前进/后退、未授权、加载失败与重试；涉及编辑状态时覆盖草稿保护，涉及设置页时覆盖现有 URL 归一化。按需复用现有用例，不添加仅镜像实现的测试。继续遵循 AGENTS 的字体、披露动画、可访问性和 transcript 约束。

### 服务与生命周期接入

使用现有类型化 RPC、认证、请求准入、取消和错误语义；不增加任意方法名/参数的通用插件调用接口。会话启动、专家快照、Context、取消与恢复在原生命周期内明确接入，保留 Provider 差异与 session 所有权。已绑定任务的必需能力缺失时明确失败，不静默清除绑定或切换执行者。

Hermes 优先作为常驻服务。实施前在专项方案中明确启动/停止所有者、健康检查、连接认证、超时、断连恢复与重试幂等；服务异常只阻塞明确依赖它的操作，原生任务仍可独立使用。当前标准不表示 Hermes 已接入或已验证其 API。

扩展迁移沿用独立 ledger 与宿主连接、事务和恢复边界，兼容与回退按升级 SOP 执行。Beta 功能沿用 AGENTS 的共享功能门控、服务端拒绝、前端入口及 Stable 持久化状态要求，不改变应用身份、数据与更新渠道隔离。

历史兼容例外：Context 已使用原生 tracker 的 `111_ContextV1`，按用户确认保留编号、名称、文件与 SQL 内容，不做 ledger 接管或搬表。[迁移检查](../scripts/check-migration-lineage.ts)冻结其身份与脚本 SHA-256，并要求新增原生迁移能追溯到锁定的上游 tag/完整 SHA；缺少来源时明确失败，新增 Linx 扩展使用 Workbench 独立 ledger。此例外不构成继续占用原生迁移编号的许可。 用户随后确认：上游 v1.0.1 已占用 111 时，允许在隔离升级候选实现旧 `ContextV1` 的精确 ledger 兼容接管，原脚本、身份和历史证据仍冻结保留；见[已确认兼容方案](./workbench-implementation-plan.md#v101-compatibility-proposal)。该方向尚未在当前 main 实施，不代表用户数据库已迁移。实际实现与检查见[架构对齐验收](./workbench-adaptation-acceptance.md#alignment-implementation-20261016)。

## 1. 目标、收益与范围

目标是让官方导航、设置、客户端接口或业务请求接入变化时，修改尽量集中于明确的宿主适配文件，专家和 MCP 的页面、校验、授权规则与配置管理可以继续复用。宿主指承载这些模块的 Synara 应用。

当前值得优先投入的是 UI 入口注册、业务请求接入和依赖检查。专家与 MCP 共用同一业务链，尚不足以支撑通用动态插件平台；独立的业务页面也不需要逐层包装所有基础组件。

| 首期纳入         | 具体交付                                                         |
| ---------------- | ---------------------------------------------------------------- |
| UI 入口          | 专家和 MCP 的导航、页面、搜索入口集中注册；复用已有路由          |
| 前端宿主接口     | 页面使用明确的数据与导航能力，原生客户端和路由差异收拢           |
| 服务端业务接入   | 专家与 MCP 请求处理集中装配，保留现有认证、契约与错误语义        |
| 原生 UI 扩展位置 | 仅整理已经存在的专家选择器、任务控制接入；按实际收益决定是否提取 |
| 依赖约束         | 检查迁入范围内的模块是否绕过适配边界，并更新接入清单             |
| 兼容验证         | 原生与自定义行为回归、受控接口变化验证、升级成本记录             |

首期不加入动态代码加载、第三方插件安装、插件市场或沙箱；不引入第二套任务执行器、通用事件总线或全局串行队列；不迁移专家绑定列、快照和数据库；不重新包装所有按钮、表单、主题；不全面重做 Sidebar、ChatView 或消息渲染；不同时集成官方新版本。看板与个人首页仍为后续需求。

## 3. 总体结构与所有权

可编辑图：[适配层架构图](./diagrams/workbench-adaptation.drawio)。图示：[接入关系预览](./diagrams/workbench-adaptation.png)。图中的“稳定”表示由我们维护的明确契约，并不承诺能自动兼容任意官方变更。

| 层              | 负责                                               | 依赖限制                                           |
| --------------- | -------------------------------------------------- | -------------------------------------------------- |
| 功能模块        | 专家编辑、MCP 列表、授权、发现与导入的业务行为     | 使用明确的宿主能力；基础组件可直接复用             |
| 工作台接口      | 页面描述、导航目标、业务查询/命令、必要 UI 上下文  | 只暴露所需能力；不交出完整 store 或 Provider 服务  |
| 宿主适配与装配  | 路由、原生客户端、请求处理接入、能力差异转换       | 可以接触原生内部；每项深层依赖登记所有者和验证路径 |
| Synara 原生内核 | 会话、Provider、认证与审批、事件投影、数据库、进程 | 保持原有所有权、事务与取消传播                     |

前端宿主接口在 Web 内部定义，服务端接口在 server 内部定义；跨进程请求/返回 schema 继续放 `packages/contracts`。共享运行工具继续沿用 `packages/shared` 的显式 subpath 导出。只有出现真实的跨包共享需求才提取公共类型，首期不新增一个万能 SDK 包。

内核在既有接入位置调用专家能力是有意保留的依赖，由宿主装配提供明确入口。边界约束不能误把这些调用改为异步广播，或把专家启动前置条件变成可忽略的 UI 通知。原生聊天路径无需经过新的模块分发器。

## 4. 前端设计

### 4.1 设置页面与入口

扩展现有 `registry.ts` 作为自定义入口元数据的唯一来源，包含模块 ID、现有 page ID、标签、描述、图标、导航分组及可搜索说明。页面实现的惰性加载映射放在单独的 Web 装配文件，按 page ID 做穷尽类型校验；元数据不静态导入大页面或原生 store，避免导航与搜索加载整套专家页面及循环依赖。

原生 settings 路由只负责确定页面、提供窄上下文并挂载工作台页面宿主。专家 / MCP 页面内的布局、表单、校验、草稿与保存反馈由原组件负责。保留当前 `experts`、`mcp` 与旧连接/应用接入地址的归一化结果、tab、expertId、connectionId 和浏览器前进/后退行为；具体 URL 字段复用已有解析，不凭模块声明接受任意路由或代码。

所有入口消费同一元数据，不能分别在 registry、导航、搜索中手写三份模块信息。原生设置条目继续使用其现有来源。页面加载失败保留返回与重试入口，不丢弃未保存草稿；切换页面继续使用 `useExpertDraftGuard` 的保存、放弃、取消与关闭提示语义。

### 4.2 页面数据与导航接口

按实际调用从 `wsNativeApi` 和现有 settings 代码收拢所需能力，例如读取/保存专家、管理连接、发现/导入配置、打开指定专家或连接。方法直接复用现有 contracts 的输入与输出，不建立第二套同义 DTO。

页面通过窄客户端能力调用业务请求。`wsNativeApi` 已有集中映射，若使用已有类型的能力子集即可限制页面依赖，就不再增加转发文件。现有查询 key、revision 冲突、失效刷新与后台 refetch 行为继续使用已有查询体系；不能让宿主订阅另维护一份任务状态或覆盖 dirty draft。实时状态采用现有快照/订阅机制，保留断线重连、重放和最终状态校准。

本地接口随同一源码 tree 编译，首期通过类型检查和行为测试保证一致，不维护多套历史适配器。独立部署的前后端仍遵循现有协议兼容机制，不另设一个能掩盖线协议差异的模块版本号。

### 4.3 原生界面的扩展位置

只针对现有 `ExpertComposerPicker` 和 `ExpertTaskControl` 明确宿主传入的上下文：当前线程/草稿身份、已有专家绑定、允许的选择/控制操作及禁用原因。组件保留其现有实现，不复制 ChatView、输入框或任务状态 store。

如果实际检查显示提取挂载组件可以消除多个原生接入点的重复条件，则增加一个明确的、类型化的挂载入口；若现有组件已足够集中，仅登记接入点与测试，不再增加空包装。首期不提供任意位置插入节点、运行脚本或修改任意原生 props 的插件机制。

挂载入口不改变消息到达、自动跟随、流式文本或虚拟化测量行为。未绑定专家的原生任务沿用现有路径；已经绑定专家的任务，必需能力缺失必须呈现可诊断错误，不能因组件异常静默清除绑定或退化为通用助手。

### 4.4 视觉与可访问性

复用现有 Button、Dialog、输入控件、主题和披露动画，沿用 `text-ui*` / `text-chat*` 字体设置、键盘和 reduced-motion 行为。共享原生组件 API 如有真实变化，只为受影响的少数复合组件增加适配，不为每个按钮建立别名层。前端适配不承担新的视觉改版。

## 5. 服务端设计与深层接入

专家与 MCP 的业务处理从现有请求分支按职责收拢，依赖由 `createWorkbenchExpertRuntime` 及既有服务装配注入。原生 RPC 入口继续拥有 schema 校验、`requireOwner` 授权、请求准入、取消信号与错误映射；一次请求只有一个明确的执行路径。现有 `rpcEffect` 与 `expertRpcEffect` 各自负责的错误处理语义保持原样，不能在提取时无依据地统一。

保留已有 RPC 名、payload、响应和 revision / CAS 语义。现有 handler map 已按 `WS_METHODS` 静态登记，优先从中提取业务处理并沿用既有 dispatch；无需再加一套动态注册。不得新增接收任意字符串和任意参数的“调用插件”接口，不得仅靠 UI 隐藏实现授权。实现前核对 Effect 等现有服务依赖，不因提取文件引入第二套错误或运行容器。

连接检查继续显式触发并释放连接；工具调用继续由既有 Gateway 会话拥有，保留工具白名单、实时停用、凭据引用、取消与关闭。配置发现继续只读来源，导入继续使用已有冲突预览、引用保护和版本检查。适配层不改变 Provider/model 选择，也不把所有 Provider 的能力压成相同布尔值。

以下深层接入继续原位维护，列入升级检查：

| 接入               | 必须保持的行为                                | 首期策略                     |
| ------------------ | --------------------------------------------- | ---------------------------- |
| 任务创建与启动     | 提交前固定专家快照；必需资源/连接失败阻止启动 | 保留原有调用与顺序           |
| 恢复、fork/handoff | 按现有语义使用固定绑定及 runtime payload      | 保留既有 Provider 差异与测试 |
| 事件与投影         | 专家绑定随任务持久化、重放、查询和 hydration  | 不新增旁路状态或异步补写     |
| 迁移与恢复         | 统一 SQLite 所有权、事务、备份和恢复点        | 不搬表、列或迁移历史         |
| 凭据与进程         | 现有 secret store、共享平台与进程边界         | 不复制凭据/启动/清理实现     |

## 7. 实施顺序与每阶段退出条件

首期已执行 A0–A4，实际结果见验收记录。后续继续执行同一原则：先保存候选基线并核对既有失败，再修改接入。各阶段保持可审查的独立变更；每阶段完成后收掉被替代的旧路径，避免长期双重注册或双写。仅改目录而没有消除依赖/重复的工作不纳入首期。

| 阶段        | 工作                                                             | 退出条件                                                   |
| ----------- | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| A0 基线核对 | 保存候选实际 tree、源码/测试差异；核对现有复用项、失败与接入清单 | 能恢复实施前版本；清单覆盖本次模块与原生接入               |
| A1 设置入口 | 统一元数据与页面装配、导航、搜索、旧地址转换                     | 自定义页面实现不再静态嵌入原生设置文件；深链与草稿行为通过 |
| A2 请求接入 | 收拢窄客户端和服务端处理，保持 contracts 与认证入口              | 方法名/响应不变；授权、CAS、错误、取消与缓存语义通过       |
| A3 边界治理 | 扩大扫描范围、登记深层接入；整理有收益的原生 UI 挂载点           | 能阻止模块新增旁路依赖；暂留依赖有明确职责和测试           |
| A4 验证收益 | 受控宿主接口变化演练；最终检查；记录实际投入                     | 变化主要集中于对应宿主接入，模块行为与原生链路通过         |

A4 的演练在临时分支或工作区进行：模拟设置宿主渲染参数变化，或客户端/请求装配接口形状变化，通过宿主接入恢复兼容，验证专家和 MCP 页面/业务规则无需同步改写；模拟变化在交付前移除。演练只证明所选接口类型的隔离，不能当作真实官方升级成功。

暂不为任务内核提取通用生命周期接口。当后续官方升级出现重复适配，或新的独立模块需要同一能力时，另按行为与事务边界评估；不能为了统一命名把启动、恢复、授权、存储同时重写。

设计阶段已完成链接、命令、图示与格式核对。代码实施检查按下表执行，实际通过、失败与未运行项见实施验收记录。

代码验收至少覆盖：原生无专家任务、保存与冲突、dirty 草稿、全局停用、工具白名单、来源导入冲突、旧任务快照、未授权请求、断线后的缓存/状态校准。先复用现有用例，只为新增边界和行为变化补有意义的测试。

隔离实例使用独立 home 和未占用端口，启动前检查 dev runner dry-run 及双栈监听；升级数据实验用一致性副本。首期不改变存储格式，代码回退仍需核对同期依赖和数据兼容；任何意外数据格式变化都应拆成独立迁移任务，不能用 Git 回退替代数据恢复。发布与生产安装沿用已有授权范围。

## 9. 风险、投入控制与收益评估

| 风险                            | 控制                                                   |
| ------------------------------- | ------------------------------------------------------ |
| 接口过大，把官方内部整体透传    | 仅暴露现有模块所需操作；新能力随真实需求加入           |
| 统一接口丢失 Provider 能力差异  | 保留支持条件、失败和不可用状态，不能静默降级           |
| 装配成为共同故障点              | 按页面/业务能力分开；保留错误来源和原生任务路径        |
| 新层改变时序或拖慢应用          | 不增加跨进程服务、全局队列或完整状态复制；按需加载页面 |
| UI 抽离丢失草稿、缓存和导航语义 | 复用现有 guard / queries，browser 回归覆盖真实路由     |
| 原生组件或深层数据模型仍变化    | 明确保留的接入与验收成本，不宣称任意版本兼容           |
| 抽象投入持续扩大                | 一项提取必须消除具体依赖或重复；无收益包装停止扩张     |

记录首期实际实现与验证投入，再在后续两到三次真实上游集成中记录：官方变更规模/类型、文本冲突文件、实际需语义适配的原生与业务模块文件、修复时间、验证时间和失败原因。同一变更产生的测试/文档文件单列，避免用改动文件总数冒充耦合程度。

判断收益时比较相似变化，并计入适配层维护和回归成本；测试数量、mock 演练或一次无冲突合并均不能证明成本下降。收益来自集中修改与减少重复，深层运行与数据验证仍需投入。尚无真实升级序列，本文不承诺固定工期、节省百分比或升级次数即可回本。

首期完成后，保留本方案、实际接入清单和一份简短验收摘要即可。是否进一步建设插件框架，由实际独立模块需求和升级记录决定。
