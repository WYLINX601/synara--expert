## 4. 资产边界与 Memory 数据模型

### 4.1 自动分类，用户不选存储位置

方法、判断步骤、模板与验收流程进入 Skill；输出偏好等稳定行为约定进入 Memory 的 `rule`；事实与环境分别进入 `fact`、`environment`。当次要求和任务状态不写成长期资产。同一反馈可产生不同资产的独立修订，但不重复保存同一句长期约定。

自动学习先读当前适用的条目及方法，修订准确目标；不能通过改为 Memory、新建同义 Skill 或换资产类型绕过只读授权。近似内容只作定位线索，不能仅凭名称或文本包含关系覆盖其他条目。

长期约定补足本次任务，不覆盖用户当次明确要求、Expert 职责和显式配置。已有 Skill 已表达的约定继续修订原来的可改目标，不为迁移分类另写一条相反 Memory；原目标只读时保留限制。这样新分类不会让第一阶段已学到的约定重复、打架或触发批量转换。

### 4.2 正式存储

拟新增 `SpaceMemoryEntry`，最小字段为：

| 字段                                     | 语义                                                     |
| ---------------------------------------- | -------------------------------------------------------- |
| `memoryId / revision / contentHash`      | 稳定条目身份与不可变修订                                 |
| `ownerId / spaceId`                      | 数据归属；由宿主确定，模型不能指定任意所有者             |
| `expertId / projectId`                   | 适用范围，两者同时存在时取交集                           |
| `kind / key / content`                   | `rule`、`fact`、`environment`；规范化主题键与内容        |
| `sourceRefs / changeId / commitSequence` | 有界来源、学习变更和正式提交顺序                         |
| `observedAt / validUntil? / status`      | 观察时间、明确有效期和生效／撤回状态；不因使用少自动过期 |

同一数据库新增条目、不可变修订和必要索引，读写归 `SpaceMemoryService`。条目头更新、修订、变更回执在同一 SQL 事务提交；并发更新检查准确 revision。不是模型生成一个更大的提示词文件，也不在 Harness 目录形成第二份可写正式库。

默认范围：偏好限定当前 Expert、当前 Space；项目事实和环境再限定当前 Project。不会自动把局部反馈提升为 Space 内所有 Expert 的规则。跨 Expert 的共享规则仅接受用户明确的正式管理操作，本期不增加自动扩大适用范围的能力。

Void 沿用宿主 `spaceId=null` 的虚拟语义，不伪造实体 Space；其中的自动条目同时限定当前 Expert 和 Project，避免形成隐式全局记忆。项目迁入正式 Space 后，不自动搬迁或扩大旧条目的范围。查询和提交始终核对当前 owner、Expert、Project 与 Space；版本固定不等于授权固定。

## 5. Run 装配与关闭语义

### 5.1 行为规则固定，事实按需读取

新增 `RunKnowledgeManifest`，保存准确的规则 `memoryId/revision/hash`、范围、渲染版本及摘要 hash，并关联原 root Run、Expert snapshot 和 Skill assembly。清单作为原 Run 持久配置的补充引用，不修改旧 Skill 包 ID 或历史指纹。

| 场景                                                 | 行为规则                        | 事实／环境                                         |
| ---------------------------------------------------- | ------------------------------- | -------------------------------------------------- |
| 学习开启，新独立 Run                                 | 解析当前适用的已提交版本并固定  | 按任务需要读取当前有效条目，保留所读 revision 回执 |
| 已有 Run、审批继续、自动续接、跨 Worker continuation | 继承原知识清单，不重新追随 head | 允许按原授权范围继续读取，记录实际读取版本         |
| 学习关闭，新独立 Run                                 | 解析关闭时固定的规则集合和版本  | 仍可读取最新业务事实；禁止该 Expert 自动持久写入   |
| 用户明确编辑／撤回                                   | 只协调被修改的准确目标          | 正式写入后下一次读取可见                           |

规则采用有界正文加准确版本索引交付；超预算部分可按该清单继续读取。读取工具必须遵守同一清单，不能从“最新 Memory”接口绕过关闭和当前 Run 的固定版本。编辑所需的最新基线是独立的受授权读取，不作为新运行规则注入当前 Run。

事实和环境以带来源的任务数据返回，不作为长期行为规则拼入系统策略。内容分类由同一学习协议和提交校验共同约束；验收检查分类、实际请求及读取回执，不声称仅凭字符串检测就能保证模型对任意自然语言均不会误判。

ProviderService 在原装配验证后接入知识上下文；原生会话匹配加入知识 hash。新独立 Run 的知识变化需要重建底层会话时，复用现有历史承接，不隐式更换账户／模型。恢复和 continuation 使用原清单及原渲染版本；校验失败不能静默采用最新内容。两端分别记录实际交付内容与后续输出，不能只验证宿主 hash。

### 5.2 固定规则集合的实现

关闭时通过同一短提交门和宿主 SQL 事务，保存规则修订的 `frozenRuleSequence`，并递增原学习 epoch。新任务对规则执行截至该水位的版本解析，包括当时的新增、修订和撤回状态；不会漏进关闭后新建的规则，也不需要复制一套私有 Memory。

用户明确修改固定 Expert 的某条规则时，记录该条目的准确 revision 覆盖；其余规则继续按原水位解析，不能整体推进水位而顺带升级。Skill 的原固定绑定逻辑继续使用。规则水位和覆盖项参加引用保留，不能清掉仍被使用的历史修订。

新增存储初始为空；旧 Run 缺少知识引用按“没有该阶段 Memory”恢复，旧关闭记录缺少水位按 0 解释。只增加恢复契约的缺省语义，不做旧配置转换、历史补学或批量改写。

既有 Context 仍由原服务和用户显式编辑管理；自动学习不改 Space 目标、共享指令、系统提示或工具权限。项目归属改变时，旧清单不获得新范围的访问权；已发送给模型的旧上下文不能声称已从其会话中收回。

## 6. 前台小修订与后台复盘共用提交

### 6.1 工作中的窄工具

拟在既有 Gateway 注册三个 Agent 工具，不新增用户表单：

| 工具                     | 职责与输入边界                                                            |
| ------------------------ | ------------------------------------------------------------------------- |
| `synara_learning_read`   | 读取本 Run 规则、适用事实或允许编辑目标的准确基线；返回版本与来源覆盖     |
| `synara_learning_commit` | 每次提交一个 Memory 条目或一份 Skill 修订，携带 requestId、基线和来源引用 |
| `synara_learning_revert` | 按确定的 changeId 撤回；与现有界面撤回调用同一服务                        |

客户端只提交内容、目标、基线和引用。宿主从实际 session、活跃 turn、Expert 绑定、账户实例和学习状态派生可信调用身份；不接受模型自报 owner、epoch、`automatic`、`manual` 或扩大权限。学习写能力只对支持的受管 OMP/Pi Expert 会话授予；发放、恢复、凭证轮换和每次提交重新核对。

写入准入固定为宿主在该 Run／turn 接受时保存的 `LearningGrant`，绑定当时的 epoch、原生生命周期和范围，沿用原 Run 持久配置记录；每次调用与当前状态比较。不能在旧请求调用时取“最新 epoch”重新授权，因此关闭后重开也不会复活旧工具请求或旧 continuation 的写入权。准入失败不取消该业务任务。

前台来源使用当前已接受的用户消息和已持久接收的有界工具事件，经过宿主身份校验后固定；不调用只接受 completed turn 的旧 `sourceFor()`，也不伪造完成时间。来源尚不可核对时转为明确的延后处理回执，由原后台路径在证据到达后处理，不能先声称保存成功。

前台只处理明确的小修订，成功即保存并返回准确回执，不再强制启动另一轮模型复盘。复杂材料和方法归纳由原协调器后台处理；后台仍使用同一 Harness 的既有无工具用途，不继承前台业务工具。

开关关闭后，旧会话即使仍持有工具定义也不能提交；开启后的新独立 Run 正常获得能力。关闭期间的用户显式编辑／撤回继续通过原 owner 操作入口，不允许 Agent 仅声称“用户要求”绕过开关。自然语言纠偏可立即调整本次回答；长期写入遵守同一开关。这一行为作为本次推荐，实施前随局部交互一起确认。

### 6.2 一套正式变更回执

新增最小 `LearningChangeSet`：记录 requestId、内容指纹、来源、实际主体、目标资产、前后版本、正式操作引用和结果。原生执行状态仍归原任务，Skill 保存／派生／绑定仍复用既有持久意图；不为前台调用伪造后台提炼任务或重复保存一套任务状态。

每个提交只涉及一个资产；多个进化点沿用串行推进。Memory 在 SQL 内原子提交，Skill 继续用既有保存未绑定恢复。只有实际保存并绑定完成的 Skill 或正式提交的 Memory 才记为生效，不承诺文件存储与 SQL 跨存储事务。

前台与后台以准确来源、目标主题和变更回执去重：前台已提交的部分不再重复提炼，其余新信息仍可后台处理。撤回也记录已经处理的原信号，避免后台马上把同一条错误规则重新学回；之后新的明确反馈可再次修订。

后台发现／生成协议扩展为 Skill、Memory 或无变化的明确结果类型。显式提供的适用 Memory 可以作为冻结输入，仍不允许后台自行访问环境 Memory。同步更新固定提示词、协议版本和 OMP/Pi 发送前断言，保留精确 OMP 构建校验、空工具、隔离目录、原生取消和原账户／模型。

## 7. 指定资料学习

资料来源限定为当前任务实际读取的片段，或用户明确指定且宿主可核对权限的文件／受管附件。前台可沿用原生阅读工具；后台只接收宿主已固定的资料，不增加浏览器、文件系统或网络工具。

扩展来源引用为消息、运行事件、工作区文件、受管附件和所选片段，保存准确身份、内容摘要、hash、范围与截断说明。复用现有 [工作区读取](../apps/server/src/workspace/Services/WorkspaceFileSystem.ts)、[路径约束](../apps/server/src/workspace/realPathContainment.ts)、[附件归属](../apps/server/src/agentGateway/delegatedAttachments.ts)和[附件路径](../apps/server/src/attachmentPaths.ts)能力，不另写万能文件读取器。

第一版直接支持可解码文本和 Markdown；PDF、图片等复用当前 Provider 已实际读取的内容，不新增 OCR 或独立解析服务。网页复用本任务已授权读取的结果，不把任意 URL 当作后台抓取授权。内容无法读取时记录缺失，不阻塞业务任务或声称学会；资料中的指令不授予工具权限。

建议初始预算：每次最多 5 个资料引用，总提炼文本 128,000 字符；单条 Memory 正文 4,000 字符；Run 首屏规则正文合计 24,000 字符。均为内部上限，超出时提供截断和继续按准确版本读取的能力，不增加用户设置项。字节读取另有上限，实施时用既有存储与附件限制中的较小值，不能先无限读取再截断。

## 8. 细粒度撤回与成长记录

Memory 撤回生成新修订或停用对应条目，不删除历史；Skill 撤回按原变更的前后内容计算逆向修改，并在当前版本上校验适用性。只撤回原变更触及的字段、文件或可确定文本片段，保留之后不相干的修改；不得将整包恢复冒充局部撤回。

当前内容仍等于原提交后内容时可直接逆向；后续变化与其无交集时合并逆向；同一片段已被再次修改、定位不唯一或资源无法恢复时，不猜测覆盖。该次用户发起的撤回可展示具体冲突并保留现有完整版本恢复入口，不能自动回退后续有效工作。撤回本身检查准确基线、可重试、记来源并受原提交门协调。

新建 Skill 的学习撤回，只有确认该绑定和资产没有后续有效改进时，才移除本专家对应绑定；执行既有安全删除还必须满足其他引用检查。若之后又学到了有效内容，保留绑定并尝试分离原创建变化，无法分离则按上段报告具体冲突，不能以解绑连带停用后续成果。共享原版不因撤回被改写。自然语言“撤回刚才那条”只能在当前上下文能准确关联 changeId 时直接处理，不能用跨会话正文搜索猜目标；歧义只影响这次撤回，不阻断自动学习主流程。

实施澄清（2026-10-31，主会话按既定连续学习目标收敛）：上段“新建”指从零创建。首次共享派生由宿主选择不冲突的专家专属名称，并固定进原操作意图；学习撤回保留这个专属 Skill 的身份、名称和当前绑定，仅逆向该次内容与可逆元数据。这样撤回后新反馈仍更新同一个副本，不因留下未绑定的旧副本而阻断学习。完整恢复共享绑定继续使用既有显式恢复绑定能力；不新增用户确认、不放宽未绑定资产的修改权限，也不删除旧副本或重写历史意图。

星图继续展示实际能力变化，新增 Memory 与撤回的类型化投影，复用现有 Skill 事件和 Memory 正式回执，不维护第二套星图知识库。节点可说明“已记住报告偏好”“已修正环境路径”，详情查看来源、差异、版本及撤回；无变化不新增节点，不把未经实际使用的修订标为效果提升。

界面仅调整既有 Expert 进化页与变更详情，不新增一级导航、Memory 管理台、范围下拉框或审批队列。真实父布局仍为 `_chat`，复用 `SettingsEditorDialog`、窄客户端、原查询缓存、草稿保护和 disclosure。正式实现前展示这次新增详情／撤回交互的局部原型；第一阶段的原型批准不自动覆盖这些新增交互。
