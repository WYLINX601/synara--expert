## 2026-10-26 本轮范围与产品方案

来源：用户逐项取舍 G1—G11，要求先理解需求、制定产品与研发方案；随后明确选择“下一次运行使用新版”，包括尚未开始的排队运行和同一任务的下一次运行。以下是需求依据与推荐产品行为；页面细节、协议形状和研发安排仍属于本轮方案，不代表已经实现或验收。

### 范围决定

| 对比项               | 用户决定                     | 本轮产品结果                                                                                |
| -------------------- | ---------------------------- | ------------------------------------------------------------------------------------------- |
| G1 Claude 可用性     | 需要解决                     | 四端均覆盖空/非空装配；解决 CLI/SDK 兼容、真实加载与调用，不能用取消校验代替修复            |
| G2 浏览器目录导入    | 暂不设计                     | 桌面为主要使用条件；不增加浏览器文件夹上传                                                  |
| G3 Markdown 阅读预览 | 按本轮新参考图纳入           | 详情文件页提供阅读预览 / 编辑切换，沿用完整包与版本保护                                     |
| G4 筛选排序          | 对齐 Multica                 | 使用状态、来源、Expert、创建者、标签筛选；名称、使用 Expert 数、创建/更新时间排序           |
| G5 外部检索          | 暂不做                       | 保留已有 GitHub 等 URL 导入，不建设 Skill 市场搜索                                          |
| G6 批量装配          | 前后端对齐                   | 列表选择 N 个 Skill，增量装配给 M 个 Expert，服务端返回逐 Expert 结果                       |
| G7 管理 CLI          | 需要                         | 提供结构化 Skill/绑定管理，为后续 Synara 管理 Agent 复用；本轮不创建或启用该 Agent          |
| G8 工作区            | 不做                         | 保持个人实例 owner 权限，不引入工作区、成员或多租户模型                                     |
| G9 机器扫描          | 不做                         | 不增加机器发现、跨机扫描和分发；已实现的当前主机只读清单保持原范围                          |
| G10 适配范围         | 现有四端                     | 仅 Codex、Claude Code、Pi、oh-my-pi                                                         |
| G11 原生执行元数据   | 允许装配，不以字段限制       | 合法 Skill 不因 `context/agent/model/hooks` 等字段被拒绝装配；保留原文，由所选 harness 解释 |
| 更新迭代             | 对齐 Multica，下一次运行生效 | 身份、绑定、标签保留；当前运行不变，未启动的排队运行与下一次运行使用更新后的内容            |

“不以字段限制装配”不等于四端具有相同的原生语义。Synara 不新增字段黑名单，也不静默删除字段或把原生执行功能降格为提示文字；某端实际不支持的语义按该端的真实结果说明。已有宿主授权、凭据和模型策略继续适用，Skill 不自行授予权限。

### 继续保持的产品契约

- Expert 只使用装配的 Skill；空装配为零，不回退到环境、项目、插件或内置 Skill。
- 未选择 Expert 时，沿用 harness 自身的 Skill 行为。
- 现有完整资源包、二进制、稳定 `skillId` 和来源信息继续复用，不重建第二套库。
- 更新和批量装配均不修改原始来源目录；导入、检查和预览不执行 Skill 的 hooks、脚本或 setup。
- 原生子运行若由 Skill 的原生语义触发，必须纳入同一装配边界的研发与验收；不能继续一概阻断子代理后宣称 G11 已完成。

### G4：列表与检索

复用 Settings → Agent skills 的既有父布局与列表，不新增顶级页面或浏览器专用设计。

| 维度                   | 推荐行为                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| 文字搜索               | 保留名称/说明/标签搜索，不缩减为只搜索名称                                                            |
| 使用状态               | 已使用/未使用；按保存的 Expert 绑定判定，disabled 绑定仍算已绑定；另外区分已启用数量                  |
| 来源                   | 手工、GitHub、Skills.sh、ClawHub、本地目录、归档、运行时副本                                          |
| Expert / 创建者 / 标签 | 支持多选；维度之间 AND，同一维度内部 OR；创建者不引入成员系统，旧记录显示未知                         |
| 排序                   | 名称、绑定 Expert 数、创建时间、更新时间，均可升/降序；默认最近更新优先；并列以名称和稳定 ID 确定次序 |
| 历史缺字段             | 不将 `updatedAt` 伪造为创建时间；未知时间排在已知时间之后                                             |
| 选择与结果             | 筛选不静默清空选择；明确显示已选数和隐藏在当前筛选之外的已选数，批量动作使用可核对的确定集合          |

2026-10-26 用户提供 Multica 截图后，本页交互调整为“搜索框 + 筛选 + 排序”：五类筛选统一收进一个下拉菜单，保留多选、已选条件数与清除筛选；清除条件不清空关键词。排序弹层组合字段、升降序和显示信息开关；默认显示被谁使用、添加者、更新时间，隐藏来源、创建时间，与所提供截图一致。显示开关只影响当前页面，不新增服务端偏好配置；列表的检索、排序和批量选择语义沿用上表。

### 导入入口补充：从运行时复制

2026-10-26 用户进一步确认：将页面常驻的“运行时与项目技能”收进“导入技能”，参考其提供的 Multica 两步弹窗。技能页与导入方式选择页均不发现外部技能；进入“从运行时复制”并选择 Codex / Claude Code / Pi / Oh My Pi 后，才读取该运行时的本机技能目录。提供搜索、当前结果全选、已选计数与直接批量复制，用户无需填写运行时目录或逐项手工预览。移除常驻的项目路径输入，不扩大到工作区或整机扫描。

来源保持只读；同名默认跳过，部分失败逐项呈现并保留失败选择以重试。复制完整资源包，只登记用户勾选的入口，不顺带登记包中其他 Skill，也不自动装配给 Expert。非 SKILL.md 格式的运行时说明文件明确标注暂不支持复制。普通任务和已运行任务的 Skill 行为不因导入发生变化。

### 详情页补充：概览与文件

2026-10-26，用户提供 Multica 的概览、文件两个详情页截图并要求能力对齐；本次将 Markdown 阅读预览纳入，替代此前 G3 的“暂不做”。入口仍为现有技能列表，详情采用适应窗口的大面板与“概览 / 文件”页签。

- 概览集中编辑名称、描述与标签，显示文件数、使用专家数、添加者和更新时间。默认只列已绑定专家，新增绑定通过“添加到专家”展开选择；来源路径和技术版本折叠显示。详情删除进入既有影响确认，不直接删除。
- 文件页区分主文件与附属文件，按目录展示并可折叠。Markdown 默认阅读预览，支持标题、列表、表格和包内引用；可切换源码编辑，保留新建支持文件、上传/替换、下载、删除等能力，主入口不能删除。
- 描述保存写回所选 SKILL.md 的 frontmatter；原始文件编辑的元数据在保存后读回，名称和描述不另建第二份来源。保存继续使用版本检查与未保存保护，变更在下一次运行生效。
- 预览不执行脚本或 HTML，不自动加载外部图片；包内链接限定于已有资源路径。切换预览、编辑或页签保留草稿，关闭与切换文件继续使用原有保存/放弃确认。

2026-10-26，用户补充 UI 交付规格，并进一步确认使用 Synara 常见浅色边框，概览适当加宽、文件适当收窄且切换宽度一致：两页统一最大 **920px**，正文撑满内容区，沿用自适应窄屏与独立滚动。此确认替代 680px 概览与宽文件页的临时方案。表单移除整行分割线，采用紧凑标签列；顶部来源、文件计数分为徽章，页签使用文字下划线；标签使用可增删胶囊与行内输入，输入中的待添加值同样纳入未保存保护。空状态内提供添加专家按钮，生效说明使用信息提示条，删除保留影响确认；未修改时保存禁用，关闭热区为 36px。字体与颜色沿用主题及用户字号；对比度、键盘顺序与审计结果按实际检查记录，不把交付规格中的估算或目标分数视为验收事实。

### G6：N × M 批量装配

1. 在现有 Skill 列表多选，进入“添加到 Expert”，再选择目标 Expert。
2. 确认前显示“选中 N 个 Skill / M 个 Expert”，以及实际新增、已绑定跳过和不能处理的数量。
3. 只追加缺少的绑定，新绑定默认 enabled + on-demand。已有绑定即使 disabled 也不重启、不改加载时机，不覆盖原有 Skill、Persona、模型或 MCP。
4. 同一 Expert 内所有新增绑定一次保存；多个 Expert 独立提交，返回成功、无变化、冲突、失败，支持只重试未成功项。不能把部分成功写成全部成功或整批回滚。
5. 遇到旧式技能配置，走已有显式转换流程；批量操作不得清空旧角色/工作流，结果指出需要转换的 Expert。

### G7：面向管理 Agent 的 CLI

本轮提供 `synara skill …` 与 `synara expert skills …` 命令，覆盖查询、创建/编辑、文件、导入、来源更新、标签、删除、单 Expert 绑定及 N × M 批量追加。修改操作与桌面走同一服务端能力，并提供 JSON、确定错误码、revision、dry-run 和部分成功结果。首次在已登录的桌面由 owner 授权本机管理客户端，颁发只覆盖 Skill/绑定管理的凭据，支持过期和撤销；普通 MCP 配对凭据不自动获得管理权。

后续管理 Agent 的使用路径是“读取状态 → 提出/预演变更 → 调用同一命令能力 → 读回核验”。本轮不创建默认 Agent、不自动绑定管理技能，不新增自动学习、自动改写 Skill 或自动发布。将来 Agent 提出经验改进时，仍通过本轮的内容保存与版本发布通道，不直接改数据库或内容包。

### Skill 更新与迭代

| 更新方式             | 用户动作与结果                                                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 手工修订             | 编辑正文/资源后保存，原 Skill ID、绑定、标签和来源保留；发布新的不可变内容头版本                                                         |
| 托管来源更新         | GitHub/Skills.sh/ClawHub Skill 可在详情、列表菜单、批量工具栏或 CLI 执行“更新”；替换名称、说明、正文及完整支持文件，保留身份、绑定与标签 |
| 本地改过的来源 Skill | 更新前明确告知会覆盖本地编辑；确认覆盖后整包替换，不静默合并冲突；可选查看资源差异，不强迫每次经过独立预览弹窗                           |
| 手工/归档/运行时副本 | 不参加“从托管来源更新”；通过编辑或重新导入并替换原 Skill ID 迭代。批量更新中记为 skipped，不记为下载失败                                 |
| 无变化 / 失败        | 相同内容记 unchanged；下载、校验、同名冲突或并发 revision 冲突均不改旧头版本                                                             |
| 来源版本             | 分支/发布频道按原来源跟踪；显式固定 commit/tag 的来源仍固定，不擅自改成默认分支                                                          |
| 批量结果             | 每个 Skill 独立处理并报告 updated / unchanged / skipped / conflict / failed，可只重试失败项                                              |

本轮不增加定时更新、后台监听或自动从任务复盘修改 Skill。对齐的是可复用身份、来源覆盖更新、批量结果及后续运行生效，而不是把 Multica 的工作区或远端运行时一起引入。

### 新版生效时点（已确认）

Run 指一个执行意图从开始到完成/取消/失败的执行单元，落盘根 Run 与底层 turn 的关系，不将每个 turn 都当作新 Run。同一用户请求的自动 goal 续跑、同一 Hub 工作项的自动续跑/重投、工具调用、审批等待、steering 和故障恢复继承原根 Run 装配。Hub 中独立派发给其他 Expert 的工作项是独立 Run，不与 harness 原生子代理混同；同一 Chat/Hub 任务可以有多次 Run。

| 状态                                        | 使用的 Skill                                |
| ------------------------------------------- | ------------------------------------------- |
| 尚未开始的排队 Run                          | 真正启动前解析当前已保存绑定及 Skill 头版本 |
| 正在运行或等待审批                          | 继续使用该 Run 已固定的装配和内容           |
| 同一 Run 的恢复/重投                        | 继续使用已落盘装配，不追随最新头版本        |
| 同一任务下一次用户请求 / 已结束后的显式重试 | 新 Run 重新解析最新版                       |

例如 Run A 使用 r3，期间库更新为 r4：A 的工具、审批与恢复仍用 r3；尚未开始的 B 和后续 C 使用 r4。Expert 的 Persona/MCP 等仍遵循原任务规则，不因 Skill 更新暗中切换；Skill 绑定来源版本与实际内容版本单独记录。

若 A 的后台原生子任务仍占用同一共享进程，B 保持排队，待其结束或用户显式停止后再真正启动并解析当时最新版；不通过强杀后台任务切版，也不承诺本轮新增同一 native session 的并行换版。进程初始化可能执行 Skill 副作用，因此装配必须在这种初始化前落盘；初始化是否完成不确定时进入可见恢复状态，不自动重复执行未知副作用。

## 案例暴露的产品问题

**本案例支持的判断是：Skill 资源的配置状态，不能单独代表它在某个任务中的可用状态。** 完整的技能包仍可能依赖特定工作目录、项目配置或初始化动作。

由此可以提出一个产品问题：用户为 Expert 选择 Skill 后，怎样知道它是否能够在当前任务中真正开始工作；如果不能，怎样理解原因并继续？这是根据案例提出的讨论切入点，尚未成为用户确认的产品目标。

需要进一步区分以下信息。这里用于分析用户需要知道什么，不预设新增状态机或界面：

- **资源完整性**：所需文件和入口是否存在，版本是否一致。
- **Expert 选择**：本次 Expert 或任务选择了哪个入口及版本。
- **执行环境**：实际工作目录是否具备该 Skill 所需的配置、脚本和依赖。
- **实际执行**：官方入口是否成功激活，并开始用户要求的工作。

这一个案例尚不足以证明所有 Skill 都需要初始化，也不足以确定统一的准备流程。

## 后续可讨论的能力方向

下表由 John 案例引出，均为候选方向。每项列出用户可观察的效果，便于后续决定是否纳入范围。

| 候选方向           | 要回答的产品问题                               | 若纳入范围，期望的可观察效果                                                 |
| ------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------- |
| 区分配置与可用状态 | “已经绑定 Skill”具体说明了什么？               | 用户能区分资源已配置、环境未就绪与实际工作已开始                             |
| 明确执行位置       | Skill 依赖应在哪个目录准备？                   | 用户能确定当前任务实际使用的目录，并理解它与关联代码仓库的关系               |
| 解释前置阻塞       | 缺文件、缺初始化、执行失败或范围限制如何区分？ | 用户能看到与本次任务有关的具体原因和下一步处理项                             |
| 处理后继续原工作   | 补齐依赖后如何恢复讨论？                       | 用户能回到原任务继续，并以实际激活结果判断是否恢复；单纯重新派发不被当成修复 |

上述能力由谁检查、何时检查、如何展示，以及哪些动作可自动执行，均待讨论。当前不确定新的页面、控件或交互流程。

本次讨论应复用既有概念，避免将“管理资源”“准备执行环境”和“从任务中改进方法”混成一个问题。

| 既有对象或方向             | 已有文档中的职责                               | 对本次讨论的约束                                          |
